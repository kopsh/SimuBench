# 产品形态决策

状态：草案，待确认

## 1. 首批深度试用用户

| 用户 | 他们在做什么 | 对 SimuBench 的核心诉求 |
| --- | --- | --- |
| 仪表开发工程师 | 开发仪表本身：命令集（SCPI 命令树）、状态与错误系统、上位机软件、仪表驱动 | 硬件样机就绪前，先有一台“行为对”的虚拟仪表，用于开发和联调上位机软件、驱动与自动化接口 |
| 校准软件开发工程师 | 开发校准程序：驱动标准源/标准表与被校仪表，完成核查（as-found）、调整（adjust）、复核（as-left），写入校准常数，生成证书数据 | 不占用昂贵标准器和被校仪表，就能开发和回归测试完整校准流程，包括超差、调整失败等异常路径 |

两类用户的共同点：

- 都是**开发者**，在本地 IDE 中用 C/C++、C#、Python、LabVIEW 等编写程序，通过 VISA / SCPI 与仪表通信；
- 都在处理**未发布或敏感**的资产：未上市仪表的命令集与内部设计、校准方法与校准常数；
- 都需要**确定、可复现**的运行结果，用于调试与回归。

## 2. 决策

**本地优先（local-first）。仿真引擎在用户本机或内网运行；协作与资产管理作为后续能力，以私有化部署为主，公有云 SaaS 为辅。**

### 理由

1. **通信延迟**：仪表与校准程序是高频的命令-应答交互，一个校准流程可达数千条命令，必须在本机或局域网内完成。
2. **兼容现有工具链**：这两类用户的程序大量使用 NI-VISA / Keysight VISA 等，而不只是 PyVISA。本地提供标准 TCP/IP 仪表接口，任何 VISA 实现都能通过资源地址直接连接，程序无需修改。
3. **保密与合规**：仪表厂商不会把未发布型号的命令集和内部模型放到公有云；校准实验室常有内网或断网要求。
4. **可复现**：本地引擎版本固定、随机种子固定，问题可以精确重现，也能进入用户自己的持续集成。

### 不选纯 SaaS 的原因

纯 SaaS 适合教学、演示与试用，但对首批用户而言，延迟、接入方式与保密三点都不满足。云端托管引擎保留为后续的试用/教学形态。

## 3. 对产品能力的影响

首批用户决定了 SimuBench 的重点与 EdgeSim 不同：EdgeSim 面向“使用仪器的测试工程师”，SimuBench 首先面向“开发仪器和校准仪器的工程师”。

### 3.1 仪表开发工程师需要

- **自定义仪表**：定义新的仪表模型，而不只是使用现成型号，包括：
  - SCPI 命令树：参数类型、单位、范围、默认值、查询格式；
  - IEEE 488.2 公共命令与状态系统：`*IDN?`、`*RST`、`*OPC`、`*ESR?`、`*STB?`、服务请求（SRQ）、状态寄存器；
  - 错误队列与错误码；
  - 内部信号链：由功能器件组合而成（参考 Liquid Instruments 的模块化思路），测量结果由配置和输入决定。
- **协议层保真**：终止符、超时、二进制块数据（`#<n><len><data>`）、命令同步与重叠命令等行为要与真实仪表一致，否则上位机软件在虚拟环境通过、在真机上失败。
- **快速迭代**：修改仪表定义后立即生效，可与真实样机的行为做对比。

### 3.2 校准软件开发工程师需要

- **计量误差模型**：仪表读数 = 真值 + 误差。误差包括偏置、增益、非线性、噪声、漂移、温度系数，按量程/功能分别建模。
- **可调整的校准常数**：仪表内部保存校准常数，调整命令会真实改变后续读数；支持校准安全（密码/锁定）、校准计数、校准日期等。
- **标准器**：提供标准源与标准表（如多功能校准源、高精度数字表），其自身也有不确定度。
- **单元个体差异**：用种子生成“一批”虚拟仪表，每台误差不同，可模拟合格品、超差品、无法调整的故障品。
- **异常路径**：通信中断、调整超限、标准器超出有效期、读数不稳定等，可按需注入。
- **自己构造 DUT**：被校仪表由校准软件工程师自行定义，而不是只能从平台提供的型号中选择（见 3.3）。

### 3.3 用户自建 DUT

在校准场景中，DUT 就是被校仪表本身。因此“构造 DUT”与仪表开发工程师“定义仪表”是同一种能力，SimuBench 应提供**统一的仪表/DUT 定义模型**，而不是两套机制。

校准软件工程师构造一个 DUT，需要描述：

| 组成 | 内容 |
| --- | --- |
| 接口 | SCPI 命令树，含校准专用命令（解锁、施加校准点、存储常数、查询校准计数/日期），支持厂商私有命令 |
| 功能与量程 | 测量/输出功能、量程、分辨率、量程切换规则 |
| 技术指标 | 按功能/量程/校准周期（24 h、90 d、1 年）的准确度表，如 ±(读数 ppm + 量程 ppm)，用于判定合格并约束误差生成 |
| 误差模型 | 偏置、增益、非线性、噪声、随时间漂移、温度系数等参数 |
| 校准常数与调整模型 | 常数如何存储、如何作用于读数；调整算法在 DUT 内部完成（施加标准值后由仪表计算），还是由校准软件计算后写入 |
| 端口 | 与测试台上标准器连接的输入/输出端口 |
| 个体分布 | 误差参数在一批仪表中的分布，可指定某台为超差品或故障品 |
| 故障 | 读数不稳定、某量程无法调整、常数写入失败、通信异常等 |

#### 构造方式：由浅入深

1. **模板**：选择仪表类别（如数字万用表），填写量程、指标表和误差参数，无需写代码；
2. **声明式文件**：可读、可 diff 的定义文件，便于版本管理与共享；
3. **代码扩展**：厂商私有的调整算法或特殊行为，用插件实现。

示意（格式未定）：

```yaml
dut: acme-dmm-6500
class: dmm
functions:
  dcv:
    ranges: [0.1, 1, 10, 100, 1000]        # V
    spec:
      1y: { reading_ppm: 35, range_ppm: 5 }
    error_model:
      offset_ppm_range: { dist: normal, sigma: 3 }
      gain_ppm:         { dist: normal, sigma: 15 }
      drift_ppm_per_year: 10
      noise_ppm_range: 0.5
calibration:
  security: { password: "CAL-1234" }
  constants: per_range [offset, gain]
  adjust: internal                          # 仪表根据施加的标准值自行计算常数
  points: { dcv: [zero, full_scale] }
```

#### 仿真带来的独特价值：已知真值

真实校准中，被校仪表的真实误差是未知的，只能通过标准器间接测量。在 SimuBench 中，每台虚拟 DUT 的真实误差、漂移和校准常数都是已知的。这使平台可以作为**校准软件的判定基准**：

- 校验校准软件算出的常数是否正确；
- 校验 as-found / as-left 的合格判定是否正确，包括临界值附近的误判；
- 校验不确定度计算是否合理；
- 在一批个体差异不同的 DUT 上做回归测试。

## 4. 交付形态（建议）

| 阶段 | 形态 | 内容 |
| --- | --- | --- |
| 第一阶段 | 本地引擎 + 命令行 | 测试台文件格式、仪表定义格式、SCPI over TCP 接入、进程内 SDK、运行记录 |
| 第二阶段 | 本地桌面/本地 Web 界面 | 可视化画布、仪表状态与信号观察、故障注入、运行记录分析 |
| 第三阶段 | 协作平台（私有化部署优先） | 资产库、共享、版本管理、团队协作；可选云端托管引擎用于试用与教学 |

测试台文件与仪表定义文件是各阶段之间的核心契约：它们可读、可 diff、可放入 Git，因此在协作平台就绪之前，用户已能用 Git 完成版本管理。

## 5. 待确认问题

1. **仪表开发工程师要仿真的是哪一层？**
   - A：仿真整台仪表的外部行为，代替仪表固件，供上位机软件、驱动开发使用；
   - B：仿真仪表内部硬件（ADC/DAC、继电器、量程切换等），让用户自己的固件逻辑运行在虚拟硬件之上。
   - 两者的架构差异很大，A 是第一阶段的默认假设。
2. **首批仪表类别**：哪 2–3 类仪表最先需要（例如数字万用表 + 多功能校准源）？
3. **接入协议优先级**：raw socket（端口 5025）、VXI-11、HiSLIP、USBTMC、GPIB 中，用户现有程序主要使用哪些？
4. **用户的主要开发语言与 VISA 实现**，决定 SDK 的优先语言。
5. **是否需要与真实仪表对比**：同一程序分别跑真机与虚拟仪表，自动比对结果差异。
6. **DUT 的构造入口**：校准软件工程师更习惯填表/图形界面，还是直接编辑定义文件？
7. **调整算法的归属**：首批 DUT 的调整是仪表内部完成为主，还是校准软件计算后写入常数为主？是否需要用户用代码自定义调整算法？
8. **指标数据来源**：是否需要从数据手册或现有表格（如 Excel 指标表）导入技术指标？

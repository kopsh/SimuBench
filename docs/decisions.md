# 决策记录

记录产品讨论中已经确定的结论。每条包含结论、理由，以及仍待细化的部分。

收录门槛：一条选择要**同时满足**以下两点才记入——有实际备选方案（两条路都说得通，以后有人可能想翻案）；影响超出单个功能（文件格式、API、术语、产品范围、安全模型等）。功能本身的说明放在 issue、PR 与对应文档。修改已有决策时改原条目，不另加新条目；已有条目保持编号不变。

## D1 产品方向：用软件定义的方式做仪表仿真

- **结论**：目的是纯软件的虚拟仪表，让工程师无需真实仪表即可开发和测试；方法是软件定义仪表，仪表由内部功能模块组合而成，信号在模块之间流动并被计算，测量结果由配置、输入和系统状态共同决定。
- **理由**：与 EdgeSim 这类“规则声明行为”的仿真器形成差异；误差、校准常数等可以放在它们真实所在的模块上，天然适合仪表开发与校准场景。
- **待细化**：模块之间传递的信号表示（采样流、直流值、频谱等）如何按场景选用；虚拟时间如何推进并与命令时序配合。
- **统一组件模型**：Bench 层与仪表内部使用同一套“组件 + 端口 + 连线”。仪表是封装好的组件组合，DUT、探头、线缆、衰减器、缓冲器、波形文件源也都是组件。同一种组件可在两层通用（如一阶低通既可作 RC DUT，也可作示波器带宽限制）；仪表内部任一组件的输出都可以被替换（如用录制波形替换 ADC 输出）。SCPI 命令层只把命令映射到组件参数，行为由组件决定。
- **界面以仪表展示**：组件模型是实现方式，不是默认的展示方式。Bench 页面上展示的是仪表（设置、读数、屏幕、端口）、DUT 与连线；仪表内部的组件图只在用户主动打开时展示（对应 D3 第 3 层）。仪表卡片由仪表定义自动生成（类别模板 + 通用布局，定义中可附显示提示），不为单个型号编写界面代码。

## D2 暂不考虑硬件

- **结论**：当前只做纯软件，不考虑将仪表定义部署到真实硬件。
- **理由**：聚焦产品核心；架构可以更简单。

## D3 分层使用，门槛按角色递进

- **结论**：内部模块结构是平台的实现方式，而不是对所有用户的要求。用户按需要逐层深入：
  1. **使用仪表**：从仪表库选现成仪表，通过 SCPI 等接口使用，无需了解内部；
  2. **配置仪表/DUT**：选择仪表类别模板，用数据手册的语言填写（量程、技术指标、校准点、误差参数），平台把这些参数映射到内部模块；
  3. **搭建仪表**：打开模板的模块图修改，或从模块搭建新仪表，必要时编写自定义模块。
- **理由**：校准软件工程师熟悉的是数据手册与校准流程，而不是电路框图；只有仪表开发等少数场景需要第 3 层。
- **第 3 层的只读查看提前提供**（issue 20）：Web Bench 可以打开任一仪表的内部组件图（组件、内部连线、面板端口），参数显示型号的标称值，跟随设置的参数显示当前设置；测试台为单台仪表设的个体偏差不属于型号，不在图中。编辑仍按原计划推后。
- **第 3 层的搭建由用户与 Agent 完成，平台提供能力**（设计见 [instrument-authoring.md](instrument-authoring.md)）：平台不可能提供所有型号，常见的命令方言、应答格式、波形传输与运行控制都应能在定义文件中声明；声明不了的行为用插件组件实现，已安装包的入口点默认加载，工作区中的插件代码默认不加载、需工程师显式开启；Agent 经 MCP 只创建与编辑定义文件，不写代码。界面中的定义编辑仍推后。
- **第 2 层从计量类仪表起步**（设计见 [metrology-authoring.md](metrology-authoring.md)，总 issue #86）：仪表定义新增 `deviations`，写明可偏差的参数、按量程等的分表、±限值与分布（均匀，或正态与包含因子）；测试台实例写 `deviation: from_specs` 时由测试台种子抽取个体偏差，写死的 `hidden` 值逐项优先。`specs` 仍只记录手册原文的指标，两者不自动对应：手册指标到参数的换算需要领域判断，由写型号的人完成。另一条路是从 `specs` 的结构化格式自动推出偏差，因为各厂商指标的写法差别太大而不采用。
- **搭建经 Agent，Web 用于验收与配置**（#123，设计见 instrument-authoring.md 第 7 节）：定义文件的格式是平台内部的，用户不需要了解。仪表的搭建与修改由 Agent 经 MCP 完成；Web 不提供定义的编辑（YAML、表单、组件图都不做），只用于验收（概览、命令、内部结构、试运行、用例、以仪表语言描述的修改记录）和像真实仪表面板一样的配置。另一条路是在 Web 中提供定义编辑器，因为要求用户掌握内部格式而不采用。第 2 层的仪表模板供 Agent 使用：按输入展开为一份普通定义（记下来源模板与输入），不采用运行时引用模板，以免多出一层格式、模板升级悄悄改变已有仪表。
- **影响**：门槛从用户转移到平台。每个仪表类别的模板（包括“技术指标 → 内部误差参数”的映射）需要平台以领域知识精心构建，这是核心工作量，也是竞争壁垒。首批应少而精地覆盖几类仪表。

## D4 核心价值：定标脚本上产线前先在虚拟环境跑通

- **结论**：首要解决的痛点是“定标脚本只有上了产线才发现问题”。SimuBench 的核心价值是把问题发现提前到开发阶段。
- **典型场景**：Python + PyVISA 编写的定标脚本，驱动信号源（如 UTG9604T）与示波器（如 T3DSO2000）完成定标。
- **要求**：虚拟环境必须复现产线与开发环境的差异，否则提前不了：连线与阻抗等测试台配置、仪表个体差异、异常与超限情况、通信时序与超时。
- **衡量标准**：在 SimuBench 中通过的脚本，上产线后出问题的比例。

## D5 首个接入方式：PyVISA

- **结论**：首先支持 PyVISA，脚本只需切换资源地址即可在虚拟仪表与真实仪表之间切换，其余代码不变。
- **理由**：首批用户的定标脚本使用 Python + PyVISA；脚本若需为仿真而修改，验证结果就不可信。

## D6 CI 是场景之一：引擎可无界面运行

- **结论**：CI 是重要场景之一，但不决定产品形态。引擎必须能以无界面方式运行（命令行 + Python 库 + PyVISA 后端），以便进入 CI。
- **CI 场景的要求**：
  1. **无界面运行**：在 Linux 容器和企业内网 CI（如 GitLab CI、Jenkins）中运行，不依赖图形界面和外网；
  2. **确定**：固定版本与随机种子下结果完全一致，CI 不能有偶发失败；
  3. **快**：虚拟时间可快于真实时间，一次 CI 要能覆盖多台 DUT、多个场景；
  4. **配置即代码**：测试台、DUT、场景都是文件，与定标脚本放在同一仓库，随代码一起版本管理；
  5. **明确的判定**：输出 CI 可识别的结果（退出码、JUnit 报告），失败时保留运行记录与种子，可在本地精确重现；
  6. （已取消）授权方式适配 CI：内部工具不设授权（D17）。
- **判定依据**：脚本“跑完没报错”不等于通过。虚拟 DUT 的真实误差已知，可以检查脚本写入的定标系数是否正确、合格判定是否正确。

## D7 可视化不后置；引擎与界面分离

- **结论**：可视化是第一个版本的一部分。引擎与界面分离：引擎通过接口对外提供测试台状态、信号与事件，界面只是客户端。
- **界面需承担的工作**：观察仪表状态与波形、修改参数与注入故障、控制虚拟时钟、查看 SCPI 通信记录、回放运行记录、展示与编辑测试台拓扑。
- **展示原则**：无论 Web Bench 还是 TUI，Bench 页面都以仪表为单位展示（见 D1）。
- **已决定**：第一个界面是 Web Bench（见 D18）。

## D8 Bench 是核心对象

- **结论**：Bench 是 SimuBench 的核心对象。用户创建、打开、运行、观察、保存、复制、共享、版本管理的都是 Bench；其他概念都属于某个 Bench 或服务于 Bench。
- **Bench 包含**：
  - 仪表：来自仪表模型（或模板）的实例及其配置；
  - 元件：RC 网络、电阻、缓冲器等不带命令层的对象（#100 之前称为“DUT”）；
  - DUT 是**角色**而不是一类对象：仪表或元件都可以标为 DUT（被测/被定标对象），例如定标时被校的万用表就是 DUT，而接在电路中的 RC 网络可能只是夹具或负载。测试台文件中写作 `dut: true`（格式 `bench/2`，`bench/1` 的 `duts` 读取时迁移为标为 DUT 的元件）；也可以没有 DUT（仪表自检、演示）。另一种做法是保留 DUT 这一类、再给仪表加“被测”标记，没有采用：同一个词会同时指一类对象和一个角色；
  - 连线与配件：线缆、衰减器、三通、负载等；
  - 运行条件：随机种子、虚拟时钟设置；
  - 故障与场景：预设的故障条件及触发时机。
- **与 Bench 相关但不属于 Bench 的**：
  - 仪表模型库：可复用的“零件”，Bench 引用它们；
  - 测试程序（如定标脚本）：在 Bench 之外，通过资源地址连接 Bench 中的仪表；
  - 运行记录：每次运行产生，归属于某个 Bench 的某个版本。
- **三种形态**：
  - **Bench 定义**：可保存、复制、共享、版本管理的文件，始终是干净的初始状态；
  - **运行中的 Bench**：由定义启动，测试程序连接并改变其状态；同一定义可同时启动多个；
  - **运行记录**：每次运行的命令、状态变化与结果，可回放、对比。
- **暂不支持保存运行状态**：运行结束后的状态（如已写入定标系数的 DUT）不回写到 Bench 定义，也不提供“快照另存为”。每次运行都从定义的初始状态开始。

## D9 三种接入方式：PyVISA 后端、本地 SCPI 网络仪表、本地 MCP

- **结论**：Bench 通过三种方式对外提供，三者都是引擎的客户端，与界面使用同一套引擎接口。
  1. **PyVISA 后端**：`pyvisa.ResourceManager("<bench 文件>@simubench")`，按 Bench 中的仪表名打开资源。Python 用户的主要方式。
  2. **本地 SCPI 网络仪表**：Bench 启动后，每台仪表在本机监听一个 TCP 端口（如 `TCPIP::127.0.0.1::5025::SOCKET`），脚本只需改地址；NI-VISA、C#、LabVIEW 等均可连接。
  3. **本地 MCP 服务**：AI Agent 通过 MCP 帮助工程师构建与部署 Bench，并控制和观察 Bench。
- **MCP 的能力（草案）**：
  - 构建：查询仪表模型库（型号、端口、支持的命令）；创建与编辑 Bench（添加仪表与 DUT、连线、配置、故障）；校验 Bench 并返回明确的错误与警告（端口不兼容、阻抗不匹配等）；
  - 由脚本生成：分析现有测试程序用到的仪表与命令，生成 Bench 草稿，并指出模型尚不支持的命令；
  - 部署：启动 Bench，返回各仪表的资源地址，生成脚本切换到虚拟环境所需的配置；
  - Bench：列出与打开 Bench、启动/停止运行、查看拓扑与仪表列表；
  - 仪表：发送 SCPI 命令与查询、读取仪表状态与测量结果、获取波形摘要；
  - 运行控制：修改参数、注入故障、暂停/单步虚拟时钟；
  - 观察：读取 SCPI 通信记录与运行记录；
  - 脚本：针对 Bench 运行一个测试程序，返回判定结果与运行记录。
- **影响**：
  - Bench 的编辑操作（添加、连线、配置、校验）必须实现在引擎中，Web 画布与 MCP 共用，而不是只存在于界面；
  - Bench 定义格式与仪表模型库要便于 Agent 理解：声明式、有完整 schema、能自我描述；
  - Agent 对 Bench 的修改落到可读、可 diff 的文件上，并实时显示在 Web Bench 中，由工程师审阅。
- **并发**：一个运行中的 Bench 可同时被多个客户端连接（脚本、pytest、界面、Agent）；所有操作按到达顺序串行执行，写入同一份运行记录。
- **真实值可见性**：作为 Bench 运行时开关。调试模式下 Agent 可读取真实值，用于定位脚本问题；验证模式下关闭，避免 Agent 在执行定标时直接读取答案。判定始终在后台使用真实值，不受开关影响。
- **进入第一个闭环**：MCP 的“由脚本生成 Bench”和“部署”纳入闭环，以及闭环所需的基础查看、SCPI 收发与脚本运行。

## D10 第一个闭环的验证场景：锁相放大器、示波器、射频信号源、频谱分析仪与 SMU

- **结论**：第一个闭环改用以下场景验证（参考 EdgeSim 的对应指南），代替“信号源 + 示波器定标”：
  1. 锁相放大器，详见 [validation-lockin.md](validation-lockin.md)。
  2. 示波器采集到电压，详见 [validation-scope.md](validation-scope.md)。
  3. 射频信号源调制，详见 [validation-rfgen.md](validation-rfgen.md)。
  4. 频谱分析仪，详见 [validation-specan.md](validation-specan.md)。
  5. 源测量单元 IV 扫描，详见 [validation-smu.md](validation-smu.md)。
- **锁相放大器与示波器场景共用同一个 RC 低通 DUT**：验证 DUT 在多个 Bench 中复用，并以“两台原理不同的仪表测同一 DUT，结果一致”作为 SimuBench 独有的验收项。
- **理由**：锁相放大器是清晰的模块化信号链，契合 D1；示波器覆盖逐点采样、触发、二进制传输与大量真机才暴露的脚本问题；被测 RC 低通有已知理论值；两者都有公开的参考输出可作为验收数据。
- **此后的型号与场景来自内部需求**：第一个闭环之后，新增或做深的型号与场景取自内部的仪表紧缺清单与在研的自研仪表，而不是参考产品的指南；按清单做深少数型号，不按类别铺开（[positioning-review.md](positioning-review.md) 第 3、5 节）。
- **已解决**：命令兼容见 D13；虚拟时间见 D12；与定标场景的关系见 D11。另有多通道场景（D15），期望值由电路理论计算。

## D11 验证分工：开发验证用参考场景，定标与自研仪表场景由使用它的工程师验收

- **结论**：开发过程中用产品负责人提供的参考场景（D10）验证引擎与仪表模型；定标场景与自研仪表场景由实际使用它的内部工程师验收（试点仪表的上位机、校准或固件工程师），产品负责人负责安排与确认验收已完成。真实型号做深后借真机对照一次：同一份用例对真机与虚拟仪表各运行一遍，差异逐条记录。
- **理由**：参考场景有公开的输出数据，可作为客观、可重复的开发验收标准；定标与自研仪表场景贴近用户的真实工作，要由熟悉仪表的人判断是否“对”。原结论是产品负责人亲自验收；产品负责人不是仪表领域的人，按手册写的定义与出自同一份手册的用例只能互相印证，不能说明与真机一致（[positioning-review.md](positioning-review.md) 2.2）。
- **影响**：定标场景所需的能力（DUT 个体误差、定标系数、真值判定）仍在闭环之后的范围内，但引擎设计不得阻碍它们；“隐藏状态”（见 validation-rfgen.md）是两者共用的基础。

## D12 虚拟时间：默认由命令驱动

- **结论**：虚拟时间支持三种推进方式，由 Bench 的运行条件选择：
  1. **命令驱动（默认）**：仪表在处理需要时间的命令时推进虚拟时钟，推进量等于该操作实际需要的时长。例如单次扫描 `:INITiate` 配合 `*OPC?` 推进一次扫描时间，示波器 `:DIGitize` 推进一次采集时间。脚本空闲、没有命令到达时（如 `time.sleep()`），虚拟时间默认跟随真实时间推进；也可由 `run.idle` 改为不计或按 `time.sleep` 精确计入（D47）。
  2. **墙钟**：虚拟时间始终等于真实时间，用于上真机前的最后一次彩排。
  3. **步进时钟**：只有显式调用推进接口时才前进，用于 SDK、pytest 与 CI 中需要精确控制时间的场景。
- **理由**：真机脚本本来就用命令或等待来同步仪表；命令驱动让未修改的 PyVISA 脚本也能获得正确的虚拟时间，同时比墙钟快，满足 D4、D5。
- **要求**：每个仪表模型必须声明哪些命令消耗时间、消耗多少；同一 Bench、同一种子、同一命令序列下结果确定。空闲的真实时间如何计入，由 D47 的 `run.idle` 选择。

## D13 兼容性：数值对齐参考场景，命令行为对齐真实仪表

- **结论**：
  - **物理与数值结果**对齐参考场景（D10）的公开输出，作为开发验收标准；
  - **命令的细节行为**（参数格式、可接受的写法、字节序等）对齐真实仪表，而不是照搬参考实现因自身模型格式造成的限制。例如列表参数加引号与不加引号都接受。
- **理由**：SimuBench 的目标是让脚本在上真机前跑通。照搬参考实现的局限，会让能在真机上运行的脚本在 SimuBench 中失败。
- **物理正确优先**：当参考实现为简化而偏离电路物理时（如把 RC 低通当作单纯的滤波操作，不计入信号源输出阻抗与 DUT 输入阻抗的相互作用），SimuBench 按物理正确求解（architecture.md 1.4 节）；受影响的期望值由电路理论重新计算，并在场景文档中列为差异。
- **信号源电平约定对齐真实仪表**：电平或幅度的定义（开路电压，或按设定负载定义）由每个仪表定义声明，与对应真实仪表一致。多数函数发生器按设定的输出负载（默认 50 Ω，可设为高阻）定义幅度，实际负载不同时输出端电压随之变化。改负载设定时保持什么也由定义声明（`amplitude_level.load_change`，#436）：`setting`（默认）保持设定值、输出随之变化；`output` 保持实际输出电压、回读的幅度与偏置按 (R+Z)/R 之比换算（Keysight Trueform 手册 Output Termination 一节）。
- **影响**：与参考实现的命令差异与数值差异逐项记录在对应场景文档中。

## D14 支持录制的波形文件（CSV / BIN）

- **结论**：工程师会使用录制好的波形文件进行开发和测试，SimuBench 支持把波形文件作为 Bench 的一部分。
- **在组件模型中的位置**：波形文件由“波形文件源”组件播放，与其他组件一样有端口、参数和行为。它可以放在两个位置：
  1. **Bench 层**：像一台信号源一样接到仪表输入端口，信号经过仪表前端（耦合、带宽、探头等）再被测量；
  2. **仪表内部**：替换仪表内部某个组件的输出（例如 ADC 之后的原始采样），绕过前端，直接驱动后续处理与测量。
- **用途**：
  - 优先：作为激励，用真实采集的信号驱动仪表和 DUT；作为仪表的返回数据，示波器等仪表按录制数据返回波形；
  - 以后：作为参考结果与测量结果比对；导出为 CSV / BIN 供其他工具使用。
- **需要定义的规则**：
  - 格式：CSV（时间与数值列，或数值列加采样率）；BIN（原始 int16 / float32 等，需要说明数据类型、字节序、采样率、比例、偏置、通道数的元数据）；
  - 采样率与仿真不一致时的重采样方式；文件结束后的行为（循环、保持最后值、归零）；与虚拟时钟的对齐；
  - 计算路径：录制信号没有解析式，走数值路径（与任意波、PRBS 相同），受相同的能力上限约束；
  - 可复现：Bench 通过相对路径引用文件，运行记录保存文件哈希；大文件按需加载。

## D15 仪表支持多通道

- **结论**：仪表可以有多个通道（如四通道示波器、四通道信号源），多通道从一开始就纳入组件模型与命令映射。
- **在组件模型中的位置**：
  - **通道是仪表内部重复的一组组件**（如示波器每个通道各有前端、耦合、带宽、ADC），各通道有自己的端口（CH1–CH4、OUT1–OUT4）、参数与隐藏状态；
  - **通道不一定相同**：同一仪表的不同通道可以有不同能力（如 UTG9604T 的 CH1/CH2 为 600 MHz、2.5 GSa/s，CH3/CH4 为 200 MHz、625 MSa/s），因此通道由“通道定义 + 每通道参数”实例化；
  - **共享组件**：时基、触发、存储深度等由多个通道共享，例如触发组件按触发源选择通道；
  - **通道间关系**：通道间相位同步、通道组合（如信号源 CH1 与 CH2 合并）、数学通道（如 CH1 − CH2）由跨通道组件实现。
- **命令映射**：命令中的通道序号（如 `:CHANnel<n>:SCALe`、`:SOURce<n>:FREQuency`、`:OUTPut<n>:STATe`、`:WAVeform:SOURce CHANnel<n>`）映射到第 n 个通道的组件；省略序号时按真实仪表的默认规则（通常为 1）。
- **展示**：仪表卡片按通道展示；示波器在一个屏幕上用不同颜色显示多条迹线，信号源逐通道列出设置与输出状态。
- **确定性**：各通道的噪声相互独立，并由 Bench 种子确定。
- **与其他决策的关系**：每个通道可以有独立的隐藏误差与定标系数（定标场景）；多列 CSV 可映射到多个通道（D14）。
- **验证**：见 [validation-multichannel.md](validation-multichannel.md)，期望值由电路理论计算。
- **待细化**：通道间共享资源的约束（如开启通道越多、每通道采样率越低）；通道间时延与串扰（与定标场景中的通道间时延定标相关）。

## D16 可观测性是一等能力：用户可观测，运维可运维

- **结论**：可观测性是 SimuBench 的核心能力，在架构中单独设计，面向两类对象：
  - **用户可观测**：工程师看清仪表、信号与运行过程；
  - **运维可运维**：产品团队能监控、诊断和改进分布在用户本机、内网与 CI 中的 SimuBench。
- **理由**：真实测试台很难看清“里面发生了什么”，仿真中所有信号与状态都是计算出来的，可以完整地观察、解释和回放；同时 SimuBench 本地优先运行在用户环境中，产品团队必须有办法在不接触用户机器的情况下定位问题。

### 用户可观测

1. **虚拟探针**：在任意网络或仪表内部组件的端口上观察信号，不影响电路；
2. **状态**：仪表设置、组件参数、隐藏状态与真实值（受 D9 的可见性开关约束）；
3. **通信**：每条命令与响应，带虚拟时间与真实时间；
   界面与 MCP 中的操作（修改值、注入故障、推进时钟）同样作为动作记录，并与 SCPI 命令区分；
4. **事件**：错误、过载、失锁、超出模型能力、故障注入等，带发生时间与来源组件；
5. **因果解释**：任一读数可以追溯到产生它的组件、信号描述与参数；
6. **保真度标注**：结果中的近似（截断、离散化、能力上限）被明确标出；
7. **时间线**：命令、状态变化、事件、测量在同一条时间线上对齐；
8. **运行记录与对比**：回放一次运行，对比两次运行的差异；
9. **出口**：界面、MCP（供 Agent 查询与解释）、CI 产物、标准格式导出。

### 运维可运维

1. **结构化日志**：分级、带会话与运行编号，便于关联同一次运行的所有记录；
2. **指标**：求解耗时、命令延迟、内存、并发会话数、错误率；
3. **产品改进信号**：哪些命令不被模型支持、哪些能力上限被触发、哪些错误最常出现，用于决定模型与组件的开发优先级；
4. **版本信息**：引擎、组件库、仪表模型、Bench 格式的版本与兼容性；
5. **健康检查**：引擎与各接入服务是否正常；
6. **崩溃报告与诊断包**：一键导出脱敏后的诊断包（日志、版本、环境、运行记录摘要），断网环境下由用户手动发送；
7. **问题重现**：用户同意时，凭 Bench 定义 + 运行记录 + 种子在产品团队本地精确重现问题；
8. **标准接口**：指标与日志可导出到标准可观测性工具，供私有化部署平台集成。

### 数据边界

- 用户的脚本、Bench 内容、波形、测量结果属于用户资产，默认不离开用户环境；
- 运维数据的收集方式待定（见下）。

- **遥测策略**：见 D17。

## D17 定位：内部仪表仿真工具，不做商业化产品

- **结论**：SimuBench 是公司内部的仪表仿真工具，不对外发布、不商业化。它解决两件事：内部工程师研发过程中的仪表短缺；研发自己的测试测量仪表时，在样机就绪前为上位机、驱动、校准程序与测试脚本提供虚拟仪表，并用于验证仪表内部的算法与架构（信号链级：模拟域保持解析，ADC 之后用采样流，positioning-review.md 第 8 节）。用户是内部的仪表开发与校准软件工程师（[positioning-review.md](positioning-review.md)）。
- **理由**：原结论是“第一阶段在内部使用”，把内部使用当作对外发布之前的阶段；实际需求只在内部，按对外产品准备的授权、分发、协作平台没有使用者。备选是保留对外发布的选项并继续为它做准备，代价是投入从“内部工程师的脚本原样跑通”分散出去。
- **遥测**：默认开启，日志、指标与产品改进信号发送到内部收集服务；收集地址与开关可配置。诊断包与问题重现机制不变。
- **数据边界**：用户资产（脚本、Bench 内容、波形、测量结果）与运维数据分开处理。
- **影响**：
  - 授权与计费（D6 第 6 项、scope.md 中的授权行）、对外发布、协作平台与私有化部署平台不在计划内；
  - 部署在内网：内部软件包源、内部 CI（如 GitLab CI、Jenkins）；
  - 与用户距离近，可直接访谈与观察使用过程，作为遥测之外的反馈来源。

## D18 界面：Web Bench 为主，终端控制台（TUI）为补充

- **结论**：第一个界面是 Web Bench，由本地的 `simubench serve` 提供，用浏览器打开，不需要安装桌面程序。终端控制台（`simubench tui`）作为补充，用于 SSH 远程、与脚本同屏观察、可复现的截图与演示。
- **理由**：画布编辑与审阅 Agent 搭建的 Bench、清晰的波形与频谱、仪表内部组件图都需要图形界面；引擎与界面分离（D7），选择不影响引擎。
- **TUI 的约束**（[tui-design.md](tui-design.md)）：
  - **只是服务的客户端**：经与 Web 相同的 HTTP/WebSocket 接口访问会话，不在进程内直接调用引擎；`simubench tui <bench>` 在本进程启动服务后连上，`--attach` 连接已运行的服务。另一条路（进程内直接用引擎）启动更快，但远程状态、确认与来源要再实现一遍，也无法与脚本、Web、Agent 共用会话，没有采用；
  - **只观察与操作，不做编辑**：测试台的修改仍只有画布、MCP 与编辑器三个入口（D25）；
  - **Textual，可选依赖** `simubench[tui]`，与 `simubench[mcp]` 一样不进核心依赖；
  - **操作来源“终端”**：请求带上客户端类型，运行记录与事件中与“界面”“Agent”区分；
  - **命令未被执行的原因进入事件**：错误事件给出分类（覆盖表中未实现、型号没有、定义中没有、已忽略、内置命令被排除、参数不合法），TUI、Web 与 MCP 共用；提示只转述定义作者声明的内容并写明出处（#172）。
- **详见**：architecture.md 第 8 节、tui-design.md。

## D19 实现语言：Python 起步，为 Rust 留好边界

- **结论**：引擎、接入层与服务用 Python（NumPy/SciPy）实现；计算密集的部分（信号求值、网络求解、频谱计算）放在清晰的接口之后，性能分析表明需要时再改用 Rust 实现，接口与上层不变。Web 前端用 TypeScript。
- **理由**：PyVISA 后端、pytest 插件、SDK 与 MCP 都在 Python 生态中；第一阶段在内部使用，首要目标是尽快验证产品。

## D20 同时支持 Windows 与 Linux

- **结论**：用户机器与 CI 同时包括 Windows 与 Linux，SimuBench 在两个平台上都要可用。
- **影响**：
  - **确定性**：同一平台、同一版本下逐字节一致；跨平台在验收容差内一致，不要求逐字节一致；
  - **CI**：验收测试在 Windows 与 Linux 上都运行；
  - **进程间通信**：服务进程与客户端之间使用本机 TCP，不依赖只在类 Unix 系统上可用的 Unix 套接字；
  - **路径与文件**：Bench 中的文件引用使用与平台无关的相对路径；
  - **发布**：纯 Python 包 + NumPy，两个平台使用同一份包。

## D21 Web 技术栈与接口生成

- **结论**：
  - 前端：React + shadcn/ui + React Flow（Bench 画布）；仪表屏幕中的波形、频谱、曲线在 React Flow 节点与独立面板中用 Canvas 绘制；
  - 后端：FastAPI，作为 `simubench serve` 的 HTTP 与 WebSocket 服务；
  - **接口文件自动生成**，不手写前后端之间的类型与客户端代码。
- **单一来源**：接口以 Python 中的 Pydantic 模型为唯一来源，自动生成：
  1. HTTP 接口：FastAPI 生成 OpenAPI 描述，再生成前端 TypeScript 类型与客户端；
  2. WebSocket 消息（事件、状态更新、动作）：同一批 Pydantic 模型导出 JSON Schema，再生成 TypeScript 类型；
  3. Bench 与仪表定义文件的 JSON Schema（用于校验与编辑器提示）；
  4. MCP 工具的输入输出 schema。
- **一致性检查**：生成结果提交到仓库；CI 中重新生成并比较，不一致即失败，防止前后端接口漂移。

## D22 界面按商用标准交付

- **结论**：界面直接按商用产品的质量设计与实现，不做演示版。宁可功能少，不交付半成品。
- **衡量**（D17）：SimuBench 是内部工具，“商用标准”指做工，不指功能范围；是否达标以内部工程师的可用性验证为准（任务完成率、耗时、出错点），不以自检清单为准。验证有结果之前不增加新的界面功能。
- **含义**：设计先行；建立 SimuBench 设计体系（基于 shadcn/ui 的设计令牌、浅色/深色主题、仪表视觉语言）；每个页面与组件实现完整状态；完整的画布交互（撤销/重做、自动保存与版本等）；性能预算；可访问性与中英文；组件、端到端与视觉回归测试；本地服务安全；每个里程碑做可用性验证。
- **详见**：roadmap.md“界面质量标准”。

## D23 没有专职设计师与品牌规范；Web 界面以中文为主、英文为辅，TUI 只用英文

- **结论**：
  - 团队没有专职产品设计师，也没有既定品牌规范；
  - Web Bench 以中文为主、英文为辅：中文完整，英文覆盖全部界面文本，文档以中文为主；
  - 终端控制台（TUI）只有英文（产品负责人决定，2026-11-02）：不再维护中文文本，没有 `--lang`；定义中只有中文的文本（`option_labels`）在 TUI 中改用仪表的写法（助记符），`label_en` 用作标签。与 Web 共用的词条以 `web/src/i18n/en.ts` 为准。
- **设计工作的承担方式**：
  - 信息架构、任务流程、线框图、交互说明、设计体系由开发团队（含 AI 辅助）产出，按 D24 自检；
  - **以代码为设计源头**：设计令牌与组件库（Storybook）就是设计稿，不另外维护一份会过时的视觉稿；
  - 以成熟的仪表软件与专业工具为对标，做启发式评审；
  - 可用性验证（roadmap.md）比有设计师时更重要，不能省略。
- **品牌基础**（M0 中建立）：SimuBench 文字标志、主色与功能色、中文字体（如思源黑体 / Noto Sans SC）与等宽数字字体、图标风格。
- **中文为主的要求**：术语表（[glossary.md](glossary.md)）统一用词；中文排版（行高、字重、中西文混排间距）；英文文本通常更长，布局需容纳；所有文本外置，便于切换语言。

## D24 开发期间不设评审卡点

- **结论**：进入开发后直到验证完成，产品负责人不再评审中间产物；开发按本文档的决策自主推进，不以评审作为卡点。
- **替代机制**：
  - 原计划中的设计评审与里程碑评审改为开发团队的自检：每个里程碑按 roadmap.md 的完成条件与界面质量标准逐条自查，结果记录在 [progress.md](progress.md)；
  - 遇到决策文档未覆盖的问题，按已有原则选择最合理的方案，记录为新的决策，继续推进；
  - 产品负责人在验证完成后确认验收（定标与自研仪表场景由使用它的工程师验收，D11）。
- **可用性验证不属于被取消的评审**：每个里程碑的可用性验证（roadmap.md）由内部工程师完成，不能以自检代替，也不再推迟到全部开发完成之后。
- **术语**：DUT 不翻译（glossary.md）。

## D25 测试台文件是编辑的唯一来源；切回操作时按新定义重建

- **结论**：画布编辑、MCP 编辑与文本编辑器修改的都是测试台文件本身，没有单独的“草稿”。每次编辑立即保存（乐观并发：带上读取时的文件哈希，哈希不符返回 409）。打开的会话不随编辑改变拓扑；文件内容指纹（不含布局与说明）与会话打开时不同，切回操作模式时自动按新定义重建（无“重新启动”按钮），并提示仪表设置回到初始值；搭建中的定义不合法（校验错误）则阻止切换、停留在搭建模式并定位问题（#31）。有脚本连着 SCPI 端口时，重建会断开它们：先确认，或选“稍后重建”回到正在运行的测试台，顶栏提示文件已改并可随时重建（#121）。
- **理由**：Agent 与工程师改的是同一份可读、可 diff 的文件（D9）；外部修改（Agent、编辑器、另一个窗口）通过轮询载入并提示变化摘要，不会被静默覆盖；移动节点不会触发重启提示。
- **撤销/重做**：保存完整文档快照，撤销即以当前哈希写回上一版本；外部修改载入后历史清空，避免撤销覆盖他人的修改。
- **预览**：编辑画布显示“按当前文件构建、但不运行”的测试台；无法构建的部分（未知型号、错误连线）省略并列出，其余照常显示。

## D26 MCP 服务与 Web Bench 同进程

- **结论**：`simubench mcp` 以 stdio 提供 MCP 服务，同一事件循环中启动 Web Bench；Agent 部署的会话、编辑的文件实时出现在工程师的浏览器中。stdout 只用于 MCP 协议，其余输出写 stderr。
- **安全**：危险命令需 `confirm=true`；仿真控制（故障注入、推进时钟、读取真实值）默认关闭，需 `--allow-control`；读取真实值还需测试台 `run.reveal_true_values`；所有工具共享限流。
- **由脚本生成**：静态分析 PyVISA 脚本（不执行），按“支持的命令最多”选择仪表定义，列出不支持的命令与行号；看不出接线，草稿只含仪表。

## D27 故障在会话的收发入口生效

- **结论**：通信层故障（超时、断连、乱码、延迟、忙）在 `Session.write/read` 生效，PyVISA 后端（`VI_ERROR_TMO`、`VI_ERROR_CONN_LOST`）、SCPI 网络仪表、界面与 MCP 看到同样的故障；仪表层故障（错误码、保护跳闸）与组件层故障（参数漂移、改变隐藏状态）通过错误队列、仪表状态与组件参数覆盖生效，故障结束时恢复。故障按虚拟时间触发与结束，可预设在测试台文件中，所有变化写入运行记录。乱码按种子可复现。

## D28 YAML 按 1.2 的规则读取浮点数

- **结论**：测试台与仪表定义文件中 `1.0e7`、`1e-7` 读作数字。PyYAML 默认的 YAML 1.1 规则要求指数带符号，否则读成字符串，工程师写的参数会被静默当成文本。

## D29 直接串联的 RC 是合法电路

- **结论**：示波器场景第 7 组中，参考实现在校验时拒绝两个 RC 直接串联（其信号流模型无法处理负载效应）。按 D13（物理正确优先），直接串联是合法电路，第二级是第一级的负载：SimuBench 接受并求解，fc 处增益 0.323（理想两级为 0.5），与独立的二端口网络计算一致（`acceptance/test_scope_scenario.py`）。

## D30 锁相放大器的解调是精确的

- **结论**：输入网络上的每条谱线与参考相乘后都是复指数；n 个相同一阶低通级联对复指数之和的响应有闭式解（特解加 e^(−t/T) 乘多项式的齐次解）。任何变化（信号、频率、相位、时间常数、斜率）都从该时刻的滤波器状态开始新的一段，因此建立过程在虚拟时间中精确，不做逐点采样。
- **噪声**：前端白噪声由按计数器生成的高斯序列经同样的 n 级滤波器冲激响应加权得到，并精确归一到 σ = eₙ·√ENBW；它是种子与虚拟时间的纯函数：同一时刻读两次结果相同，一个时间常数内的读数相关。
- **引擎支持**：带有时间演化状态的组件（`dynamic`）在每次信号变化时、虚拟时间前进之前由会话调用 `sync()`，记录变化发生的确切时刻。
- **任意波**：表格按线性插值播放，谱线精确（sinc²），解调也精确，因此“接近但不等于参考频率”不是模型边界（见 validation-lockin.md）。

## D31 PyVISA 中每个资源管理器是一台刚上电的测试台

- **结论**：PyVISA 按测试台路径缓存后端库对象。关闭资源管理器时会话随之关闭，之后再打开的资源管理器得到新的会话。测试之间不会继承彼此修改过的仪表状态，与真实测试中“每个测试从已知状态开始”的习惯一致。

## D32 前面板的读数与操作不经过 SCPI

- **结论**：界面显示仪表读数（锁相放大器的 X/Y/R/θ、万用表读数）使用只读的读数接口：不产生通信记录、不改变错误队列、不推进虚拟时间。
- **面板操作**（示波器的运行、停止、单次）同样不是 SCPI 命令：在仪表内部执行（定义的 `display.actions` 给出与之等价的型号命令，否则用采集组件的 `run`、`stop`、`single`），不进“通信”、不改变错误队列与脚本待读的回复、不推进虚拟时间；每次操作记为一个“面板操作”事件（来源：界面），写入运行记录，回放时重新执行。运行中的屏幕在当前虚拟时间重算画面（噪声逐帧不同），这些画面不是采集记录；停止或等待单次触发时定格在最近一次采集。脚本看到的命令、回复与虚拟时间与界面是否开着屏幕无关；“单次”是一次真正的采集，脚本随后读到的就是它（issue 32）；型号声明采集在虚拟时间中完成时（`completion: pending`，#134），脚本在它完成后读到它，完成前读到的是上一帧；面板按下的“单次”当场完成，用的是面板自己的时间。
- **远程状态**（#121）：仪表的 SCPI 端口（raw socket、HiSLIP）上有连接时，它处于远程状态，与真机的 REM 一样：界面经 HTTP 接口的改设置、SCPI 控制台与面板操作被拒绝（409，列出客户端）；只读读数、探针、时间线与故障注入不受影响。界面的“本地（LOCAL）”从脚本接管这台仪表，直到远程客户端向它发出下一条命令，两次切换都记为 `remote` 事件。会断开或扰动已连接脚本的整台操作——打开另一个测试台、关闭、重置、推进虚拟时间——须带 `force` 确认。脚本的一条消息与随后的回复读取是一次动作，界面控制台的查询不会取走脚本的回复。MCP 的工具是 Agent 的操作，不受远程状态限制；但会断开或扰动已连接脚本的整台操作——启动（替换）、关闭、推进虚拟时间——同样要带 ``force`` 确认，拒绝就是护栏本身，收在 SessionManager 与会话层，任何门面都不会漏掉（issue 624）。墙钟模式下虚拟时间本来就等于真实时间，只读接口读取的是当前真实时刻（不产生事件）。锁相放大器另外返回按当前设置“将要走的”建立曲线（不含噪声），界面与已读取的历史一起画出。

## D33 频谱仪：谱线精确，噪声按分辨单元确定

- **结论**：RF_IN 上的每条谱线按 V²/2R 经高斯 RBW 滤波器画出；接收机噪声 kT₀·F·NBW（加衰减）按“迹线点 × 分辨单元”生成，由种子、扫描序号、点与单元确定。迹线是设置、RF_IN 历史信号、种子与扫描序号的纯函数；每次扫描使用该扫描开始时 RF_IN 上的信号，因此信号源中途改变时，平均与最大保持能“记住”之前的谱线。
- **周期信号一律精确**：方波、锯齿、任意波表、PRBS 都由精确的谱线表示，不做加窗 FFT 估计（D13、D30）。模型唯一的截断是谱线数上限，截断时信号带有说明，读取它的仪表据此报告（锁相放大器 329、频谱仪 −221）。
- **模型缺陷不影响脚本**：仪表模型内部的异常转为 −300 设备错误进入错误队列并写日志，不会让客户端脚本崩溃。

## D34 分段线性器件：限值与负载按工作点精确求解

- **结论**：带限值的源（SMU）与电子负载是分段线性器件：每种模式（恒压、恒流、受最小电阻限制）都是线性元件。会话求解后，每个器件按直流工作点检查自己的模式是否成立，不成立则切换并重新求解，直到所有器件一致（最多 40 次）。四象限限值、负载向源灌电流、电子负载的拐点都由此精确得到。
- **仪表内部扫描对任意负载有效**：每个扫描点都按当时的测试台求解，因此参考实现拒绝的“非线性负载上的仪表内部扫描”在 SimuBench 中给出每点精确的工作点（D13）。逐点扫描得到相同的结果。
- **恒压模式的电流直接取自节点分析**：理想电压源的支路电流是方程组的未知量，读数不经过两个相近电压相减，七位有效数字下电阻读数为 999.9 Ω 而不是 999.8999 Ω。

## D35 测试台文件的版本历史

- **结论**：每次保存都在工作区的 `.simubench/history/<测试台路径>/` 留下一个版本，记录保存者（界面、Agent、API、外部修改、恢复）与时间。在 SimuBench 之外的修改（文本编辑器、git 检出）在下一次保存时作为“外部修改”版本补记，历史不会漏掉工程师看到过的内容。
- **合并**：同一来源在两分钟内连续只移动节点的保存合并为一个版本，拖动节点不会淹没历史。
- **恢复**：把旧版本作为新版本写回，之后的版本仍保留；只有超过 200 个版本时删除最旧的。
- **审阅**：界面按项列出差异（仪表、DUT、连线的新增、删除与修改，修改列出每个字段的新旧值），可看“这次修改了什么”或“与当前文件相比”。Agent 通过 MCP 的保存都标为 Agent，MCP 也提供 `list_bench_history`、`read_bench_version`。

## D36 运行记录可以独立回放

- **结论**：运行记录的头部携带完整的测试台与每个仪表定义的哈希，记录本身就能回放。`simubench replay <记录>` 用记录中的种子重建测试台，按记录的虚拟时刻重发每条命令、界面中的设置变化与注入的故障，并逐条比较回复；第一处不同给出记录序号、仪表、虚拟时刻、之前的命令与两边的内容，退出码 1。命令驱动、步进、墙钟三种时钟的记录都按记录的时刻回放（墙钟记录以步进方式回放）。
- **采集保存为配方**：示波器每次采集写入一条 acquisition 事件（触发时刻、采样间隔、点数、种子、每个通道数据的哈希）；二进制回复（波形数据块）在记录中只保存长度、哈希与对应的采集，不保存原始字节，回放时按哈希比较。需要原始字节时以 `--record-raw` 启动。文本回复照原样保存。
- **定义变化**：回放时仪表定义与记录中的哈希不同，报告警告，差异可能来自定义本身。
- **界面**：首页列出最近的运行记录（服务以 `--record-dir` 启动时）；运行记录页按仪表分道显示虚拟时间上的时间线与事件列表，“回放并比较”给出结果并定位到第一处不同。

## D37 虚拟探针与“为什么是这个值”

- **结论**：在运行模式中选中一个网络（或一根连线），检查器显示虚拟探针：网络上的波形、直流、有效值、峰值与主要谱线。探针不加载电路、不经过仪表、不产生事件。
- **解释即计算**：网络电压按独立源分解——每个源的电动势乘以节点分析求得的、从该源到这个网络的传递函数（幅度与相位），逐频率列出“电动势 × |H|∠φ = 贡献”。这正是引擎计算网络信号的方式，因此解释与读数严格一致，不是事后的近似说明。信号不精确时（谱线截断等），同时列出保真度说明。

## D38 运维：结构化日志、版本清单、健康检查、诊断包

- **日志**：`--log-format json` 每行一个 JSON 对象（UTC 时间、级别、来源、消息与附加字段），`--log-file` 另存文件；进程内保留最近 2000 条 info 及以上的记录，供诊断包使用。
- **版本清单**：`simubench version --full` 与 `/api/manifest`：引擎（版本与构建它的提交，D58）、Python、平台、主要依赖版本、每个仪表定义的版本与哈希、界面构建的哈希、工作区与运行记录目录。与运行记录头部的定义哈希一起，可判断两次运行的差异是否来自版本。
- **健康检查**：`simubench doctor`（退出码 1 表示有失败项）与界面“关于与诊断”：Python 版本、依赖、MCP、PyVISA 后端注册、仪表定义、界面构建、工作区中的测试台文件、端口、临时目录；每项说明如何修复。
- **指标**：`/api/metrics` 以 Prometheus 文本格式给出会话数、各会话按类型的事件计数、电路求解次数与耗时、虚拟时间。
- **保真度标注**：会话信息中每个网络附带其信号的保真度说明（谱线截断等）；画布上该网络的连线标 ≈，悬停显示原因。说明只随信号到达的网络传播。
- **诊断包**：`simubench diagnose` 与界面导出：版本清单、健康检查、最近日志、正在运行的会话（含最近的错误与故障）及其测试台文件、最近的运行记录（每份最多 5 MB）。不含访问令牌，不自动上传，由用户自行提交（D17）。

## D41 HiSLIP 接入：同步与重叠两种模式、2.0 安全连接、共用端口、按子地址区分仪表

- **结论**：除 raw socket 外，每台虚拟仪表也以 HiSLIP（IVI-6.1）暴露，NI-VISA、Keysight IO Libraries、pyvisa-py 等客户端不改脚本即可连接 `TCPIP0::127.0.0.1::hislip<i>,<端口>::INSTR`。三条设计约束：
  1. **共用一个端口，按子地址区分仪表**（默认 4880，`--hislip-port 0` 自动分配）：真实仪表各自有 IP、都用 `hislip0`；本机只有一个 IP，用 `hislip0`、`hislip1`…（编号规则与 SOCKET 端口一致）最接近真实情况，另接受 `hislip_<实例名>` 别名。
  2. **同步与重叠两种模式都服务**（IVI-6.1 3）：起始模式由 `--hislip-overlapped` 选定（默认 synchronized，`InitializeResponse` 控制位 0 宣告），设备清除时服务器提议自己的模式、接受客户端在 `DeviceClearComplete` 里的选择（6.12.1）。synchronized：查询被打断时丢弃旧响应并回 `Interrupted`/`AsyncInterrupted`。overlapped：消息只缓冲、不触发 interrupted，响应的 MessageID 由服务器自己的计数器给（从 0xffffff00 起，每条加 2），MAV 按客户端在 `AsyncStatusQuery` 里报告的已取走 ID 计算（6.14.2）。消息边界、设备清除、读 STB、锁（独占/共享；D63 起与同一仪表的 VXI-11 与 PyVISA 会话共用一份）、SRQ 按规范实现。协商版本为客户端与服务器中较低者，最高 2.0；`GetDescriptors`（2.0 起）在两个通道上应答。**重叠模式需要懂重叠模式的客户端**：规范要求客户端两种模式都支持（3.2.2），但 pyvisa-py 只实现同步模式的 MessageID 校验，对重叠起始的服务器第一次 `write` 之后的 `query` 会因 ID 对不上而丢弃响应、超时，所以默认仍是 synchronized，重叠只在命令行显式要求时才起。
  3. **安全连接能力（2.0，IVI-6.1 4、6.15、6.16）有证书与密钥才开**（`--hislip-cert`/`--hislip-key`，`--hislip-tls optional|initial|mandatory` 选加密模式）：两个通道各自在连接中途由 `AsyncStartTLS`/`StartTLS` 升级为 TLS（1.2 起），`AsyncEndTLS`/`EndTLS` 降回明文（加密强制时拒绝）；握手前先看缓冲区是否为空（busy/success/error），客户端把 ClientHello 紧跟在 StartTLS 后发出也不丢字节，所以不用 asyncio 的 `start_tls` 而用内存 BIO 自己跑 TLS 状态机（`access/hislip_tls.py`）。强制加密或要求首先加密时，除 TLS 建立类消息外任何消息都是致命错误 5；加密建立后在登录前只回应登录类消息，其余回非致命错误 5。SASL 登录：`--hislip-users`（`name:password` 行）给出时只提供 PLAIN，否则只提供 ANONYMOUS，失败按次数递增延迟；认证只在该加密连接内有效。登录只管 HiSLIP 这个端口，不是测试台的访问控制：加密可选时从不请求加密的客户端（和 1.0 客户端）免登录，raw socket 与 VXI-11 也没有登录，所以命令行只在 `--hislip-tls initial` 或 `mandatory`（每个客户端都必须先加密再登录）时接受 `--hislip-users`。仍只绑定 127.0.0.1（D38/安全自检同款约束）。
- **理由**：很多现有脚本与 LabVIEW/C# 程序用 HiSLIP 地址；raw socket 以换行结尾，二进制块中的 0x0A 只能靠解析长度，HiSLIP 用 `DataEnd` 标出消息边界，且只有它支持设备清除、读 STB 与 SRQ 这些 IEEE 488.2 语义。
- **实现位置**：`access/hislip_server.py`（服务器）；`Session.clear_output` 提取为 PyVISA 后端与 HiSLIP 服务器共用的设备清除语义；PyVISA 后端地址表加入 HiSLIP 形式（含 Bench 中配置的 HiSLIP 真实地址直接打开），TCPIP INSTR 资源的 VISA 属性（`TCPIP_IS_HISLIP`、`TCPIP_DEVICE_NAME` 等）按 PyVISA 属性表填齐。
- **不做**：SASL 的 EXTERNAL（客户端证书）、GSSAPI 等其余机制，TLS 会话恢复，厂商自定义消息，监听本机以外地址。VXI-11、GPIB、USBTMC 见 D63。NI-VISA 与 Keysight IO Libraries 的手动验证不作为合并条件，见 progress-log.md 留待进行。

## D42 内置仪表都是真实型号

- **结论**：内置仪表（随软件包发布、出现在元件库、MCP `list_catalog` 与命令行中的仪表）都是按真实型号实现的定义（如 Siglent SDS2104X Plus、Keysight 34465A）。每份定义的 `reference` 是**作者选定并提供的依据**：内置型号是厂商手册，用户自建或在研仪表可以是自己的设计规格、接口契约。命令行为以该依据为准；测量值仍来自电路求解（D13）。规则见 [real-models.md](real-models.md)。

- **依据由作者提供和管理**：`reference` 的 title / document / version / firmware 由定义作者填写，SimuBench 只保存和展示它。带 `reference` 的定义——不论内置还是工作区的——适用同一套规则：未实现的命令必须报错、不允许 `unknown_commands: ignore`、覆盖表与依据一致并与定义、用例互相检查。用户自己造成什么样的仪表由用户控制（[instrument-authoring.md](instrument-authoring.md) 第 0 节）。
- **`sb-*` 只用于开发验证，不发布**：SimuBench 自造的 `sb-*` 定义放在仓库的 `validation/instruments/`，不进 wheel；测试、验收与开发时通过定义搜索路径加载（工作区的 `instruments/` 目录，或环境变量 `SIMUBENCH_DEFINITIONS`）。用到它们的测试台在 `validation/benches/` 与 `acceptance/benches/`，`examples/` 只放真实型号的测试台。CI 检查 wheel 与 `examples/` 中没有 `sb-*`（issue 35）。
- **理由**：自造型号没有手册可依，脚本在它上面通过不能说明在真机上也通过（D4、D5）；它们的价值是在没有对应真实型号时验证引擎与组件。只被 `sb-*` 使用的组件（锁相、频谱仪、SMU、电子负载、射频源、PRBS）保留在引擎中，供验证与以后的真实型号使用。
- **代价**：在有对应真实型号之前，发布版中没有锁相放大器、频谱仪、SMU、电子负载、射频信号源、万用表等类别。
- **三种实现程度**：依据中的每条命令属于“实现”“接受”（解析并保存，不影响仿真）或“未实现”之一。未实现的命令回复 `-113,"…;not implemented in this definition"`，说明的是“这个定义尚未实现”，不把责任归给 SimuBench，也不静默接受，避免脚本在虚拟环境通过、在真机失败。
- **按接口契约编写的定义**：有既定主机程序、按接口契约实现的仪表（如低频校准工作台，[lowfreq-cal.md](lowfreq-cal.md)）可以带 `reference`（指向契约或设计规格），此时与真实型号同一套规则；也可以不带 `reference`，此时契约要求未知命令不报错时允许设 `unknown_commands: ignore`：未知命令头不进错误队列、不回复，事件历史记为 `ignored`。带 `reference` 的定义不允许 `ignore`（定义校验拒绝）。这类定义不进内置仪表库，放在工作区的 `instruments/`（可以在 `examples/` 下的工作区中）。主机按 `*IDN?` 校验型号时，型号串由测试台实例的 `idn` 给出，不写死在定义里。
- **可验证**：每个型号有覆盖表（按作者所依据的文件列出全部命令及其程度）和用例（命令与预期返回，注明依据的章节或条目），CI 检查两者与定义一致。工作区中的自建定义同样可以用 `simubench coverage`、`simubench cases` 与 MCP `run_cases` 检查。
- **首批型号**：Keysight 34465A 与 Fluke 5522A（定标演示）；此后按 D45（Siglent SDS2104X Plus、SDG2042X 替代了原计划的 33500B 与 InfiniiVision 3000T）与 #181 的类别铺开推进，Keithley 2450（#12）在第二波。
- **商标**：`*IDN?` 返回真实厂商与型号，这是脚本不改即可运行（D5）的前提，发布版也如此。只以名称指明所模拟的型号：不使用厂商标志与商业外观，定义与文档不大段摘抄手册文字（手册本身存放在 `manuals/` 供开发查阅，不随发布版分发，#412），文档声明 SimuBench 与各厂商无关联、商标归各自所有者（real-models.md 第 7 节）。

## D43 访问令牌改为可选，默认关闭

- **结论**：`simubench serve` 与 `simubench mcp` 默认不要求访问令牌；`--require-token`（随机生成）或 `--token 值` 开启。只监听本机、Host/Origin 校验、工作区边界等其他防护不变。
- **理由**：令牌是同机威胁模型下的一次性访问凭证，不是登录或识别用户的手段；在工程师自己的电脑上，浏览器页面已由 Host/Origin 校验挡住，令牌带来的主要是“新标签页或重开浏览器后令牌无效”的使用摩擦。
- **代价**：默认时不再防护本机其他用户（他们可以绕过浏览器直接访问 127.0.0.1）。多人共用的电脑上应开启令牌；见 [security.md](security.md)。

## D44 画布在运行时反映信号与活动

- **结论**：运行中的画布展示测试台此刻的状态，而不是静态的拓扑图：
  - 连线按网络电平着色：有信号时以通道色从源向负载流动，0 V 时为灰色；悬停显示网络的直流、有效值与峰值；
  - 示波器节点的通道行带波形缩略图（两个周期）；
  - 仪表收到 SCPI 写入时节点短暂闪烁；
  - 顶栏把“运行中”细分为“等待命令”“执行命令”（命令驱动时钟、步进时钟）与“时钟走动”（墙钟）、“时钟走动 ×N”（按倍率时钟，#683），悬停说明原因与操作。
- **数据**：一个只读接口 `GET /api/sessions/{sid}/levels` 一次返回所有网络的电平与缩略图（与虚拟探针 D37 同一求解），界面在状态变化时重新读取；编辑模式下不显示（预览的测试台可能与运行中的不同）。
- **理由**：命令驱动时钟下，没有命令时虚拟时间不动，原来的画布在“运行中”时没有任何变化，用户分不清是在运行、在等待还是坏了，也看不出信号有没有到达。
- **约束**：动效遵循 `prefers-reduced-motion`；状态同时用文字与颜色表达（ui-design.md 4.2）。
- **时钟模式补充（#683）**：新增 `scaled`（`run.clock: scaled` 加 `run.time_scale`，命令行 `--clock scaled --time-scale N`，API 启动参数 `time_scale`，`POST …/clock/scale` 在运行中改倍率）。虚拟时间 = 真实时间 × 倍率，倍率变化不回退已走过的时间。它与墙钟同属非确定性模式（D47）：截图与测试仍用命令 / 步进时钟，记录回放按步进时钟，`a` 被拒绝。顶栏显示“时钟走动 ×N”。

## D45 真实型号：示波器与信号源改用 Siglent

- **结论**：示波器与信号源的首个真实型号改为 Siglent SDS2104X Plus 与 Siglent SDG2042X，替代 D42 中计划的 Keysight InfiniiVision 3000T 与 33500B（产品负责人同意）。Keysight 34465A、Fluke 5522A、Keithley 2450 不变。
- **理由**：D42 要求逐条以编程手册为准，并在 `reference` 中写明版本。Siglent 的 *SDS Series Programming Guide*（EN11F）、*SDG Series Programming Guide*（PG02_E05C）与两份数据手册可从官方站点直接下载；Keysight 两份手册无法从公开渠道直接获取。D4 场景中的 T3DSO2000 同属 Siglent 平台。
- **框架补充**：`builtins` 限定一个型号回答哪些内置命令（SDS 手册只写了 `*IDN`、`*OPC`、`*RST`，没有错误队列，其余一律“未建模”）；返回格式 `enum: as_defined` 按定义原样返回枚举（Siglent 回复 `RISing`、`FMDepth`）；`display.actions.single` 指定面板“单次”在仪表内部执行的命令（SDS 没有 `:SINGle`，用 `:TRIGger:MODE SINGle`；不经过 SCPI，见 D32）；手册用例的 `binary` 步骤按块读取二进制回复。
- **手册没有给出的值**：`*RST` 后的多数设置、存储深度的默认值等，手册没有写；这些值作为 SimuBench 的默认值写入覆盖表的说明，而不是当作手册内容。
- **示波器的开发验证基准改为 Keysight DSO-X 2024A**（#151）：SDS 的手册不给 `*RST` 值、回复格式与多数取值范围，示波器模块的每项能力都要另找依据。InfiniiVision 2000 X-Series *Programmer's Guide*（02.66.0000）给出每条命令的回复格式、`*RST` 示例回复与范围，数据手册 5990-6618EN 给出增益、偏置、时基与输入的指标；两份文件可从公开镜像稳定取得。示波器模块的新能力以 DSO-X 2024A 为验收型号；SDS2104X Plus 保留为第一个产品型号与 Siglent 平台的样本，不再作为新能力的依据。信号源仍是 SDG2042X。

## D46 示波器的噪声与量化（真实型号）

- **结论**：真实型号示波器（首个为 SDS2104X Plus）的每条记录包含输入噪声、触发抖动和 ADC 量化：
  - **输入噪声**：白噪声，均方根值由数据手册的噪声底推得。SDS2000X Plus 只给出“500 MHz 带宽时 80 µV rms”，按白噪声随 √带宽变化，100 MHz 型号取 80 µV × √(100/500) ≈ 35.8 µV（输入端），显示电压中乘以探头衰减比。这是推导值，写在定义的 `specs` 中。
  - **触发抖动**：数据手册的 10 ps rms，作为每次采集的记录时间偏移。
  - **量化**：记录按当前分辨率（8 位每格 30 个码，10 位每格 120 个码）取整后再保存，测量和波形读取看到的都是码。
  - **平均**：`:ACQuire:TYPE AVERage,N` 的噪声为 1/√N，并消耗 N 次采集的时间。
- **确定性**：噪声是种子、仪表、通道与绝对采样序号的纯函数（`engine/noise.py`）：每次采集不同，相同的会话重放逐位一致（architecture.md 2.5）。
- **随档位变化的噪声、ERES、PEAK**（修改，instrument-authoring.md 第 8 节 G4）：原定数据手册没给数值就不建模，结果是大档位上噪声远小于 1 LSB、平均与高分辨率提高不了分辨率，脚本在虚拟环境中得出错误的数值。改为：噪声按档位表给出（V rms 或格 rms），平均、峰值检测与高分辨率在码值上处理；数据手册没给的档位值可以由写型号的人估计，必须在 `specs` 与覆盖表中标为“估计”并写明依据。另一条路是继续不建模，因为错误结论比估计值的误差更有害而不采用。
- **通则（#746 修改）**：不只示波器，各类仪表的噪声取数据手册值；手册没给的，用写型号的人**标明为估计**的值（`specs.noise_*`，注释写“估计”与依据），不再因为手册没给就不建模（SDG2042X 只给了失真、杂散上限与 150 ps 周期抖动，没有输出噪声底，输出暂仍按无噪声处理，加了真实需求再用杂散谱线表示）。`sb-*` 仪表不加噪声（D42 不为虚构型号编造指标）。
- **读数噪声的位置（#746；#750 扩展）**：万用表、源表等的读数噪声在**仪表内部、电路求解之后**的读数一步加（校准之后、量化之前，过载判断看加噪后的值），用组件的 `noise` 参数，默认无。有量程概念的读数（万用表、源表、数据采集的内部 DMM——DAQ 的测量链就是 `dmm_conditioning`+`dmm_adc`，本就带量程）用 `{ppm_of_range, ref_time_s, table}`（ppm 占当前量程）；没有量程概念的读数——电源回读、电子负载、校准源回读——用绝对值 `{rms: <数 或 读数量→rms 的映射>}`（与 `ppm_of_range`/`table` 互斥），噪声加在回读值上而非电路信号里。`Signal`（电路里的谱线）不带随机的白噪声项。脚本读数以该组件的读数序号为键（单次读数与触发突发的样本统一编号，每个样本一次独立抽样，#749；不取触发模型的样本序号——它每次 INITiate 从 0 重计，用作键会让相邻两次突发的噪声逐位相同），Web 面板读数用自己的帧计数，二者互不影响（D32）。频率计数器的抖动（时间戳与事件时间误差）#750 起改走同一 `noise_sample`：键从 `seed, 仪表, 组件, 流, σ` 收敛为 `seed, 组件, 流, 时刻`，统计特征与种子确定性不变，同一种子下的具体数值变了（现有断言都是容差与复现，不受影响；旧录制回放的是记录值，同样不受影响）。`mux_card` 不带 `noise`（只有继电器与模拟总线，无测量读数）；校准源回读噪声只作用于 Web 面板读数（校准源无脚本侧电压回读命令，#796）。
- **一并修正**：周期测量在量化记录上把 -0.0 当作负值导致 NaN；PyVISA 后端逐字节读取，大波形块的读取时间与长度的平方成正比；运行记录把无穷大（高阻负载设定）写成 null，重放时测试台无法加载。均已修正并加测试。


## D47 命令时钟的空闲时间：`run.idle` 三档，pytest 默认 `sleep`

- **结论**：Bench 的 `run` 新增 `idle`，表示命令之间空闲的真实时间怎么计入虚拟时间（只对命令驱动时钟有意义；墙钟、步进时钟不读它）：
  - `wall`（默认，即原有行为）：空闲的真实时间计入虚拟时间。交互使用、界面与 `simubench serve` 保持如此，脚本里的等待能“等”出建立时间；
  - `sleep`：空闲不计入；进程内把 `time.sleep(t)` 拦截为虚拟时间恰好推进 `t`、不真的等待。pytest 插件默认此档（环境变量 `SIMUBENCH_IDLE` 与标记参数 `idle=` 可覆盖，与 `SIMUBENCH_CLOCK` 一致；issue 640 后这三个设置也可写在资源串查询参数里，资源串优先、环境变量兜底，见 architecture.md 7.3）；
  - `off`：空闲完全不推进虚拟时间，只有命令与显式 `advance` 推进。
- **理由**：`wall` 空闲推进让慢机器把命令间的调度延迟算进虚拟时间，同一个测试在不同机器上读到不同的数（issue 4 的 Windows 1508 Ω）。测试要的是可复现：`sleep` 档下结果只由命令、`time.sleep` 和显式推进决定，脚本里的 `sleep(5)` 也不再真的等 5 秒，CI 更快。
- **`sleep` 只在本进程有效**：拦截 `time.sleep` 是进程级补丁，在测试台打开期间生效、最后一个关闭后恢复原函数；进程内同时打开多个 `sleep` 档测试台时，一次被拦截的 `sleep` 推进其中每一个。只拦截 `time.sleep`：`asyncio.sleep`、线程等待与外部进程（SOCKET、HiSLIP 客户端）的等待都不拦截，因此 `simubench serve` 把配置为 `sleep` 的测试台按 `off` 处理。
- **记录与回放**：记录头部写入 `idle`；回放按记录中的设置执行，但 `sleep` 按 `off` 处理（回放的时间由记录驱动，重放环境中不应有补丁改变行为）。
- **用例运行器**：`simubench cases`、MCP `run_cases` 与测试中的用例都在 `idle: off` 的测试台上运行（不论测试台文件的设置）：用例的结果只由它的命令决定。测试台文件不写 `idle` 时为 `wall`，慢的 CI 机器上空闲时间推进虚拟时间，带噪声的读数随之变化（main 上 Windows 的 SDS 校准契约用例读到 -10.4 V）。
- **代价**：同一个测试台在 `sleep` 档下，靠“命令间空等”建立的时序不再出现——测试需要建立时间时应写 `time.sleep(t)`（会精确推进）或显式 `advance`。依赖旧行为的测试显式标注 `idle="wall"`。

## D48 幅度的多单位：范围按 Vpp 检查，切单位换算数值

- **结论**：信号源的幅度状态仍以当前单位存值；范围由 `amplitude_level` 的 `vpp_min` / `vpp_max`（负载设定下的 Vpp）检查，任一单位写入先换算到 Vpp 再比较，越界报 -222；改波形或负载设定导致越界报 -221 并拒绝。切换单位时把数值换算到新单位，物理输出不变（Rigol / Keysight 的 `VOLT:UNIT` 行为）。
- **理由**：真机只有一个物理上限（输出级在负载设定下的 Vpp），Vrms 与 dBm 的范围由它随波形和负载推出，不是独立约束；按单位各写一对静态范围，换波形或负载后就错了。SDG 的 `AMP` / `AMPVRMS` / `AMPDBM` 独立关键字与单位开关都能落在这一语义上。
- **影响**：模板 `signal_source` 的 `amplitude.min/max` 改为 Vpp 口径；含 dBm 时最小幅度必须大于 0；多单位的幅度状态不再有静态范围。

## D49 测试分三层：单元 ≤100ms，启动级与 e2e 复用环境、在 main 上跑

- **结论**：测试按启动成本分三层，预算与运行时机如下；`scripts/check_test_rules.py` 与 conftest 的时长守卫强制。
  1. **单元（默认层，快速门禁）**：纯逻辑与接口级——不 import Textual、不起服务器、无网络，依赖全部 mock 或注入（如 `tests/tui_mock.py`）。单个用例 `call` 阶段 **≤100ms**（conftest 对带 `unit` 标记的用例强制，超时即失败：拆分或上移一层；CI 的共享 runner 上负载尖刺会落进本地毫秒级的 call 阶段，`CI=true` 时预算 ×3——仍拦得住 5ms→300ms 级别的真实回归，#482）。一个用例只验证一个行为（限本层：纯逻辑便宜，拆开不亏，失败命名精确）。
  2. **启动级（`tui_boot` 标记，main 合并后 CI 跑）**：需要启动 Textual 应用或真实服务器的测试（屏幕、按键、快照）。单模块 ≤90s。
  3. **e2e（`*e2e*.py`，main 合并后 CI 跑）**：完整验收场景，单个用例 ≤30s。
  - **环境必须复用**（第 2、3 层）：服务器类夹具一律 **module（或 session）作用域**，一个模块最多起一个服务器；用例之间通过各自开自己的会话/重建夹具数据隔离，而不是各自起环境。函数作用域的服务器夹具由检查脚本拒绝。
  - **e2e 断言不能太少**：每个 e2e 用例 **≥5 条断言**——昂贵的环境要让一次启动换来足够的验证；只差一两条断言的用例合并进相邻场景，而不是单独起一遍环境（脚本以 AST 数 `assert` 强制）。
  - **判断不用正则**（#926）：测试判断一个值，就把它解析回数值，与期望值 ± 有依据的容差比较（容差取型号的噪声 σ 或精度指标，从定义读出，不在测试里抄一份）；判断文字用子串或相等。不按"显示成什么样"的正则去匹配——小数位数、工程前缀随量级变化，正则会漏放错误量级（`500 mV` 被当成近 0 V）或误拦正确读数（#924）。`tests/` 与 `acceptance/` 不 import `re`、不给 `pytest.raises`/`warns` 传 `match=`（`helpers.raises_with` 按子串查消息，`helpers.Near`/`reading_of` 解析屏幕读数），Web 的测试文件不写正则字面量（ESLint `no-restricted-syntax`，`e2e/judge.ts` 提供对应的解析与容差判断）；源码扫描类守卫读语法树（`ast`），不按行匹配。型号与契约用例（`cases.yaml`）同理：步骤的预期写含义——`expect_prefix`（错误码与消息开头）、`expect_value(s)` + `tolerance`（可逐值）、`expect_fields`（逐字段：值 ± 容差、范围、单位、写法、取值之一……）、`expect_format`（手册规定的写法：命名格式或 `±d.ddddddE±dd` 这样的图样）、`expect_block`（IEEE 488.2 块）；`expect_match`（正则）取消，载入时报错并指出替代写法（`library/expectations.py`，[real-models.md](real-models.md) 第 4 节）。备选是保留正则、只把带噪读数改成数值容差，因为正则仍会按显示位数判断数值、放过错误量级而不采用。三项检查强制：`scripts/check_test_rules.py`、`web` 的 lint 与用例文件的模型校验。
  - **引擎层允许流程式用例**（#704）：`tests/test_*.py` 里要开真实 bench 的模型/引擎测试，一个用例可以沿一条手册或操作流程走多步、逐条断言（断言消息带步骤名，失败定位靠它）——bench 一次启动换一条完整流程的验证；同一流程的相邻小用例合并进这条流程，而不是各自重开一遍 bench。合并只动结构，断言一条不删。
- **运行时机**与 AGENTS.md 的现有分层一致：PR 只跑快速检查（`-m "not tui_boot and not load_sensitive"`），Windows、wheel、e2e、视觉、`tui_boot` 与墙钟预算（`load_sensitive`，如 test_performance.py——忙碌机器上必红，只在 main 的空闲 runner 上有效）在 main 合并后跑。
- **理由**：等待测试是开发中最贵的空闲。此前 TUI 测试每个用例起真实服务器 + Textual 应用（约 20s/个），单元与 e2e 混在一层，本地迭代与 CI 都以分钟计。启动成本是测试本身的属性，按它分层并把慢的移出快速门禁，两层各自变快；e2e 的成本在环境而不在断言，所以断言要密、环境要省。引擎/模型层的 bench 同理（#704：38 个测试一个 fixture 逐测重开），断言密度换启动次数，新型号的边际用例数也随之下降。
- **迁移**：既有引擎/验收用例不受此预算约束（另行逐步迁移）；新增用例从第一天起按本规则。

- **结论**：内置型号的内部组件及其连线对应该仪表真实框图的主要功能块；组件命名与参数用仪表工程师认知中的真实功能块（NPLC、CV/CC 交叉、中频带宽、扫描表），不按软件抽象。本条分两部分，适用范围不同：

- **执行**：类别铺开（#181）的每个拆分 issue 按 component-map.md 的框图与求解层级落地——**拆分前先定每块的求解层级**（进电路求解还是设置/数据层），先录金标准（#94 方法），行为不变。

## D51 通道号域由定义声明：SCPI 用仪表的号，内部用序号

- **结论**：定义用 `channels.numbering` 声明仪表在 SCPI 上使用的通道号：按通道顺序列出号码块（`{first: 101, count: 20}`），第 k 块从内部序号 `sum(前块 count)+1` 起，覆盖 `first .. first+count-1`；不写时号码就是 `1..count`。SCPI 面向的通道号——`channel_list` 参数的列表与 `default`、命令头的 `<n>` 后缀、`int_list` 状态（`ROUT:SCAN`）——一律按声明的号码读写；状态路径 `ch<n>.*`、组件名、`channels.overrides`、连线与端口的 `{n}` 保持 1..count 的序号。范围按 34970A 手册处理：首尾必须是已声明的号，中间未声明的号跳过（跨槽位的 `(@101:205)`）；显式写出的未声明号报 -114。
- **理由**：34970A 的通道号是「槽位 + 通道」的三位号（101–320），E36312A 等是个位数；引擎不能把 101 当作第 101 个通道。备选是让定义在命令里写 1..60 的内部序号（与手册和真实脚本对不上），或让 34970A 不走展开（手册的测量命令几乎全是 `(@…)` 列表，丢掉的正是 DAQ 的核心路径），都不采用。
- **影响**：定义格式新增可选的 `channels.numbering`（`schemas/instrument.schema.json` 随生成）；SCPI 命令里的通道号与定义/测试台里的通道序号从此可以不同。34970A（#199）的扫描表与 `MEAS:VOLT? (@101:110)` 这类脚本可直接使用。界面仍按序号显示通道；按槽位显示号码留给该型号的屏幕工作。

## D52 恒功率负载（CP）用 D34 的模式迭代求解，不扩展电路求解器

- **结论**：CP 模式的 I = P/V 作为分段线性器件（D34）的一步：模式环在每一轮重解时用当前输入电压算出目标电流（受最小电阻拐点、最大电流与功率包络限制），盖章后再解，电流自洽（相对 1e-9）即停。CV 用 `loop_source` 把输入调在设定电压（与 SMU 的限值环同一求解元素）；源电压低于设定值时负载开路——负载不能向电路灌电流。
- **理由**：CP 是负载类别的一等模式（DL3000 的 `FUNCtion` 四模式之一），拒绝会让型号 issue 的命令表残缺；D34 已把「模式与工作点一致」作为求解终止条件，定点迭代在常见源–负载电路上收敛（有串联电阻时等价于二次方程，初值取开路电压，收敛到高压根）。备选是拒绝 CP 或给电路求解器加非线性牛顿迭代：前者丢功能，后者改动所有器件共用的求解器，不在首波。
- **影响**：CP 可能有多个工作点，以迭代到达的那个为准；无解或振荡时按 `MAX_MODE_ITERATIONS` 停止，不报错，落在确定的工作点：用最后一轮选定的模式再解一次电路并保留它，不再改模式，所以 V、I 满足电路、P = V·I，重复查询回同一读数，直到设置或电路变化（#258）。未收敛对用户可见：首次未收敛时运行记录写一条 `solver` 事件（reason `unsettled`），负载面板的 `regulating` 为假，SCPI 脚本读 `STATus:QUEStionable:CONDition?` 的 UNR 位（`sb-el-1` 位 10；输入开启却未保持设定值时置位，恢复后清零，#343）。`sb-el-1` 的 10 V / 1 Ω / 20 W 用例锁住高压根（7.236 V / 2.764 A）。Von 在阈值附近没有滞回，DC 模型可能模式抖动，记入缺口清单。

## D53 真机接受、模型未实现的参数词：定义声明 `not_modeled`，报 -224 并标为未建模

- **结论**：数值参数的 INFinity/NINFinity 与 INF/NINF 同义（引擎解析为 ±∞），同一个词的长短形式得到同一个错误码。真机接受但模型没有实现的词，由定义在设置或参数上声明 `not_modeled: {INFinity: <原因>}`（SCPI 大小写，长短形式都匹配）；写这个词报 -224，错误事件标为未建模（reason `not_modeled`）并带定义给的原因，而不是被当作数值按范围拒绝（-222）或类型错误（-104）（#360）。
- **理由**：脚本作者需要分清「仪表不接受」与「仿真没做」：前者是脚本的错，后者是模型的边界。备选一是只让引擎把长形式也解析成 ∞（短/长同码，但都是 -222「超出范围」，与真机接受这个词的事实相反）；备选二是引擎对数值参数上的未注册词一律报某个码（各型号无法说明原因，也会把真正的错字与模型边界混在一起）；把未建模的词映射到合法值（INFinity→MAX）会让仿真结果与真机不同。三者都不如由定义逐词声明。
- **影响**：引擎的数值关键字集合加入 INFINITY、NINFINITY——没有声明 `not_modeled` 的有界设置上，INFinity 从 -104 变为与 INF 相同的 -222。34970A `TRIGger:COUNt` 与 34465A `TRIGger:COUNt` 声明 INFinity 未建模，两种形式都回 -224；覆盖表同步。`not_modeled` 只拒绝，不接受：接受一个词仍用 `special`（给数值）或参数的 `keywords`（代写设置）。

## D54 组件应答的数值按定义格式写：`format.readings` 由定义选择

- **结论**：组件写数值应答用 `Component.reply_number(value, digits)`，交出数值而不是字符串；定义的 `format.readings` 为 `format` 时按定义的应答格式写（与设置查询同一格式），默认 `component` 按组件自己的位数写（#366）。N9320B（16 位、3 位指数）与 53220A（15 位有效数字）采用 `format`。
- **理由**：真机手册的样例回复常是一种格式，驱动按字符串比对；组件写死位数会与定义声明的格式脱节。备选一是把位数做成每个组件的参数（每个组件、每个定义各填一次，易漏）；备选二是只在覆盖表记录差异（每处手写，易漂移）；备选三是对组件应答的字符串再格式化（精度已在组件里丢掉，补出的位数是假的）。由组件交出数值、定义选格式，位数只在一处声明。默认保持组件位数，是因为现有型号（SR830 的 `nr2` 3 位等）的设置格式并不适用于读数。
- **影响**：已转为 `reply_number` 的组件：频谱（标记、迹线、带宽、扫描时间等）、计数器、锁相、曲线缓冲、负载与电源回读、射频列表、校准存储、SMU 的读数与电阻。位数已是定义参数的组件（`dmm_adc.digits`、`trigger_model.digits`、`waveform_transfer.digits`）与示波器前导不变。新组件写数值应答一律用 `reply_number`。

## D55 被动视图：外部读运行中的会话一律经 `Session.view()`

- **结论**：对外读运行中测试台的一致视图只有一个入口：会话的 `view()`。它与动作互斥（同一把会话锁）但不是动作：不推进虚拟时间（D47 的空闲只属于动作）、不发事件、不进通信记录（D32）。`view()` 内跟随墙钟；到期的等待操作由调用点显式要求结算（`settle`）——屏幕类读点结算，画布与探针不结算。引擎之外不直接拿会话 `_lock`、不直接调 `follow_wall`/`settle_pending`；故障的列出、注入与清除由 FaultManager 自持会话锁。
- **理由**：锁、墙钟跟随、结算的协议曾在 manager/app/MCP 的 16 个调用点各自手写，漏一行就读到撕裂或陈旧的数据——MCP 的真实值读取就漏过 `follow_wall`（wall 时钟下读到旧时刻）。该协议在任何接口上都测不到，因为它只存在于调用方代码里；收进 `view()` 后成为会话接口上可直接测试的行为。备选一是具名快照方法（每种读一个方法，协议全藏）——DTO 组装需要的中间量得再从快照对象取，会长出平行的快照对象层；备选二是维持调用方仪式——协议继续漂移。均不采用。
- **影响**：WS 事件流的「快照+订阅」也在 `view()` 内组合（单一调用方，不加 Session 方法）；`read_true_values` 的陈旧读由构造消除。测试面：墙钟跟随、被动读不推进命令时钟、按调用点结算、动作内嵌套视图可重入（`tests/test_passive_view.py`）。术语见 glossary「被动视图 / passive view」。

## D56 运行时写隐藏状态：`Session.set_parameter` 是唯一产品入口，覆盖写收口 `engine/deviation.py`

- **结论**：运行中写一个隐藏参数只有 `Session.set_parameter(owner, component, parameter, value)` 一条路（动作：持锁校验 → 写覆盖 → 一条 `hidden` 事件 → invalidate；不进通信记录，D32）。所有对 `comp.overrides` 的运行时写——会话的 hidden 装配、个体偏差抽取、故障的注入/漂移/恢复、`set_parameter`——都经 `engine/deviation.py` 的原语：`set_override`（校验+写+invalidate，唯一写点；构造期传 `invalidate=False`）、`clear_override`（撤销）、`draw_overrides`（hidden 占住的跳过 → 抽取 → 记录）；`ch<n>.` 键命名规则只在 `deviation_keys` 一处（#462）。
- **理由**：「hidden 压过抽取、压过 `$state` 绑定」这条不变式曾分居四处（session 装配跳过、instrument 抽取跳过、component 读序、fault 恢复），抽取流与键规则也各写一遍，任何一处改动都可能静默破坏优先级或同种子的可复现性。收口后不变式成为模块上可直接测试的行为。备选一是只加注释与交叉测试（写点继续分居）；备选二是给 Component 加可变参数对象（把覆盖从 dict 换成受控类型，改动面大而收益相同）。均不采用。故障保留自己的事件节奏（每拍漂移不发事件），只复用原语。
- **影响**：`set_parameter` 是 D39 定标系数写入的地基；此后任何「运行时改隐藏状态」的需求都走它，不再新开私有锁仪式或直写 `overrides`。测试里 `comp.overrides[` 直写清零（读取型交叉核对保留），优先级不变式有直接单元测试（`tests/test_deviation_protocol.py`）；同种子抽取值由既有 golden 测试守护，抽取流未变。库组件为自身机制写的内部覆盖（如 SMU 触发模型驱动其子组件）不在此协议内。写入值按参数 `defaults` 的声明类型校验（#495）：数值须有限、数值/字符串参数接受逐格偏差表（叶子递归校验）、`defaults` 为 `None` 的参数不约束、`$state` 绑定参数同按其 `defaults` 类型；故障 `hidden` 注入共用该校验（`_check` 时即拒绝，坏值不到启动才暴露），漂移值由引擎计算不经此路。

## D57 引擎定义 pydantic 契约模型：接口对象与它的数学同居

## D58 版本号：由 git 提交历史算出；变更记录按打包，只收产品变更

- **结论**：版本号不写在源码里，也不打 tag：构建时由 `scripts/version.py` 从 `main` 的第一父提交历史算出 `YYYY.M.D.N`——日期是最新提交的提交日期（UTC+8），N 是当天第几个提交；同一段历史永远得到同一个版本，同一天再来一个提交版本就更大（`pip` 能升级）。GitHub 与内部都不创建、不推送任何 tag：内部构建只能 fetch，不需要写回。hatchling 经 `[tool.hatch.version] source = "code"` 调用它；构建它的提交写进 `_version.py`（`hatch_build.py`），由版本清单（D38）给出。没有 `.git` 时（GitHub zip、`git archive`）日期取自 `.git_archival.txt`、N 为 0；sdist 沿用其中的 `_version.py`。需要完整历史：浅克隆数不出当天的提交数，`version.py` 在 stderr 提示并给 N 为 0（与 zip 导出一致，比任何真实版本都小，不静默给出看似合法的小版本）；`build-wheel.sh` 这条发布路径直接拒绝浅克隆（#828）。开发用的可编辑安装与 CI 的浅检出不受影响，只是版本末位是 0。

- **理由**：代码在外部开发，wheel 在公司内部构建；写死的 `0.1.0` 让每次构建同名，`pip` 不升级、内部源拒绝重复上传。版本与变更记录都由外部历史自动得出，内部只 fetch 与构建，不需要手工步骤，也不需要把内部信息传回外部。「版本对应唯一提交」没有人需要；曾经每个 `main` 提交一个 tag 的做法让 GitHub 上 tag 成堆、改为现算。备选一语义版本（`0.x.y`）手工升级：要有人判断并记得改。备选二按构建日期：同一份源码不同天构建版本不同，且同一天多次构建无法递增。备选三按提交标题前缀筛选变更记录：前缀写法不统一（`CI`、`docs`、`测试`、型号名……），会漏进噪声。备选四变更记录发在 GitHub Release：内部看不到。备选五内部构建时打 tag：内部只能 fetch，tag 推不回去，全新克隆里也不留存；「上一次发布」改由发布人传入（内部包源里有）。备选六软件内升级提示：用户经内部包源取包，发布说明走内部群与网站，不做。均不采用。
- **代价**：版本号不表达兼容性；不兼容的文件格式靠 `schema` 版本（D40）明确报错。日期版本比任何 `0.x` 都大，以后改回语义版本只能从更大的主版本开始。变更记录按包分节，靠本机的 `dist/BUILT_VERSION` 区分各包；发布说明依赖发布人告知上一个已发布版本。

## D59 定义复用分两层：类别默认块与 extends（单亲、整列表替换、禁止环）

- **结论**：内置库为每个类别（`class`）保存默认块（`library/class_defaults.py`，目前是各类别通用 errors 表），loader 在 `model_validate` 前把所属类别的默认块深合并到定义数据之下：定义数据逐键胜出、`errors` 按 code 胜出；类别表只收「该类全部内置文件逐字一致」的条目，措辞不同或器件特有的码留在型号文件里。定义可声明 `extends: <内置型号 id>`（#596）：loader 先解析父定义（父定义自身的 extends 照此递归，单亲、禁止环），再把子定义深合并上去；dict 递归合并、列表整体替换；合并次序 类别默认 → 父 → 子，类别默认按子定义的 `class` 取表、对一切带 `reference` 的定义生效（不按文件位置；`sb-*` 验证仪器与无 `reference` 的定义不拿表——表条目会整体替换引擎「标准文本；细节」的回包，sb-* 的金测依赖后者）——extends 跨出内置库时，带 reference 的子定义靠这一点拿到父定义文件里已上收进类别表的条目。
- **理由**：内置定义的 errors 有 ~480 条跨文件重复（通用 SCPI 块逐字重抄），一次行为改动多文件锁步（PR #582 同触 4 个文件）。备选一：每型号 partial 文件/模板展开——D3 的 template 是来源记录而非维护方式，partial 需要新的文件种类；备选二：commands 按命令头逐条合并——部分更新一条命令的参数易错，整列表替换可预期、可直接单测；备选三：子定义以 null 表示「删除继承键」——keysight-b2912b（双通道，设置在 `channel_state`）继承 keysight-b2901a（单通道，仪器级 `state`）需要它，否则 23 条仪器级状态与仪器级端口泄进双通道型号；#644 采用：`deep_merge` 保留 null 标记，全部层合并完才一次 `drop_deleted`（下层、类别默认带不回来），b2912b 改写为 extends，daq970a 的 22 条 34970A 器件码与 53230a 的 53220A `specs` 行同法清除；同时修正多级链的合并次序（近亲在祖先之上）；备选四：类别默认只作用于库内文件——父定义文件的通用错误行已上收进类别表，跨库 extends 的子定义会丢表。均不采用。

- **结论**：组件侧三类逐字样板只在引擎与 scpi.values 各定义一次（#629）。`on_state(self, key, path, old, new)` 第一参就是该变化经哪个参数到达（同路径多参数绑定时取声明顺序的第一个，#436 的负载设定与 Vpp 表；经 `watches` 或嵌套映射到达时为 None），组件不再用 `bound_paths()` 反转还原参数名；要把值写回某参数绑定的设定，用 `bound_path(key)`。兄弟组件引用只有 `peer(name, required=...)` 与 `ref(key)`（refs 声明的一行访问器；可选 ref 未填为 None，必填 ref 缺失报 -300）一个入口，四种错误策略（KeyError / -300 / None / peer）收敛成一种。布尔型设定解析只有 `V.flag`：非字符串按真值（int 1 即 True，与运行时 `bool(value)` 一致），ON/OFF/1/TRUE 词按词义——原五份 `_flag` 私有拼写（electrical/calibrator/smu/daq/meters，int 1 有的返回 True、有的透传原值）删除。守卫 `tests/test_component_boilerplate.py` 锁定：组件目录无 `bound_paths()` 查询（喂 watcher 登记的三处 override 除外）、无手拼 `ch{self.channel}` 兄弟名、无 `components[str(self.param(...))]` 方括号访问器、无 `def _flag`。

## D62 组件缝声明为 Protocol，refs 的目标可以是协议，加载期点名缺的方法

- **结论**：组件之间的鸭子接口缝仿 `Sampler` 声明为 `runtime_checkable` Protocol（`engine/component.py`，#630）：`Acquisition`（`read_record`、`transfer_record`、`timebase_scale`、`acq_count`——`waveform_transfer` 的 `record` 引用）、`AcquisitionInput`（可选的输入链 figures：`probe_ratio`、`adc_unit`、`adc_codes_per_div`，没有就落回传输自己的参数）、`TraceSource`（`trace_value`——曲线缓冲的迹线与锁相显示读的量）。`Component.refs` 的目标除组件类型名外可以是一个协议类；定义加载时按协议的**方法**成员扫描被指组件的类，缺方法在第一条 E-DEF-COMPONENT-REF 里点名（`缺 read_record, transfer_record, …`），运行时组件访问器再以 isinstance 复查一次（同 `trigger_model._sampler`，属性成员如 `acq_count` 只在这一层查得到）。transfer/curve/lockin 的 `hasattr` 探测与 `type: ignore[attr-defined]` 清零，守卫 `tests/test_component_boilerplate.py` 锁定组件目录无 `hasattr(`。校准器的 `_Setpoint`/`_Control` mixin 直接继承 `Component`（`range_name` 下移为 mixin 默认 None，`hasattr(sp, "range_name")` 删除），25 处 attr-defined ignore 一并清零。
- **理由**：换采集组件时没有任何声明告诉作者必须实现 `transfer_record`，六处 ignore 与三连 hasattr 是类型系统对同一问题的抗议。备选一是抽象基类：`runtime_checkable` 的 isinstance 只查成员存在性已够，ABC 重架构不必要；备选二只在运行时报错：作者要跑到第一条命令才发现写错组件，加载期校验（`E-DEF-COMPONENT-REF` 已有的流程）是第一条错误就指明缺什么的现成落点。类级检查只扫方法成员，是因为实例属性（`acq_count` 在 `__init__` 赋值）对类不可见——扫它会误报合法组件。
- **影响**：写新采集/迹线组件的要求有了名字（实现协议即是全部）；`refs` 声明与加载期校验对有效定义行为不变（全部内置定义原样通过）。同类未清的遗留：rfgen/sources 的 6 处 attr-defined ignore（synth/clock 缝，未列入 #630）、calibrator 的 `getattr` 探测（`kind`/`check_sense`/`_locked`，mixin 类型化后可再收）、lockin 的 3 处 return-value ignore。

## D63 VXI-11 做成网络服务；GPIB 与 USBTMC 的行为在虚拟总线上仿真，脚本从进程内或进程外都能用；锁与远程/本地状态各仪表一份

- **结论**：
  1. **VXI-11 是网络协议，做**：`access/vxi11_server.py`，ONC RPC over TCP，核心、abort、中断（SRQ）三个通道，只监听 127.0.0.1。设备名 `inst<i>`（按 bench 顺序）、`inst_<实例名>`，以及 bench 的 `address:` 声明为 GPIB 的仪表另有 LAN/GPIB 网关形式 `gpib<板>,<主地址>[,<次地址>]`，不替没声明的仪表编 GPIB 地址。端口映射器（RFC 1833，只答 GETPORT）可选：VISA 库只会问 111 端口，那是特权端口、常被 rpcbind 占着，所以默认不开（`--portmapper-port`），不开时地址写成 `TCPIP0::127.0.0.1,<端口>::inst0::INSTR`（pyvisa-py 认这种写法，NI-VISA 不认）。只服务 TCP，不服务 UDP；`device_readstb` 是串行轮询（读后清 RQS）。
  2. **GPIB 与 USBTMC 的仿真对象是脚本能观察到的行为，不是物理线缆**。用户不关心仪表程控接口用什么实现，要的是 `GPIB0::4::INSTR`、`USB0::…::INSTR` 的脚本不改就能调。所以两种总线各有服务端模型，访问方式另行协商：
     - **虚拟 GPIB 总线**（`access/gpib_bus.py`，每块板一条）：bench 里 `address:` 声明为 GPIB 的仪表是总线上的设备；板卡主地址 0（有设备占 0 时用 30）。控制器用命令字节寻址 talker/listener（含次地址），UNL/UNT/SDC/DCL/GET/GTL/LLO/SPE/SPD 按 IEEE 488.1 作用于被寻址的听者或全部设备；IFC 让总线接口回到空闲但不清仪表；REN 是整条总线的线，被寻址时才进入远程；SRQ 线是各设备 RQS 锁存之或；无听者时写返回 `VI_ERROR_NLISTENERS`。VISA 在设备会话背后做的事按真实命令序列发生：写是 UNL+MTA(板)+MLA(设备)，`viClear` 是 SDC，`viAssertTrigger` 是 GET，`viReadSTB` 是 SPE+MTA+串行轮询+SPD。`GPIB<n>::INTFC` 会话是板卡本身：`viGpibCommand`、`viGpibSendIFC`、`viGpibControlATN`、`viGpibControlREN`，读写发给被寻址者，线路状态属性可读。没有模型的设备能接过控制（C0、PP0），所以传递控制只能失败（`VI_ERROR_NSUP_OPER`）。
     - **虚拟 USBTMC/USB488 接口**（`access/usbtmc.py`，每台 USB 仪表一个）：按 USBTMC 1.00 与 USB488 1.00（usb.org）的表实现：全部类请求及其 USBTMC_status、响应布局（GET_CAPABILITIES 24 字节、INDICATOR_PULSE、READ_STATUS_BYTE 与 bTag 2–127、REN_CONTROL/GO_TO_LOCAL/LOCAL_LOCKOUT）；INITIATE/CHECK 拆分事务（ABORT_BULK_OUT/IN、CLEAR），拆分期间别的类请求回 STATUS_SPLIT_IN_PROGRESS；端点 halt 只有 `CLEAR_FEATURE(ENDPOINT_HALT)` 能解除，`GET_STATUS` 可查；Interrupt-IN 端点承载 SRQ（bTag 1）与状态字节，队列满回 STATUS_INTERRUPT_IN_BUSY；RL 状态机（REN 加一条消息或 TRIGGER 才进入远程）。端点地址（0x02/0x81/0x83）与中断 FIFO 深度是仿真设备自己的选择，所有仪表相同；GET_CAPABILITIES 只报模型实现了的能力（SCPI 位不置）。
     - 事件 `bus_control` 记录每次总线动作（命令字节作用、IFC、REN 模式、USB 控制请求）。
  3. **总线状态各仪表一份**（`access/bus.py`）：资源锁（一把独占锁，或一把共享锁、同键者共享）、REN/GTL/LLO 状态机（RL1：LOCS/REMS/LWLS/RWLS）与 RQS 锁存按仪表保存，HiSLIP、VXI-11、GPIB、USB、PyVISA 会话看到同一份。RQS 锁存是 IEEE 488.1/488.2 的规则：仪表状态字节第 6 位在引擎里是 MSS（汇总），“新原因”才置位 RQS 并拉起 SRQ，串行轮询返回带 RQS 的状态字节并清掉它，所以等 SRQ 再轮询的脚本只看到一次请求，所有接口的读状态字节（GPIB、USB、VXI-11、HiSLIP 状态查询、进程内会话）都是这一条规则；锁存由引擎的 scpi 事件驱动观察，不依赖访问层记得调用。
  4. **一个 VISA 会话在总线上能做的事是 `Link`**（`access/links.py`）：写、读、清除、触发、读状态字节、REN、锁、SRQ 等待，网络/GPIB/USB/INTFC 各一种实现；PyVISA 后端只留 VISA 自己的缓冲区、属性与超时。不适用于会话类型的属性、未知请求按 VISA 报错（此前后端只返回状态码，PyVISA 不会因此抛错）。
  5. **进程外的脚本用连接模式**（`access/bench_link.py`）：`serve`/`tui`/`mcp` 默认在 127.0.0.1:4881 开一个控制端口（`--link-port`，0 自动分配；绑定失败只警告），一行 JSON 一个请求，把 `Link` 的方法原样转发到服务里执行，所以行为与进程内一致，界面同时看得到。`PYVISA_LIBRARY=127.0.0.1:4881@simubench`（或 `SIMUBENCH_LINK`）让不指定库的 `pyvisa.ResourceManager()` 连到服务；什么都不给时试默认端口。每个 link 有自己的连接（一个资源的长等待不挡住另一个资源的查询），算远程客户端（界面拒绝改动、客户端列表与锁标记可见，事件里标 `bench:` 前缀），连接断开时锁随之释放。服务把自己各端口的地址随 hello 告诉脚本，所以 `serve` 打印的 SOCKET/HiSLIP/VXI-11 地址在连接模式下同样能打开。脚本自己的等待（读超时、等 SRQ）在命令时钟下推进共享的虚拟时间（`Session.wait`，原因 `wait`，记录并可回放），不走会被“有脚本连着就拒绝”拦下的显式推进；界面的显式推进仍受保护。传输可以换：HiSLIP 厂商自定义消息也能承载同一组调用，选专用端口是因为板卡会话不属于任何仪表、HiSLIP 连接却必须挂在一个子地址上。
- **理由**：VXI-11 是大量老仪表脚本与 LAN/GPIB 网关的写法，纯软件可以完整做到；GPIB 线缆与 USB 设备需要硬件（GPIB 适配卡多半不支持设备端，USB 要 gadget 硬件），但脚本观察到的行为不需要：寻址、命令、SRQ、串行轮询、控制请求都是协议，可以仿真。上一版曾把 GPIB 总线命令、USB 控制请求、进程外 USBTMC 写成“不支持”，那等于把仿真行为当可选，已改正。备选一在 SimuBench 里自带 GPIB/USB 驱动层：要特权与硬件，得不偿失；备选二给没声明地址的仪表自动分配 GPIB/USB 地址：会编出厂商号与序列号，违背“拒绝而不猜”。锁与 REN 若各接入方式各存一份，同一台仪表被 HiSLIP 与 VXI-11 脚本同时用时行为与真机不符。
- **影响**：HiSLIP 的锁不再只在 HiSLIP 会话之间生效（D41 已改）；HiSLIP 共享锁现在要求同键才合并（与 VISA 一致）；`SessionInfo` 的仪表多 `address_vxi11`，会话多 `link_address`，`ClientInfo` 与 `remote` 含 `vxi11:`、`bench:` 客户端；`serve`/`tui`/`mcp` 多 `--vxi11-port`（0 为自动分配）、`--portmapper-port`（隐含开启 VXI-11）、`--link-port`；VXI-11 在 `SessionManager` 与命令行都默认不开：端口随机，默认开会让启动器输出的地址表（TUI 脚本与 e2e 的固定画面）变得不确定，要用时显式打开。
- **已知缺口**：
  - VXI-11 `device_docmd`（经 LAN/GPIB 网关发 GPIB 总线命令，VXI-11.2）：规范原文取不到（vxibus.org 拒绝自动访问），命令码与数据布局不凭记忆写，仍回“不支持”。NI-VISA、LabVIEW 这类不走 PyVISA 的程序因此还不能从网关做 GPIB 总线命令，设备读写、状态字节、触发、清除、REN、锁照常。
  - NI-VISA、LabVIEW、C# 等不走 PyVISA 的程序没有 USB 与 GPIB 地址的进程外入口（它们的 VISA 库要真硬件）；软件路径是 USB/IP 服务器导出虚拟 USBTMC 设备，客户端用 vhci-hcd 或 usbip-win 接入，需要客户端机器的管理员权限，是另一块大工作，未做。
  - GPIB：EOI 不是单独的线（消息在引擎的消息边界结束），握手时序、并行轮询（设备是 PP0）、传递控制（设备是 C0）不仿真。
  - USB：标准描述符与枚举（GET_DESCRIPTOR 等）不仿真，请求回 STALL；一次传输就是一条消息。
  - UDP 版 VXI-11；HiSLIP 的缺口见 D41。

## D64 Web 读数新鲜度：事件版本 re-key，不轮询；会话与故障键 250ms 防抖

- **结论**：仪表屏幕的读数查询（`useReadings`）以事件版本号进 queryKey，版本一变重新取一次，不做定时轮询（原 `refetchInterval: 1000` 已删，#694）。版本号保证在四类时机前进：写命令（SCPI write）、状态变化事件、wall/scaled 时钟节拍（每 500ms）、WebSocket 重连（`events.ts` 重连成功时 +1；首次连接不 +1——各查询刚以版本 0 挂载，+1 会让每屏的首次加载翻倍）。页级的 `session`/`faults` 键不带版本，保留 WorkbenchPage 的 250ms 防抖失效（事件风暴合并），与读数的仪表级即时取数分工：一个命令恰好触发一次 readings 请求（`web/src/api/hooks.test.tsx` 计数断言）。
- **理由**：前端面板是"改一个值马上看读数"的界面，事件驱动立即反映，轮询最快也要 1s；轮询还让挂载的每屏每秒打一次端点，8 仪表 bench 闲时也有底噪，且与 re-key 并存时同一命令双请求。备选"只留 1s 轮询"：命令后读数最多延迟 1s，面板手感迟钝，弃。断线缺口靠重连 bump 补：断连期间丢的事件追不回来，重连 +1 让全部版本键查询重读一次，自愈；连接着的时候 TCP 不丢事件，不需要兜底轮询。
- **影响**：`useInstrumentReadings` 收整个 `inst` 并内聚 `stateMap`（各屏不再每渲染自建 Map）；readings 端点请求量从"每屏每秒一次 + 每命令一次"降为"每命令一次 + 每次重连一轮"；Scope（自己的查询）、网探针、内部构造视图订阅同一版本给自己的查询（不是读数接线，各自保留延迟订阅）；Lockin 的历史点累积留在屏内（SettlingChart 自己的采样规则，#694 给出结论）。

## D65 测试台不内置；随包只发一个 Hello World 示例，首页一键复制进工作区；首页的仪表画面来自真实运行

- **结论**：软件包内置的只有仪表（D42），测试台都是用户工作区里的文件。为了让新用户第一步就看到结果，随包发布**一个** Hello World 示例（`library/examples/hello.bench.yaml`：函数发生器同一方波分别接示波器与频谱仪，时域与频域各一台真实型号）。它不出现在测试台列表里，是模板：首页「从 Hello World 开始」经 `POST /api/benches/hello` 把它**原样**（注释保留）复制成工作区的 `hello.bench.yaml` 并打开；已有同名文件时直接打开、绝不覆盖，复制记入版本历史（D35）。复制后就是用户的文件，可以改名、换型号（`replace_instrument`）、改设置。首页是产品介绍页：上面展示的示波器波形、频谱、TUI 与网页画面一律来自这个示例的真实运行（`scripts/capture_hello_preview.py`、`docs/tui/hello.steps.yaml`），不手画；示例或相关型号变化后重新生成。
- **理由**：首批用户在本地 IDE 里开发，`simubench serve` 在他们自己的项目目录里运行（product-form.md 2），工作区一开始是空的，旧首页只能说"放入 *.bench.yaml"。备选一"启动时在空工作区自动写示例"：零点击，但不经同意往用户目录写文件，IDE 也只在"新建项目"时生成 Hello World，不在打开文件夹时写；备选二"内置一批测试台、在列表里只读出现"：模糊了"测试台是用户资产"的界线，而且只读的测试台改不了，第一件想做的事（换成自己的仪表）就做不到；备选三"随包发布全部 examples/（每个型号一个）"：数量多、选择成本高，而且 examples 里有为排查练习故意设的陷阱（探头倍率不一致），不适合当第一印象。手画的预览会与用户点开后看到的画面不一致，对以"行为像真机"为卖点的产品是反效果；实测还暴露了要靠设置规避的提示（参考电平余量、记录长度够两个上升沿），示例文件里写明原因。
- **影响**：wheel 多一个示例文件；首页资源（实测 JSON、3 张网页截图、3 张 TUI SVG，约 0.5 MB）随 web 打包；`DefinitionSummary.workspace` 区分"我的仪表"；`docs/ui-design.md` 2 与 6 记首页结构与仪表屏幕动效（示波器余辉、频谱仪扫频线，减少动态效果时关闭）。CLI 与 MCP 暂未提供复制示例的入口，需要时复用 `BenchFiles.create_hello`。

## D66 Web AI 助手：服务端对话循环（PydanticAI）、直接实施加按轮恢复、工具权限在服务端强制

- **结论**：Web Bench 增加对话式助手（总览 #871，设计 `docs/ai-assistant.md`），用于搭建 bench 与定制仪表。对话循环在服务端，用 PydanticAI 接 OpenAI 兼容与 Anthropic 兼容两种协议，LLM 由用户配置（服务端配置或环境变量给默认值，Web 设置页可覆盖，API key 只写不读，地址只允许 http/https 且不得指向 SimuBench 自身端口）。工具复用 MCP 背后的同一批服务，权限由服务端实现强制：运行中只能调参数、可删仪表与连线、不能删 bench 或定义文件。AI **直接实施**，不做预览确认（用户不读 YAML）；兜底是每轮自然语言总结、自动校验与自修复、“恢复到上一轮之前”（只在最后一轮，文件之后被改过则先列出将丢失的改动）。上下文用 compact 管理，不设每轮次数上限，由“停止”与原地打转检测兜底。用户的“我的模板”是独立快照（不 `extends` 内置型号），与 D59 的“复制为我的仪表”并存。第一版只做 Web。
- **理由**：备选一：自己写薄循环——依赖最少，但两种协议与压缩要自己维护。备选二：生成变更预览由用户确认——用户看不懂 YAML，确认形同虚设。备选三：每轮固定次数上限——正常的长任务会被误断，且压缩管不了原地打转，所以改为停止加打转检测。备选四：模板沿用 `extends`——内置型号改名、删除或列表新增时子定义会失败或悄悄变旧。
- **代价**：新增 PydanticAI 依赖（`pydantic-ai-slim[openai,anthropic]`，装好约 78 MB，SimuBench 自己的 wheel 不变；#872 已验证两种协议、流式、工具调用与压缩）；服务端新增“用户发起的删除”（仅限本轮新建的文件，#876）；LLM 地址由服务端发起请求，允许内网地址是有意的取舍；独立快照拿不到内置型号后续的修正，用户需要重新保存。

## D67 仪表内部的信号链：模拟域保持解析，ADC 之后是按帧拉取的采样流

- **结论**：仪表内部功能块之间有两种信号连接。模拟域沿用现有的解析描述（`Signal`：直流 + 谱线，D1、architecture.md 2）；数字域新增采样流（介质 `samples`，数据 `SampleFrame`：一帧采样，带采样率与格式）。ADC 是两者之间唯一的边界：按采样时刻对解析信号求值，在此实现模拟噪声、量化与削波。采样流**按帧拉取**：下游向上游请求“从某时刻起的 N 个采样”，一帧是请求、参数、上游信号版本与种子的纯函数；块不保存跨帧的流状态，需要历史的块向上游多要预热采样。信号一律走连线，`refs` 只表示设置依赖。频谱仪的迹线有两种求值方式，由定义选择：`analytic`（默认，现有的谱线解析求值）与 `sampled`（整条链的采样流），两者共用同一批功能块与参数。设计见 [signal-chain.md](signal-chain.md)。
- **理由**：定位包含验证仪表内部的算法与架构（D17），要求采样点在功能块之间流动、每一级可观察；待验证的算法几乎都在 ADC 之后，真实的软件定义仪表也是这个结构。备选一是把网络上的信号整体改为采样流（时域仿真）：能表达瞬态，但放弃了模拟域的精确、速度与能力上限的明确规则，现有全部组件与金标准都要重做。备选二是推送式的连续流、块带状态（GNU Radio 的方式）：结果取决于读取的次序与次数，违反“同一时刻两次读取相同”与被动读取不改变仿真（D55）。备选三是频谱仪只保留采样式求值：窄 RBW 宽跨度的计算量没有上限，现有型号的行为会从“能算”变成“拒绝”。均不采用。
- **代价**：没有连续流与跨帧状态（长冲激响应用预热近似，块写明误差界）；两种求值方式的结果只在容差内一致，由对照测试约束；混频器之后的模拟信号取决于本振的调谐点，求值多一个输入。瞬态与单次事件仍需时域信号源，不在本条范围。
- **第一版的范围**：示波器的采集改经采样流（外部行为不变）、频谱仪的信号链与前端非理想、内部探针。算法托管、定点类型、金标准比对与链路预算工具不做，只留接口（signal-chain.md 第 8 节）。

## D68 硬件选件：定义声明选件带来的组件参数与命令，测试台实例列出装了哪些

- **结论**：定义的 `components` 与 `commands` 描述不带任何选件的整机。`options` 逐个声明硬件选件：`id`、`label`、`params`（`{组件: {参数: 值}}`，装了该选件的整机用它替换同名参数）；命令可写 `option: <id>`，没装的整机跳过它，由同一命令头上后面不带 `option` 的命令回答，没有时回 `-241`。测试台实例用 `options: [P03]` 列出这台仪表装了的选件，不写即不带选件（#1004）。选件在打开测试台时生效，运行中不变。
- **理由**：数据手册把前置放大器这类部件列为选件，同一型号的两台整机前端指标不同，而一份定义原来只能二选一。备选一是每种选件组合一份定义（或用 `extends` 派生）：型号数随选件组合成倍增加，“同一型号、不同配置”在测试台上变成不同的 `model`，`*IDN?` 的型号字段还要另外改回去。备选二是只用测试台的 `hidden` 覆盖参数：能改参数，但命令的有无改不了，而且每个测试台都要抄一遍数据手册的数值，数值不在定义里就没有出处。备选三是选件声明整块组件与连线：表达力最强，但内部结构随实例变化，连线校验、内部探针与界面的结构图都要按实例展开；目前的选件（前放、扩频段）都只是已有功能块的参数。
- **代价**：选件不能增减组件、端口、状态量与连线；属于选件的设置在未装的整机上仍然存在（只是没有命令能写它，也没有参数读它）。授权类选件在运行中安装（`LIC` 命令）不在本条范围。`*OPT?` 只有在定义写了 `identity.options_reply` 时才按实例已装的选件回复；不写时仍由定义自己绑定状态量（#1007）。实例的 `options` 由编辑操作 `set_options` 整体替换（Web 检查器与 MCP 共用），与其他改变结构的编辑一样在测试台重新打开时生效（#1007）。

## D69 设置之间的约束写在定义里：按改动后的状态判断，拒绝或改另一个设置

- **结论**：定义顶层的 `constraints` 声明“`when` 的设置取这些值时，`forbid` 的设置不能取那些值”，以及仪表怎么办：`refuse`（报错，默认 -221，什么都不改）或 `coerce`（改动生效，被禁止的设置改成给定值）。判断用改动之后的整机状态，与先设哪个无关；一条命令写几个设置时按它全部写完后的状态判断（#1013）。SCPI 与界面、MCP 的设置（`configure`）都受约束；仪表自己的连带写入、回放与故障注入不受。静态校验 `E-DEF-CONSTRAINT`，开机与 `*RST` 后的状态不能违反约束。
- **理由**：仪表越复杂，设置之间的联动越多（模式互斥、选件与功能、通道数与采样率、RBW/跨度/扫描时间），手册的写法是两种：“不可用”（拒绝）和 coupling（自动改另一个）。备选是每遇到一类联动就给组件加参数（如 `scope_acquisition` 的 `segmented_processing`）：范围小、各组件自己判断，但每一类冲突都要改组件代码，型号 issue 因此反复被能力缺口卡住（#1013 本身就是这样来的），而且同一种“不可用”在不同组件里各写一遍。约束写在定义里，型号作者照手册逐条声明，出处跟着条目走。
- **代价**：第一版只有等值条件、只用整机设置，数值关系与按通道的设置以后加；组件里已有的联动判断（如 `check_settings`）不迁移，两处并存；`coerce` 改的设置在运行记录里是一次普通的设置变化，看不出是被约束带动的。

## D70 几个设置共同决定一个参数：嵌套映射与按设置分组的个体偏差

- **结论**：组件参数的映射可以嵌套：`map`、`table` 的取值与 `default` 可以是另一个映射，选中时按它自己的设置再取一次（#383 起运行时已能解析 `map` 里的嵌套，#1020 补上 `table` 里嵌套的变更通知与所有嵌套的静态校验）。个体偏差可写 `when`（写法同 D69）与 `option`（D68）：同一参数每组设置一条，各抽一条个体值，运行时取第一条 `when` 成立的，不带 `when` 的一条是其余情况；记录键带条件（`input.flatness[power.gain=ON,…]`）。数据手册按“通路”给出整条通路的指标时，前放起作用的那条通路把指标全写在前放上，其后的级在这条通路上不计入（`null`）。
- **理由**：真实仪表的指标常由几个设置一起决定（频谱仪的前放开关 × 频段 × 中心频率、示波器的带宽限制 × 输入阻抗、功率计的传感器 × 量程），手册按组合列表。备选一是给每类组件加专用参数（如 `specan_input` 的 `paths: {std: …, lna: …}` 加 `path: $power.path`）：每个类别各写一遍，下一个类别还要再加；备选二是定义层另设“按设置选参数组”的块：与已有的映射重复，同一个参数有两种写法。嵌套映射沿用已有的写法，只是允许取值再是映射，校验与通知都在同一处；分组偏差与约束共用 `when`，作者只学一种条件写法。
- **代价**：深层嵌套的 YAML 难读（同一组数值用锚点与别名写一次可缓解）；条件只有等值、只用整机设置，数值区间（如中心频率 ≥ 3.6 GHz）仍要写成 `table` 嵌套；按设置分组的偏差彼此独立抽取，两组条件共享同一段硬件时（N9042B 前放频段 LOW 在 3.6 GHz 以上走标准通路），那一段的个体曲线在两组之间不相同，覆盖表注明。

# 决策记录

记录产品讨论中已经确定的结论。每条包含结论、理由，以及仍待细化的部分。

## D1 产品方向：用软件定义的方式做仪表仿真

- **结论**：目的是纯软件的虚拟仪表，让工程师无需真实仪表即可开发和测试；方法是软件定义仪表，仪表由内部功能模块组合而成，信号在模块之间流动并被计算，测量结果由配置、输入和系统状态共同决定。
- **理由**：与 EdgeSim 这类“规则声明行为”的仿真器形成差异；误差、校准常数等可以放在它们真实所在的模块上，天然适合仪表开发与校准场景。
- **待细化**：模块之间传递的信号表示（采样流、直流值、频谱等）如何按场景选用；虚拟时间如何推进并与命令时序配合。

## D2 暂不考虑硬件

- **结论**：当前只做纯软件，不考虑将仪表定义部署到真实硬件。
- **理由**：聚焦产品核心；架构可以更简单。

## D3 分层使用，门槛按角色递进

- **结论**：内部模块结构是平台的实现方式，而不是对所有用户的要求。用户按需要逐层深入：
  1. **使用仪表**：从仪表库选现成仪表，通过 SCPI 等接口使用，无需了解内部；
  2. **配置仪表/DUT**：选择仪表类别模板，用数据手册的语言填写（量程、技术指标、校准点、误差参数），平台把这些参数映射到内部模块；
  3. **搭建仪表**：打开模板的模块图修改，或从模块搭建新仪表，必要时编写自定义模块。
- **理由**：校准软件工程师熟悉的是数据手册与校准流程，而不是电路框图；只有仪表开发等少数场景需要第 3 层。
- **影响**：门槛从用户转移到平台。每个仪表类别的模板（包括“技术指标 → 内部误差参数”的映射）需要平台以领域知识精心构建，这是核心工作量，也是竞争壁垒。首批应少而精地覆盖几类仪表。

## D4 核心价值：定标脚本上产线前先在虚拟环境跑通

- **结论**：首要解决的痛点是“定标脚本只有上了产线才发现问题”。SimuBench 的核心价值是把问题发现提前到开发阶段。
- **典型场景**：Python + PyVISA 编写的定标脚本，驱动信号源（如 UTG9604T）与示波器（如 T3DSO2000）完成定标。
- **要求**：虚拟环境必须复现产线与开发环境的差异，否则提前不了：连线与阻抗等测试台配置、仪表个体差异、异常与超限情况、通信时序与超时。
- **衡量标准**：在 SimuBench 中通过的脚本，上产线后出问题的比例。

## D5 首个接入方式：PyVISA

- **结论**：首先支持 PyVISA，脚本只需切换资源地址即可在虚拟仪表与真实仪表之间切换，其余代码不变。
- **理由**：首批用户的定标脚本使用 Python + PyVISA；脚本若需为仿真而修改，验证结果就不可信。

## D6 CI 是场景之一：引擎可无界面运行

- **结论**：CI 是重要场景之一，但不决定产品形态。引擎必须能以无界面方式运行（命令行 + Python 库 + PyVISA 后端），以便进入 CI。
- **CI 场景的要求**：
  1. **无界面运行**：在 Linux 容器和企业内网 CI（如 GitLab CI、Jenkins）中运行，不依赖图形界面和外网；
  2. **确定**：固定版本与随机种子下结果完全一致，CI 不能有偶发失败；
  3. **快**：虚拟时间可快于真实时间，一次 CI 要能覆盖多台 DUT、多个场景；
  4. **配置即代码**：测试台、DUT、场景都是文件，与定标脚本放在同一仓库，随代码一起版本管理；
  5. **明确的判定**：输出 CI 可识别的结果（退出码、JUnit 报告），失败时保留运行记录与种子，可在本地精确重现；
  6. **授权方式适配 CI**：支持无界面、离线、临时容器环境下的授权。
- **判定依据**：脚本“跑完没报错”不等于通过。虚拟 DUT 的真实误差已知，可以检查脚本写入的定标系数是否正确、合格判定是否正确。

## D7 可视化不后置；引擎与界面分离

- **结论**：可视化是第一个版本的一部分。引擎与界面分离：引擎通过接口对外提供测试台状态、信号与事件，界面只是客户端。
- **界面需承担的工作**：观察仪表状态与波形、修改参数与注入故障、控制虚拟时钟、查看 SCPI 通信记录、回放运行记录、展示与编辑测试台拓扑。
- **待定**：第一个界面是 Web Bench 还是 TUI。

## D8 Bench 是核心对象

- **结论**：Bench 是 SimuBench 的核心对象。用户创建、打开、运行、观察、保存、复制、共享、版本管理的都是 Bench；其他概念都属于某个 Bench 或服务于 Bench。
- **Bench 包含**：
  - 仪表：来自仪表模型（或模板）的实例及其配置；
  - DUT：被测/被定标对象；
  - 连线与配件：线缆、衰减器、三通、负载等；
  - 运行条件：随机种子、虚拟时钟设置；
  - 故障与场景：预设的故障条件及触发时机。
- **与 Bench 相关但不属于 Bench 的**：
  - 仪表模型库：可复用的“零件”，Bench 引用它们；
  - 测试程序（如定标脚本）：在 Bench 之外，通过资源地址连接 Bench 中的仪表；
  - 运行记录：每次运行产生，归属于某个 Bench 的某个版本。
- **三种形态**：
  - **Bench 定义**：可保存、复制、共享、版本管理的文件，始终是干净的初始状态；
  - **运行中的 Bench**：由定义启动，测试程序连接并改变其状态；同一定义可同时启动多个；
  - **运行记录**：每次运行的命令、状态变化与结果，可回放、对比。
- **暂不支持保存运行状态**：运行结束后的状态（如已写入定标系数的 DUT）不回写到 Bench 定义，也不提供“快照另存为”。每次运行都从定义的初始状态开始。

## D9 三种接入方式：PyVISA 后端、本地 SCPI 网络仪表、本地 MCP

- **结论**：Bench 通过三种方式对外提供，三者都是引擎的客户端，与界面使用同一套引擎接口。
  1. **PyVISA 后端**：`pyvisa.ResourceManager("<bench 文件>@simubench")`，按 Bench 中的仪表名打开资源。Python 用户的主要方式。
  2. **本地 SCPI 网络仪表**：Bench 启动后，每台仪表在本机监听一个 TCP 端口（如 `TCPIP::127.0.0.1::5025::SOCKET`），脚本只需改地址；NI-VISA、C#、LabVIEW 等均可连接。
  3. **本地 MCP 服务**：AI Agent 通过 MCP 帮助工程师构建与部署 Bench，并控制和观察 Bench。
- **MCP 的能力（草案）**：
  - 构建：查询仪表模型库（型号、端口、支持的命令）；创建与编辑 Bench（添加仪表与 DUT、连线、配置、故障）；校验 Bench 并返回明确的错误与警告（端口不兼容、阻抗不匹配等）；
  - 由脚本生成：分析现有测试程序用到的仪表与命令，生成 Bench 草稿，并指出模型尚不支持的命令；
  - 部署：启动 Bench，返回各仪表的资源地址，生成脚本切换到虚拟环境所需的配置；
  - Bench：列出与打开 Bench、启动/停止运行、查看拓扑与仪表列表；
  - 仪表：发送 SCPI 命令与查询、读取仪表状态与测量结果、获取波形摘要；
  - 运行控制：修改参数、注入故障、暂停/单步虚拟时钟；
  - 观察：读取 SCPI 通信记录与运行记录；
  - 脚本：针对 Bench 运行一个测试程序，返回判定结果与运行记录。
- **影响**：
  - Bench 的编辑操作（添加、连线、配置、校验）必须实现在引擎中，Web 画布与 MCP 共用，而不是只存在于界面；
  - Bench 定义格式与仪表模型库要便于 Agent 理解：声明式、有完整 schema、能自我描述；
  - Agent 对 Bench 的修改落到可读、可 diff 的文件上，并实时显示在 Web Bench 中，由工程师审阅。
- **真实值可见性**：作为 Bench 运行时开关。调试模式下 Agent 可读取真实值，用于定位脚本问题；验证模式下关闭，避免 Agent 在执行定标时直接读取答案。判定始终在后台使用真实值，不受开关影响。
- **进入第一个闭环**：MCP 的“由脚本生成 Bench”和“部署”纳入闭环，以及闭环所需的基础查看、SCPI 收发与脚本运行。

## D10 第一个闭环的验证场景：锁相放大器、示波器与射频信号源

- **结论**：第一个闭环改用以下场景验证（参考 EdgeSim 的对应指南），代替“信号源 + 示波器定标”：
  1. 锁相放大器，详见 [validation-lockin.md](validation-lockin.md)；
  2. 示波器采集到电压，详见 [validation-scope.md](validation-scope.md)。
  3. 射频信号源调制，详见 [validation-rfgen.md](validation-rfgen.md)。
- **两个场景共用同一个 RC 低通 DUT**：验证 DUT 在多个 Bench 中复用，并以“两台原理不同的仪表测同一 DUT，结果一致”作为 SimuBench 独有的验收项。
- **理由**：锁相放大器是清晰的模块化信号链，契合 D1；示波器覆盖逐点采样、触发、二进制传输与大量真机才暴露的脚本问题；被测 RC 低通有已知理论值；两者都有公开的参考输出可作为验收数据。
- **待定**：命令集是否与 EdgeSim 兼容；虚拟时间的推进方式；与定标场景的关系。

## D11 验证分工：开发验证用参考场景，定标场景由产品负责人验收

- **结论**：开发过程中用产品负责人提供的参考场景（D10）验证引擎与仪表模型；定标场景由产品负责人亲自验收。
- **理由**：参考场景有公开的输出数据，可作为客观、可重复的开发验收标准；定标场景贴近首批用户的真实工作，由熟悉业务的人判断是否“对”。
- **影响**：定标场景所需的能力（DUT 个体误差、定标系数、真值判定）仍在闭环之后的范围内，但引擎设计不得阻碍它们；“隐藏状态”（见 validation-rfgen.md）是两者共用的基础。

# 决策记录

记录产品讨论中已经确定的结论。每条包含结论、理由，以及仍待细化的部分。

收录门槛：一条选择要**同时满足**以下两点才记入——有实际备选方案（两条路都说得通，以后有人可能想翻案）；影响超出单个功能（文件格式、API、术语、产品范围、安全模型等）。功能本身的说明放在 issue、PR 与对应文档。修改已有决策时改原条目，不另加新条目；已有条目保持编号不变。

## D1 产品方向：用软件定义的方式做仪表仿真

- **结论**：目的是纯软件的虚拟仪表，让工程师无需真实仪表即可开发和测试；方法是软件定义仪表，仪表由内部功能模块组合而成，信号在模块之间流动并被计算，测量结果由配置、输入和系统状态共同决定。
- **理由**：与 EdgeSim 这类“规则声明行为”的仿真器形成差异；误差、校准常数等可以放在它们真实所在的模块上，天然适合仪表开发与校准场景。
- **待细化**：模块之间传递的信号表示（采样流、直流值、频谱等）如何按场景选用；虚拟时间如何推进并与命令时序配合。
- **统一组件模型**：Bench 层与仪表内部使用同一套“组件 + 端口 + 连线”。仪表是封装好的组件组合，DUT、探头、线缆、衰减器、缓冲器、波形文件源也都是组件。同一种组件可在两层通用（如一阶低通既可作 RC DUT，也可作示波器带宽限制）；仪表内部任一组件的输出都可以被替换（如用录制波形替换 ADC 输出）。SCPI 命令层只把命令映射到组件参数，行为由组件决定。
- **界面以仪表展示**：组件模型是实现方式，不是默认的展示方式。Bench 页面上展示的是仪表（设置、读数、屏幕、端口）、DUT 与连线；仪表内部的组件图只在用户主动打开时展示（对应 D3 第 3 层）。仪表卡片由仪表定义自动生成（类别模板 + 通用布局，定义中可附显示提示），不为单个型号编写界面代码。

## D2 暂不考虑硬件

- **结论**：当前只做纯软件，不考虑将仪表定义部署到真实硬件。
- **理由**：聚焦产品核心；架构可以更简单。

## D3 分层使用，门槛按角色递进

- **结论**：内部模块结构是平台的实现方式，而不是对所有用户的要求。用户按需要逐层深入：
  1. **使用仪表**：从仪表库选现成仪表，通过 SCPI 等接口使用，无需了解内部；
  2. **配置仪表/DUT**：选择仪表类别模板，用数据手册的语言填写（量程、技术指标、校准点、误差参数），平台把这些参数映射到内部模块；
  3. **搭建仪表**：打开模板的模块图修改，或从模块搭建新仪表，必要时编写自定义模块。
- **理由**：校准软件工程师熟悉的是数据手册与校准流程，而不是电路框图；只有仪表开发等少数场景需要第 3 层。
- **第 3 层的只读查看提前提供**（issue 20）：Web Bench 可以打开任一仪表的内部组件图（组件、内部连线、面板端口），参数显示型号的标称值，跟随设置的参数显示当前设置；测试台为单台仪表设的个体偏差不属于型号，不在图中。编辑仍按原计划推后。
- **第 3 层的搭建由用户与 Agent 完成，平台提供能力**（设计见 [instrument-authoring.md](instrument-authoring.md)）：平台不可能提供所有型号，常见的命令方言、应答格式、波形传输与运行控制都应能在定义文件中声明；声明不了的行为用插件组件实现，已安装包的入口点默认加载，工作区中的插件代码默认不加载、需工程师显式开启；Agent 经 MCP 只创建与编辑定义文件，不写代码。界面中的定义编辑仍推后。
- **第 2 层从计量类仪表起步**（设计见 [metrology-authoring.md](metrology-authoring.md)，总 issue #86）：仪表定义新增 `deviations`，写明可偏差的参数、按量程等的分表、±限值与分布（均匀，或正态与包含因子）；测试台实例写 `deviation: from_specs` 时由测试台种子抽取个体偏差，写死的 `hidden` 值逐项优先。`specs` 仍只记录手册原文的指标，两者不自动对应：手册指标到参数的换算需要领域判断，由写型号的人完成。另一条路是从 `specs` 的结构化格式自动推出偏差，因为各厂商指标的写法差别太大而不采用。
- **搭建经 Agent，Web 用于验收与配置**（#123，设计见 instrument-authoring.md 第 7 节）：定义文件的格式是平台内部的，用户不需要了解。仪表的搭建与修改由 Agent 经 MCP 完成；Web 不提供定义的编辑（YAML、表单、组件图都不做），只用于验收（概览、命令、内部结构、试运行、用例、以仪表语言描述的修改记录）和像真实仪表面板一样的配置。另一条路是在 Web 中提供定义编辑器，因为要求用户掌握内部格式而不采用。第 2 层的仪表模板供 Agent 使用：按输入展开为一份普通定义（记下来源模板与输入），不采用运行时引用模板，以免多出一层格式、模板升级悄悄改变已有仪表。
- **影响**：门槛从用户转移到平台。每个仪表类别的模板（包括“技术指标 → 内部误差参数”的映射）需要平台以领域知识精心构建，这是核心工作量，也是竞争壁垒。首批应少而精地覆盖几类仪表。

## D4 核心价值：定标脚本上产线前先在虚拟环境跑通

- **结论**：首要解决的痛点是“定标脚本只有上了产线才发现问题”。SimuBench 的核心价值是把问题发现提前到开发阶段。
- **典型场景**：Python + PyVISA 编写的定标脚本，驱动信号源（如 UTG9604T）与示波器（如 T3DSO2000）完成定标。
- **要求**：虚拟环境必须复现产线与开发环境的差异，否则提前不了：连线与阻抗等测试台配置、仪表个体差异、异常与超限情况、通信时序与超时。
- **衡量标准**：在 SimuBench 中通过的脚本，上产线后出问题的比例。

## D5 首个接入方式：PyVISA

- **结论**：首先支持 PyVISA，脚本只需切换资源地址即可在虚拟仪表与真实仪表之间切换，其余代码不变。
- **理由**：首批用户的定标脚本使用 Python + PyVISA；脚本若需为仿真而修改，验证结果就不可信。

## D6 CI 是场景之一：引擎可无界面运行

- **结论**：CI 是重要场景之一，但不决定产品形态。引擎必须能以无界面方式运行（命令行 + Python 库 + PyVISA 后端），以便进入 CI。
- **CI 场景的要求**：
  1. **无界面运行**：在 Linux 容器和企业内网 CI（如 GitLab CI、Jenkins）中运行，不依赖图形界面和外网；
  2. **确定**：固定版本与随机种子下结果完全一致，CI 不能有偶发失败；
  3. **快**：虚拟时间可快于真实时间，一次 CI 要能覆盖多台 DUT、多个场景；
  4. **配置即代码**：测试台、DUT、场景都是文件，与定标脚本放在同一仓库，随代码一起版本管理；
  5. **明确的判定**：输出 CI 可识别的结果（退出码、JUnit 报告），失败时保留运行记录与种子，可在本地精确重现；
  6. **授权方式适配 CI**：支持无界面、离线、临时容器环境下的授权。
- **判定依据**：脚本“跑完没报错”不等于通过。虚拟 DUT 的真实误差已知，可以检查脚本写入的定标系数是否正确、合格判定是否正确。

## D7 可视化不后置；引擎与界面分离

- **结论**：可视化是第一个版本的一部分。引擎与界面分离：引擎通过接口对外提供测试台状态、信号与事件，界面只是客户端。
- **界面需承担的工作**：观察仪表状态与波形、修改参数与注入故障、控制虚拟时钟、查看 SCPI 通信记录、回放运行记录、展示与编辑测试台拓扑。
- **展示原则**：无论 Web Bench 还是 TUI，Bench 页面都以仪表为单位展示（见 D1）。
- **已决定**：第一个界面是 Web Bench（见 D18）。

## D8 Bench 是核心对象

- **结论**：Bench 是 SimuBench 的核心对象。用户创建、打开、运行、观察、保存、复制、共享、版本管理的都是 Bench；其他概念都属于某个 Bench 或服务于 Bench。
- **Bench 包含**：
  - 仪表：来自仪表模型（或模板）的实例及其配置；
  - 元件：RC 网络、电阻、缓冲器等不带命令层的对象（#100 之前称为“DUT”）；
  - DUT 是**角色**而不是一类对象：仪表或元件都可以标为 DUT（被测/被定标对象），例如定标时被校的万用表就是 DUT，而接在电路中的 RC 网络可能只是夹具或负载。测试台文件中写作 `dut: true`（格式 `bench/2`，`bench/1` 的 `duts` 读取时迁移为标为 DUT 的元件）；也可以没有 DUT（仪表自检、演示）。另一种做法是保留 DUT 这一类、再给仪表加“被测”标记，没有采用：同一个词会同时指一类对象和一个角色；
  - 连线与配件：线缆、衰减器、三通、负载等；
  - 运行条件：随机种子、虚拟时钟设置；
  - 故障与场景：预设的故障条件及触发时机。
- **与 Bench 相关但不属于 Bench 的**：
  - 仪表模型库：可复用的“零件”，Bench 引用它们；
  - 测试程序（如定标脚本）：在 Bench 之外，通过资源地址连接 Bench 中的仪表；
  - 运行记录：每次运行产生，归属于某个 Bench 的某个版本。
- **三种形态**：
  - **Bench 定义**：可保存、复制、共享、版本管理的文件，始终是干净的初始状态；
  - **运行中的 Bench**：由定义启动，测试程序连接并改变其状态；同一定义可同时启动多个；
  - **运行记录**：每次运行的命令、状态变化与结果，可回放、对比。
- **暂不支持保存运行状态**：运行结束后的状态（如已写入定标系数的 DUT）不回写到 Bench 定义，也不提供“快照另存为”。每次运行都从定义的初始状态开始。

## D9 三种接入方式：PyVISA 后端、本地 SCPI 网络仪表、本地 MCP

- **结论**：Bench 通过三种方式对外提供，三者都是引擎的客户端，与界面使用同一套引擎接口。
  1. **PyVISA 后端**：`pyvisa.ResourceManager("<bench 文件>@simubench")`，按 Bench 中的仪表名打开资源。Python 用户的主要方式。
  2. **本地 SCPI 网络仪表**：Bench 启动后，每台仪表在本机监听一个 TCP 端口（如 `TCPIP::127.0.0.1::5025::SOCKET`），脚本只需改地址；NI-VISA、C#、LabVIEW 等均可连接。
  3. **本地 MCP 服务**：AI Agent 通过 MCP 帮助工程师构建与部署 Bench，并控制和观察 Bench。
- **MCP 的能力（草案）**：
  - 构建：查询仪表模型库（型号、端口、支持的命令）；创建与编辑 Bench（添加仪表与 DUT、连线、配置、故障）；校验 Bench 并返回明确的错误与警告（端口不兼容、阻抗不匹配等）；
  - 由脚本生成：分析现有测试程序用到的仪表与命令，生成 Bench 草稿，并指出模型尚不支持的命令；
  - 部署：启动 Bench，返回各仪表的资源地址，生成脚本切换到虚拟环境所需的配置；
  - Bench：列出与打开 Bench、启动/停止运行、查看拓扑与仪表列表；
  - 仪表：发送 SCPI 命令与查询、读取仪表状态与测量结果、获取波形摘要；
  - 运行控制：修改参数、注入故障、暂停/单步虚拟时钟；
  - 观察：读取 SCPI 通信记录与运行记录；
  - 脚本：针对 Bench 运行一个测试程序，返回判定结果与运行记录。
- **影响**：
  - Bench 的编辑操作（添加、连线、配置、校验）必须实现在引擎中，Web 画布与 MCP 共用，而不是只存在于界面；
  - Bench 定义格式与仪表模型库要便于 Agent 理解：声明式、有完整 schema、能自我描述；
  - Agent 对 Bench 的修改落到可读、可 diff 的文件上，并实时显示在 Web Bench 中，由工程师审阅。
- **并发**：一个运行中的 Bench 可同时被多个客户端连接（脚本、pytest、界面、Agent）；所有操作按到达顺序串行执行，写入同一份运行记录。
- **真实值可见性**：作为 Bench 运行时开关。调试模式下 Agent 可读取真实值，用于定位脚本问题；验证模式下关闭，避免 Agent 在执行定标时直接读取答案。判定始终在后台使用真实值，不受开关影响。
- **进入第一个闭环**：MCP 的“由脚本生成 Bench”和“部署”纳入闭环，以及闭环所需的基础查看、SCPI 收发与脚本运行。

## D10 第一个闭环的验证场景：锁相放大器、示波器、射频信号源、频谱分析仪与 SMU

- **结论**：第一个闭环改用以下场景验证（参考 EdgeSim 的对应指南），代替“信号源 + 示波器定标”：
  1. 锁相放大器，详见 [validation-lockin.md](validation-lockin.md)。
  2. 示波器采集到电压，详见 [validation-scope.md](validation-scope.md)。
  3. 射频信号源调制，详见 [validation-rfgen.md](validation-rfgen.md)。
  4. 频谱分析仪，详见 [validation-specan.md](validation-specan.md)。
  5. 源测量单元 IV 扫描，详见 [validation-smu.md](validation-smu.md)。
- **锁相放大器与示波器场景共用同一个 RC 低通 DUT**：验证 DUT 在多个 Bench 中复用，并以“两台原理不同的仪表测同一 DUT，结果一致”作为 SimuBench 独有的验收项。
- **理由**：锁相放大器是清晰的模块化信号链，契合 D1；示波器覆盖逐点采样、触发、二进制传输与大量真机才暴露的脚本问题；被测 RC 低通有已知理论值；两者都有公开的参考输出可作为验收数据。
- **已解决**：命令兼容见 D13；虚拟时间见 D12；与定标场景的关系见 D11。另有多通道场景（D15），期望值由电路理论计算。

## D11 验证分工：开发验证用参考场景，定标场景由产品负责人验收

- **结论**：开发过程中用产品负责人提供的参考场景（D10）验证引擎与仪表模型；定标场景由产品负责人亲自验收。
- **理由**：参考场景有公开的输出数据，可作为客观、可重复的开发验收标准；定标场景贴近首批用户的真实工作，由熟悉业务的人判断是否“对”。
- **影响**：定标场景所需的能力（DUT 个体误差、定标系数、真值判定）仍在闭环之后的范围内，但引擎设计不得阻碍它们；“隐藏状态”（见 validation-rfgen.md）是两者共用的基础。

## D12 虚拟时间：默认由命令驱动

- **结论**：虚拟时间支持三种推进方式，由 Bench 的运行条件选择：
  1. **命令驱动（默认）**：仪表在处理需要时间的命令时推进虚拟时钟，推进量等于该操作实际需要的时长。例如单次扫描 `:INITiate` 配合 `*OPC?` 推进一次扫描时间，示波器 `:DIGitize` 推进一次采集时间。脚本空闲、没有命令到达时（如 `time.sleep()`），虚拟时间默认跟随真实时间推进；也可由 `run.idle` 改为不计或按 `time.sleep` 精确计入（D47）。
  2. **墙钟**：虚拟时间始终等于真实时间，用于上真机前的最后一次彩排。
  3. **步进时钟**：只有显式调用推进接口时才前进，用于 SDK、pytest 与 CI 中需要精确控制时间的场景。
- **理由**：真机脚本本来就用命令或等待来同步仪表；命令驱动让未修改的 PyVISA 脚本也能获得正确的虚拟时间，同时比墙钟快，满足 D4、D5。
- **要求**：每个仪表模型必须声明哪些命令消耗时间、消耗多少；同一 Bench、同一种子、同一命令序列下结果确定。空闲的真实时间如何计入，由 D47 的 `run.idle` 选择。

## D13 兼容性：数值对齐参考场景，命令行为对齐真实仪表

- **结论**：
  - **物理与数值结果**对齐参考场景（D10）的公开输出，作为开发验收标准；
  - **命令的细节行为**（参数格式、可接受的写法、字节序等）对齐真实仪表，而不是照搬参考实现因自身模型格式造成的限制。例如列表参数加引号与不加引号都接受。
- **理由**：SimuBench 的目标是让脚本在上真机前跑通。照搬参考实现的局限，会让能在真机上运行的脚本在 SimuBench 中失败。
- **物理正确优先**：当参考实现为简化而偏离电路物理时（如把 RC 低通当作单纯的滤波操作，不计入信号源输出阻抗与 DUT 输入阻抗的相互作用），SimuBench 按物理正确求解（architecture.md 1.4 节）；受影响的期望值由电路理论重新计算，并在场景文档中列为差异。
- **信号源电平约定对齐真实仪表**：电平或幅度的定义（开路电压，或按设定负载定义）由每个仪表定义声明，与对应真实仪表一致。多数函数发生器按设定的输出负载（默认 50 Ω，可设为高阻）定义幅度，实际负载不同时输出端电压随之变化。
- **影响**：与参考实现的命令差异与数值差异逐项记录在对应场景文档中。

## D14 支持录制的波形文件（CSV / BIN）

- **结论**：工程师会使用录制好的波形文件进行开发和测试，SimuBench 支持把波形文件作为 Bench 的一部分。
- **在组件模型中的位置**：波形文件由“波形文件源”组件播放，与其他组件一样有端口、参数和行为。它可以放在两个位置：
  1. **Bench 层**：像一台信号源一样接到仪表输入端口，信号经过仪表前端（耦合、带宽、探头等）再被测量；
  2. **仪表内部**：替换仪表内部某个组件的输出（例如 ADC 之后的原始采样），绕过前端，直接驱动后续处理与测量。
- **用途**：
  - 优先：作为激励，用真实采集的信号驱动仪表和 DUT；作为仪表的返回数据，示波器等仪表按录制数据返回波形；
  - 以后：作为参考结果与测量结果比对；导出为 CSV / BIN 供其他工具使用。
- **需要定义的规则**：
  - 格式：CSV（时间与数值列，或数值列加采样率）；BIN（原始 int16 / float32 等，需要说明数据类型、字节序、采样率、比例、偏置、通道数的元数据）；
  - 采样率与仿真不一致时的重采样方式；文件结束后的行为（循环、保持最后值、归零）；与虚拟时钟的对齐；
  - 计算路径：录制信号没有解析式，走数值路径（与任意波、PRBS 相同），受相同的能力上限约束；
  - 可复现：Bench 通过相对路径引用文件，运行记录保存文件哈希；大文件按需加载。

## D15 仪表支持多通道

- **结论**：仪表可以有多个通道（如四通道示波器、四通道信号源），多通道从一开始就纳入组件模型与命令映射。
- **在组件模型中的位置**：
  - **通道是仪表内部重复的一组组件**（如示波器每个通道各有前端、耦合、带宽、ADC），各通道有自己的端口（CH1–CH4、OUT1–OUT4）、参数与隐藏状态；
  - **通道不一定相同**：同一仪表的不同通道可以有不同能力（如 UTG9604T 的 CH1/CH2 为 600 MHz、2.5 GSa/s，CH3/CH4 为 200 MHz、625 MSa/s），因此通道由“通道定义 + 每通道参数”实例化；
  - **共享组件**：时基、触发、存储深度等由多个通道共享，例如触发组件按触发源选择通道；
  - **通道间关系**：通道间相位同步、通道组合（如信号源 CH1 与 CH2 合并）、数学通道（如 CH1 − CH2）由跨通道组件实现。
- **命令映射**：命令中的通道序号（如 `:CHANnel<n>:SCALe`、`:SOURce<n>:FREQuency`、`:OUTPut<n>:STATe`、`:WAVeform:SOURce CHANnel<n>`）映射到第 n 个通道的组件；省略序号时按真实仪表的默认规则（通常为 1）。
- **展示**：仪表卡片按通道展示；示波器在一个屏幕上用不同颜色显示多条迹线，信号源逐通道列出设置与输出状态。
- **确定性**：各通道的噪声相互独立，并由 Bench 种子确定。
- **与其他决策的关系**：每个通道可以有独立的隐藏误差与定标系数（定标场景）；多列 CSV 可映射到多个通道（D14）。
- **验证**：见 [validation-multichannel.md](validation-multichannel.md)，期望值由电路理论计算。
- **待细化**：通道间共享资源的约束（如开启通道越多、每通道采样率越低）；通道间时延与串扰（与定标场景中的通道间时延定标相关）。

## D16 可观测性是一等能力：用户可观测，运维可运维

- **结论**：可观测性是 SimuBench 的核心能力，在架构中单独设计，面向两类对象：
  - **用户可观测**：工程师看清仪表、信号与运行过程；
  - **运维可运维**：产品团队能监控、诊断和改进分布在用户本机、内网与 CI 中的 SimuBench。
- **理由**：真实测试台很难看清“里面发生了什么”，仿真中所有信号与状态都是计算出来的，可以完整地观察、解释和回放；同时 SimuBench 本地优先运行在用户环境中，产品团队必须有办法在不接触用户机器的情况下定位问题。

### 用户可观测

1. **虚拟探针**：在任意网络或仪表内部组件的端口上观察信号，不影响电路；
2. **状态**：仪表设置、组件参数、隐藏状态与真实值（受 D9 的可见性开关约束）；
3. **通信**：每条命令与响应，带虚拟时间与真实时间；
   界面与 MCP 中的操作（修改值、注入故障、推进时钟）同样作为动作记录，并与 SCPI 命令区分；
4. **事件**：错误、过载、失锁、超出模型能力、故障注入等，带发生时间与来源组件；
5. **因果解释**：任一读数可以追溯到产生它的组件、信号描述与参数；
6. **保真度标注**：结果中的近似（截断、离散化、能力上限）被明确标出；
7. **时间线**：命令、状态变化、事件、测量在同一条时间线上对齐；
8. **运行记录与对比**：回放一次运行，对比两次运行的差异；
9. **出口**：界面、MCP（供 Agent 查询与解释）、CI 产物、标准格式导出。

### 运维可运维

1. **结构化日志**：分级、带会话与运行编号，便于关联同一次运行的所有记录；
2. **指标**：求解耗时、命令延迟、内存、并发会话数、错误率；
3. **产品改进信号**：哪些命令不被模型支持、哪些能力上限被触发、哪些错误最常出现，用于决定模型与组件的开发优先级；
4. **版本信息**：引擎、组件库、仪表模型、Bench 格式的版本与兼容性；
5. **健康检查**：引擎与各接入服务是否正常；
6. **崩溃报告与诊断包**：一键导出脱敏后的诊断包（日志、版本、环境、运行记录摘要），断网环境下由用户手动发送；
7. **问题重现**：用户同意时，凭 Bench 定义 + 运行记录 + 种子在产品团队本地精确重现问题；
8. **标准接口**：指标与日志可导出到标准可观测性工具，供私有化部署平台集成。

### 数据边界

- 用户的脚本、Bench 内容、波形、测量结果属于用户资产，默认不离开用户环境；
- 运维数据的收集方式待定（见下）。

- **遥测策略**：见 D17。

## D17 第一阶段在内部使用

- **结论**：SimuBench 第一阶段只在公司内部使用，用户是内部的仪表开发与校准软件工程师。
- **遥测**：内部阶段默认开启，日志、指标与产品改进信号发送到内部收集服务；收集地址与开关可配置。对外发布时改为默认关闭、由用户主动开启，诊断包与问题重现机制不变。
- **数据边界仍按对外标准设计**：用户资产（脚本、Bench 内容、波形、测量结果）与运维数据分开处理，对外发布时只需改变默认配置，不需要改架构。
- **影响**：
  - 授权与计费（D6 第 6 项、scope.md 中的授权行）推迟到对外发布前；
  - 部署在内网：内部软件包源、内部 CI（如 GitLab CI、Jenkins）；
  - 与用户距离近，可直接访谈与观察使用过程，作为遥测之外的反馈来源。

## D18 界面：Web Bench 为主，终端控制台（TUI）为补充

- **结论**：第一个界面是 Web Bench，由本地的 `simubench serve` 提供，用浏览器打开，不需要安装桌面程序。终端控制台（`simubench tui`）作为补充，用于 SSH 远程、与脚本同屏观察、可复现的截图与演示。
- **理由**：画布编辑与审阅 Agent 搭建的 Bench、清晰的波形与频谱、仪表内部组件图都需要图形界面；引擎与界面分离（D7），选择不影响引擎。
- **TUI 的约束**（[tui-design.md](tui-design.md)）：
  - **只是服务的客户端**：经与 Web 相同的 HTTP/WebSocket 接口访问会话，不在进程内直接调用引擎；`simubench tui <bench>` 在本进程启动服务后连上，`--attach` 连接已运行的服务。另一条路（进程内直接用引擎）启动更快，但远程状态、确认与来源要再实现一遍，也无法与脚本、Web、Agent 共用会话，没有采用；
  - **只观察与操作，不做编辑**：测试台的修改仍只有画布、MCP 与编辑器三个入口（D25）；
  - **Textual，可选依赖** `simubench[tui]`，与 `simubench[mcp]` 一样不进核心依赖；
  - **操作来源“终端”**：请求带上客户端类型，运行记录与事件中与“界面”“Agent”区分；
  - **命令未被执行的原因进入事件**：错误事件给出分类（覆盖表中未实现、型号没有、定义中没有、已忽略、内置命令被排除、参数不合法），TUI、Web 与 MCP 共用；提示只转述定义作者声明的内容并写明出处（#172）。
- **详见**：architecture.md 第 8 节、tui-design.md。

## D19 实现语言：Python 起步，为 Rust 留好边界

- **结论**：引擎、接入层与服务用 Python（NumPy/SciPy）实现；计算密集的部分（信号求值、网络求解、频谱计算）放在清晰的接口之后，性能分析表明需要时再改用 Rust 实现，接口与上层不变。Web 前端用 TypeScript。
- **理由**：PyVISA 后端、pytest 插件、SDK 与 MCP 都在 Python 生态中；第一阶段在内部使用，首要目标是尽快验证产品。

## D20 同时支持 Windows 与 Linux

- **结论**：用户机器与 CI 同时包括 Windows 与 Linux，SimuBench 在两个平台上都要可用。
- **影响**：
  - **确定性**：同一平台、同一版本下逐字节一致；跨平台在验收容差内一致，不要求逐字节一致；
  - **CI**：验收测试在 Windows 与 Linux 上都运行；
  - **进程间通信**：服务进程与客户端之间使用本机 TCP，不依赖只在类 Unix 系统上可用的 Unix 套接字；
  - **路径与文件**：Bench 中的文件引用使用与平台无关的相对路径；
  - **发布**：纯 Python 包 + NumPy，两个平台使用同一份包。

## D21 Web 技术栈与接口生成

- **结论**：
  - 前端：React + shadcn/ui + React Flow（Bench 画布）；仪表屏幕中的波形、频谱、曲线在 React Flow 节点与独立面板中用 Canvas 绘制；
  - 后端：FastAPI，作为 `simubench serve` 的 HTTP 与 WebSocket 服务；
  - **接口文件自动生成**，不手写前后端之间的类型与客户端代码。
- **单一来源**：接口以 Python 中的 Pydantic 模型为唯一来源，自动生成：
  1. HTTP 接口：FastAPI 生成 OpenAPI 描述，再生成前端 TypeScript 类型与客户端；
  2. WebSocket 消息（事件、状态更新、动作）：同一批 Pydantic 模型导出 JSON Schema，再生成 TypeScript 类型；
  3. Bench 与仪表定义文件的 JSON Schema（用于校验与编辑器提示）；
  4. MCP 工具的输入输出 schema。
- **一致性检查**：生成结果提交到仓库；CI 中重新生成并比较，不一致即失败，防止前后端接口漂移。

## D22 界面按商用标准交付

- **结论**：界面直接按商用产品的质量设计与实现，不做演示版。宁可功能少，不交付半成品。
- **含义**：设计先行；建立 SimuBench 设计体系（基于 shadcn/ui 的设计令牌、浅色/深色主题、仪表视觉语言）；每个页面与组件实现完整状态；完整的画布交互（撤销/重做、自动保存与版本等）；性能预算；可访问性与中英文；组件、端到端与视觉回归测试；本地服务安全；每个里程碑做可用性验证。
- **详见**：roadmap.md“界面质量标准”。

## D23 没有专职设计师与品牌规范；界面以中文为主、英文为辅

- **结论**：
  - 团队没有专职产品设计师，也没有既定品牌规范；
  - 界面以中文为主、英文为辅：中文完整，英文覆盖全部界面文本，文档以中文为主。
- **设计工作的承担方式**：
  - 信息架构、任务流程、线框图、交互说明、设计体系由开发团队（含 AI 辅助）产出，按 D24 自检；
  - **以代码为设计源头**：设计令牌与组件库（Storybook）就是设计稿，不另外维护一份会过时的视觉稿；
  - 以成熟的仪表软件与专业工具为对标，做启发式评审；
  - 可用性验证（roadmap.md）比有设计师时更重要，不能省略。
- **品牌基础**（M0 中建立）：SimuBench 文字标志、主色与功能色、中文字体（如思源黑体 / Noto Sans SC）与等宽数字字体、图标风格。
- **中文为主的要求**：术语表（[glossary.md](glossary.md)）统一用词；中文排版（行高、字重、中西文混排间距）；英文文本通常更长，布局需容纳；所有文本外置，便于切换语言。

## D24 开发期间不设评审卡点

- **结论**：进入开发后直到验证完成，产品负责人不再评审中间产物；开发按本文档的决策自主推进，不以评审作为卡点。
- **替代机制**：
  - 原计划中的设计评审与里程碑评审改为开发团队的自检：每个里程碑按 roadmap.md 的完成条件与界面质量标准逐条自查，结果记录在 [progress.md](progress.md)；
  - 遇到决策文档未覆盖的问题，按已有原则选择最合理的方案，记录为新的决策，继续推进；
  - 产品负责人在验证完成后验收（含定标场景，D11）。
- **术语**：DUT 不翻译（glossary.md）。

## D25 测试台文件是编辑的唯一来源；切回操作时按新定义重建

- **结论**：画布编辑、MCP 编辑与文本编辑器修改的都是测试台文件本身，没有单独的“草稿”。每次编辑立即保存（乐观并发：带上读取时的文件哈希，哈希不符返回 409）。打开的会话不随编辑改变拓扑；文件内容指纹（不含布局与说明）与会话打开时不同，切回操作模式时自动按新定义重建（无“重新启动”按钮），并提示仪表设置回到初始值；搭建中的定义不合法（校验错误）则阻止切换、停留在搭建模式并定位问题（#31）。有脚本连着 SCPI 端口时，重建会断开它们：先确认，或选“稍后重建”回到正在运行的测试台，顶栏提示文件已改并可随时重建（#121）。
- **理由**：Agent 与工程师改的是同一份可读、可 diff 的文件（D9）；外部修改（Agent、编辑器、另一个窗口）通过轮询载入并提示变化摘要，不会被静默覆盖；移动节点不会触发重启提示。
- **撤销/重做**：保存完整文档快照，撤销即以当前哈希写回上一版本；外部修改载入后历史清空，避免撤销覆盖他人的修改。
- **预览**：编辑画布显示“按当前文件构建、但不运行”的测试台；无法构建的部分（未知型号、错误连线）省略并列出，其余照常显示。

## D26 MCP 服务与 Web Bench 同进程

- **结论**：`simubench mcp` 以 stdio 提供 MCP 服务，同一事件循环中启动 Web Bench；Agent 部署的会话、编辑的文件实时出现在工程师的浏览器中。stdout 只用于 MCP 协议，其余输出写 stderr。
- **安全**：危险命令需 `confirm=true`；仿真控制（故障注入、推进时钟、读取真实值）默认关闭，需 `--allow-control`；读取真实值还需测试台 `run.reveal_true_values`；所有工具共享限流。
- **由脚本生成**：静态分析 PyVISA 脚本（不执行），按“支持的命令最多”选择仪表定义，列出不支持的命令与行号；看不出接线，草稿只含仪表。

## D27 故障在会话的收发入口生效

- **结论**：通信层故障（超时、断连、乱码、延迟、忙）在 `Session.write/read` 生效，PyVISA 后端（`VI_ERROR_TMO`、`VI_ERROR_CONN_LOST`）、SCPI 网络仪表、界面与 MCP 看到同样的故障；仪表层故障（错误码、保护跳闸）与组件层故障（参数漂移、改变隐藏状态）通过错误队列、仪表状态与组件参数覆盖生效，故障结束时恢复。故障按虚拟时间触发与结束，可预设在测试台文件中，所有变化写入运行记录。乱码按种子可复现。

## D28 YAML 按 1.2 的规则读取浮点数

- **结论**：测试台与仪表定义文件中 `1.0e7`、`1e-7` 读作数字。PyYAML 默认的 YAML 1.1 规则要求指数带符号，否则读成字符串，工程师写的参数会被静默当成文本。

## D29 直接串联的 RC 是合法电路

- **结论**：示波器场景第 7 组中，参考实现在校验时拒绝两个 RC 直接串联（其信号流模型无法处理负载效应）。按 D13（物理正确优先），直接串联是合法电路，第二级是第一级的负载：SimuBench 接受并求解，fc 处增益 0.323（理想两级为 0.5），与独立的二端口网络计算一致（`acceptance/test_scope_scenario.py`）。

## D30 锁相放大器的解调是精确的

- **结论**：输入网络上的每条谱线与参考相乘后都是复指数；n 个相同一阶低通级联对复指数之和的响应有闭式解（特解加 e^(−t/T) 乘多项式的齐次解）。任何变化（信号、频率、相位、时间常数、斜率）都从该时刻的滤波器状态开始新的一段，因此建立过程在虚拟时间中精确，不做逐点采样。
- **噪声**：前端白噪声由按计数器生成的高斯序列经同样的 n 级滤波器冲激响应加权得到，并精确归一到 σ = eₙ·√ENBW；它是种子与虚拟时间的纯函数：同一时刻读两次结果相同，一个时间常数内的读数相关。
- **引擎支持**：带有时间演化状态的组件（`dynamic`）在每次信号变化时、虚拟时间前进之前由会话调用 `sync()`，记录变化发生的确切时刻。
- **任意波**：表格按线性插值播放，谱线精确（sinc²），解调也精确，因此“接近但不等于参考频率”不是模型边界（见 validation-lockin.md）。

## D31 PyVISA 中每个资源管理器是一台刚上电的测试台

- **结论**：PyVISA 按测试台路径缓存后端库对象。关闭资源管理器时会话随之关闭，之后再打开的资源管理器得到新的会话。测试之间不会继承彼此修改过的仪表状态，与真实测试中“每个测试从已知状态开始”的习惯一致。

## D32 前面板的读数与操作不经过 SCPI

- **结论**：界面显示仪表读数（锁相放大器的 X/Y/R/θ、万用表读数）使用只读的读数接口：不产生通信记录、不改变错误队列、不推进虚拟时间。
- **面板操作**（示波器的运行、停止、单次）同样不是 SCPI 命令：在仪表内部执行（定义的 `display.actions` 给出与之等价的型号命令，否则用采集组件的 `run`、`stop`、`single`），不进“通信”、不改变错误队列与脚本待读的回复、不推进虚拟时间；每次操作记为一个“面板操作”事件（来源：界面），写入运行记录，回放时重新执行。运行中的屏幕在当前虚拟时间重算画面（噪声逐帧不同），这些画面不是采集记录；停止或等待单次触发时定格在最近一次采集。脚本看到的命令、回复与虚拟时间与界面是否开着屏幕无关；“单次”是一次真正的采集，脚本随后读到的就是它（issue 32）；型号声明采集在虚拟时间中完成时（`completion: pending`，#134），脚本在它完成后读到它，完成前读到的是上一帧；面板按下的“单次”当场完成，用的是面板自己的时间。
- **远程状态**（#121）：仪表的 SCPI 端口（raw socket、HiSLIP）上有连接时，它处于远程状态，与真机的 REM 一样：界面经 HTTP 接口的改设置、SCPI 控制台与面板操作被拒绝（409，列出客户端）；只读读数、探针、时间线与故障注入不受影响。界面的“本地（LOCAL）”从脚本接管这台仪表，直到远程客户端向它发出下一条命令，两次切换都记为 `remote` 事件。会断开或扰动已连接脚本的整台操作——打开另一个测试台、关闭、重置、推进虚拟时间——须带 `force` 确认。脚本的一条消息与随后的回复读取是一次动作，界面控制台的查询不会取走脚本的回复。MCP 的工具是 Agent 的操作，不受远程状态限制。墙钟模式下虚拟时间本来就等于真实时间，只读接口读取的是当前真实时刻（不产生事件）。锁相放大器另外返回按当前设置“将要走的”建立曲线（不含噪声），界面与已读取的历史一起画出。

## D33 频谱仪：谱线精确，噪声按分辨单元确定

- **结论**：RF_IN 上的每条谱线按 V²/2R 经高斯 RBW 滤波器画出；接收机噪声 kT₀·F·NBW（加衰减）按“迹线点 × 分辨单元”生成，由种子、扫描序号、点与单元确定。迹线是设置、RF_IN 历史信号、种子与扫描序号的纯函数；每次扫描使用该扫描开始时 RF_IN 上的信号，因此信号源中途改变时，平均与最大保持能“记住”之前的谱线。
- **周期信号一律精确**：方波、锯齿、任意波表、PRBS 都由精确的谱线表示，不做加窗 FFT 估计（D13、D30）。模型唯一的截断是谱线数上限，截断时信号带有说明，读取它的仪表据此报告（锁相放大器 329、频谱仪 −221）。
- **模型缺陷不影响脚本**：仪表模型内部的异常转为 −300 设备错误进入错误队列并写日志，不会让客户端脚本崩溃。

## D34 分段线性器件：限值与负载按工作点精确求解

- **结论**：带限值的源（SMU）与电子负载是分段线性器件：每种模式（恒压、恒流、受最小电阻限制）都是线性元件。会话求解后，每个器件按直流工作点检查自己的模式是否成立，不成立则切换并重新求解，直到所有器件一致（最多 40 次）。四象限限值、负载向源灌电流、电子负载的拐点都由此精确得到。
- **仪表内部扫描对任意负载有效**：每个扫描点都按当时的测试台求解，因此参考实现拒绝的“非线性负载上的仪表内部扫描”在 SimuBench 中给出每点精确的工作点（D13）。逐点扫描得到相同的结果。
- **恒压模式的电流直接取自节点分析**：理想电压源的支路电流是方程组的未知量，读数不经过两个相近电压相减，七位有效数字下电阻读数为 999.9 Ω 而不是 999.8999 Ω。

## D35 测试台文件的版本历史

- **结论**：每次保存都在工作区的 `.simubench/history/<测试台路径>/` 留下一个版本，记录保存者（界面、Agent、API、外部修改、恢复）与时间。在 SimuBench 之外的修改（文本编辑器、git 检出）在下一次保存时作为“外部修改”版本补记，历史不会漏掉工程师看到过的内容。
- **合并**：同一来源在两分钟内连续只移动节点的保存合并为一个版本，拖动节点不会淹没历史。
- **恢复**：把旧版本作为新版本写回，之后的版本仍保留；只有超过 200 个版本时删除最旧的。
- **审阅**：界面按项列出差异（仪表、DUT、连线的新增、删除与修改，修改列出每个字段的新旧值），可看“这次修改了什么”或“与当前文件相比”。Agent 通过 MCP 的保存都标为 Agent，MCP 也提供 `list_bench_history`、`read_bench_version`。

## D36 运行记录可以独立回放

- **结论**：运行记录的头部携带完整的测试台与每个仪表定义的哈希，记录本身就能回放。`simubench replay <记录>` 用记录中的种子重建测试台，按记录的虚拟时刻重发每条命令、界面中的设置变化与注入的故障，并逐条比较回复；第一处不同给出记录序号、仪表、虚拟时刻、之前的命令与两边的内容，退出码 1。命令驱动、步进、墙钟三种时钟的记录都按记录的时刻回放（墙钟记录以步进方式回放）。
- **采集保存为配方**：示波器每次采集写入一条 acquisition 事件（触发时刻、采样间隔、点数、种子、每个通道数据的哈希）；二进制回复（波形数据块）在记录中只保存长度、哈希与对应的采集，不保存原始字节，回放时按哈希比较。需要原始字节时以 `--record-raw` 启动。文本回复照原样保存。
- **定义变化**：回放时仪表定义与记录中的哈希不同，报告警告，差异可能来自定义本身。
- **界面**：首页列出最近的运行记录（服务以 `--record-dir` 启动时）；运行记录页按仪表分道显示虚拟时间上的时间线与事件列表，“回放并比较”给出结果并定位到第一处不同。

## D37 虚拟探针与“为什么是这个值”

- **结论**：在运行模式中选中一个网络（或一根连线），检查器显示虚拟探针：网络上的波形、直流、有效值、峰值与主要谱线。探针不加载电路、不经过仪表、不产生事件。
- **解释即计算**：网络电压按独立源分解——每个源的电动势乘以节点分析求得的、从该源到这个网络的传递函数（幅度与相位），逐频率列出“电动势 × |H|∠φ = 贡献”。这正是引擎计算网络信号的方式，因此解释与读数严格一致，不是事后的近似说明。信号不精确时（谱线截断等），同时列出保真度说明。

## D38 运维：结构化日志、版本清单、健康检查、诊断包

- **日志**：`--log-format json` 每行一个 JSON 对象（UTC 时间、级别、来源、消息与附加字段），`--log-file` 另存文件；进程内保留最近 2000 条 info 及以上的记录，供诊断包使用。
- **版本清单**：`simubench version --full` 与 `/api/manifest`：引擎、Python、平台、主要依赖版本、每个仪表定义的版本与哈希、界面构建的哈希、工作区与运行记录目录。与运行记录头部的定义哈希一起，可判断两次运行的差异是否来自版本。
- **健康检查**：`simubench doctor`（退出码 1 表示有失败项）与界面“关于与诊断”：Python 版本、依赖、MCP、PyVISA 后端注册、仪表定义、界面构建、工作区中的测试台文件、端口、临时目录；每项说明如何修复。
- **指标**：`/api/metrics` 以 Prometheus 文本格式给出会话数、各会话按类型的事件计数、电路求解次数与耗时、虚拟时间。
- **保真度标注**：会话信息中每个网络附带其信号的保真度说明（谱线截断等）；画布上该网络的连线标 ≈，悬停显示原因。说明只随信号到达的网络传播。
- **诊断包**：`simubench diagnose` 与界面导出：版本清单、健康检查、最近日志、正在运行的会话（含最近的错误与故障）及其测试台文件、最近的运行记录（每份最多 5 MB）。不含访问令牌，不自动上传，由用户自行提交（D17）。

## D39 定标场景的基础能力

- **结论**：按 calibration-notes.md 实现定标场景所需的平台能力：实例级仪表身份、Bench 日历（`run.start`）与仪表时钟、虚拟校准台账（`assets`）、万用表可校准的测量通道（隐藏的增益与零点误差、安全码保护的调整命令、计数与日期）、判定规则与基于真值的判定评估。定标场景本身（具体的 DUT 个体、台账条目、验收标准）由产品负责人设计与验收（D11、D24）。
- **只读状态**：校准系数等状态对 SCPI 写入只读，只能由仪表自身的调整命令改变；内置的 `:SYSTem:DATE/TIME` 设置不再被误报为未定义命令。
- **一并修复**：保存测试台文件时，`faults`（预设故障）此前被丢弃，现与 `assets` 一起写回。

## D40 pytest 插件与文件格式迁移

- **pytest 插件**：随包注册（`pytest11` 入口）。`@pytest.mark.bench(路径, clock=, seed=)` 或 `--simubench-bench` / ini 中的 `simubench_bench` 指定测试台；夹具 `visa_rm`（PyVISA 资源管理器，每个测试一台刚上电的测试台）、`instruments`（按实例名或真实地址打开资源，换行结束符）、`bench_session`（推进时间、注入故障等仿真控制）。`--simubench-record-dir` 为每个测试写运行记录，失败时在报告中给出记录路径与回放命令。
- **格式迁移**：每种文件以 `schema` 声明格式与版本；迁移按版本逐级升级解析后的数据，加载时在内存中完成，`simubench migrate [--write]` 改写文件。来自更新版本的文件给出“请升级 SimuBench”的明确诊断（E-FORMAT），而不是难以理解的校验错误。首个迁移：没有 `schema` 行的旧文件视为版本 0。
- **首次使用引导**：首页的“开始使用”卡片给出三种入口（在界面中运行、用 PyVISA 脚本驱动、让 Agent 搭建），关闭后不再显示。

## D41 HiSLIP 接入：synchronized 模式、共用端口、按子地址区分仪表

- **结论**：除 raw socket 外，每台虚拟仪表也以 HiSLIP（IVI-6.1）暴露，NI-VISA、Keysight IO Libraries、pyvisa-py 等客户端不改脚本即可连接 `TCPIP0::127.0.0.1::hislip<i>,<端口>::INSTR`。三条设计约束：
  1. **共用一个端口，按子地址区分仪表**（默认 4880，`--hislip-port 0` 自动分配）：真实仪表各自有 IP、都用 `hislip0`；本机只有一个 IP，用 `hislip0`、`hislip1`…（编号规则与 SOCKET 端口一致）最接近真实情况，另接受 `hislip_<实例名>` 别名。
  2. **只实现 synchronized 模式**（IVI-6.1 3.1）：`InitializeResponse` 一律回复 synchronized，客户端请求 overlapped 也如此，规范允许服务器这样选择。消息边界、设备清除、读 STB、锁（独占/共享，仅在同一仪表的 HiSLIP 会话之间生效）、SRQ 按规范实现；查询被打断按 synchronized 规则丢弃旧响应并回 `Interrupted`/`AsyncInterrupted`。
  3. **不实现加密与凭证认证**：客户端请求 StartTLS 等按规范以 Error 回复。只绑定 127.0.0.1（D38/安全自检同款约束）。
- **理由**：很多现有脚本与 LabVIEW/C# 程序用 HiSLIP 地址；raw socket 以换行结尾，二进制块中的 0x0A 只能靠解析长度，HiSLIP 用 `DataEnd` 标出消息边界，且只有它支持设备清除、读 STB 与 SRQ 这些 IEEE 488.2 语义。
- **实现位置**：`access/hislip_server.py`（服务器）；`Session.clear_output` 提取为 PyVISA 后端与 HiSLIP 服务器共用的设备清除语义；PyVISA 后端地址表加入 HiSLIP 形式（含 Bench 中配置的 HiSLIP 真实地址直接打开），TCPIP INSTR 资源的 VISA 属性（`TCPIP_IS_HISLIP`、`TCPIP_DEVICE_NAME` 等）按 PyVISA 属性表填齐。
- **不做**：overlapped、TLS/认证（HiSLIP 2.0 SC 部分）、`GetDescriptors`、VXI-11、USBTMC、GPIB、监听本机以外地址。NI-VISA 与 Keysight IO Libraries 的手动验证不作为合并条件，见 progress.md 留待进行。

## D42 内置仪表都是真实型号

- **结论**：内置仪表（随软件包发布、出现在元件库、MCP `list_catalog` 与命令行中的仪表）都是按真实型号实现的定义（如 Siglent SDS2104X Plus、Keysight 34465A）。命令行为以该型号的编程手册为准；测量值仍来自电路求解（D13）。规则见 [real-models.md](real-models.md)。
- **`sb-*` 只用于开发验证，不发布**：SimuBench 自造的 `sb-*` 定义放在仓库的 `validation/instruments/`，不进 wheel；测试、验收与开发时通过定义搜索路径加载（工作区的 `instruments/` 目录，或环境变量 `SIMUBENCH_DEFINITIONS`）。用到它们的测试台在 `validation/benches/` 与 `acceptance/benches/`，`examples/` 只放真实型号的测试台。CI 检查 wheel 与 `examples/` 中没有 `sb-*`（issue 35）。
- **理由**：自造型号没有手册可依，脚本在它上面通过不能说明在真机上也通过（D4、D5）；它们的价值是在没有对应真实型号时验证引擎与组件。只被 `sb-*` 使用的组件（锁相、频谱仪、SMU、电子负载、射频源、PRBS）保留在引擎中，供验证与以后的真实型号使用。
- **代价**：在有对应真实型号之前，发布版中没有锁相放大器、频谱仪、SMU、电子负载、射频信号源、万用表等类别。
- **三种实现程度**：手册中的每条命令属于“实现”“接受”（解析并保存，不影响仿真）或“未实现”之一。未实现的命令回复 `-113` 并标注 “not modeled by SimuBench”，不静默接受，避免脚本在虚拟环境通过、在真机失败。
- **按接口契约编写的定义**：没有手册可依、但有既定主机程序的接口契约时（如低频校准工作台，[lowfreq-cal.md](lowfreq-cal.md)），定义按契约编写，不带 `reference`，不进内置仪表库，放在工作区的 `instruments/`（可以在 `examples/` 下的工作区中）。契约要求未知命令不报错时，定义设 `unknown_commands: ignore`：未知命令头不进错误队列、不回复，事件历史记为 `ignored`。真实型号不允许 `ignore`（定义校验拒绝）。主机按 `*IDN?` 校验型号时，型号串由测试台实例的 `idn` 给出，不写死在定义里。
- **可验证**：每个型号有覆盖表（按手册章节列出全部命令及其程度）和手册用例（命令与预期返回，注明手册章节），CI 检查两者与定义一致。
- **首批型号**：Keysight 34465A 与 Fluke 5522A（定标演示）；此后按 D45（Siglent SDS2104X Plus、SDG2042X 替代了原计划的 33500B 与 InfiniiVision 3000T）与 #181 的类别铺开推进，Keithley 2450（#12）在第二波。
- **商标**：`*IDN?` 返回真实厂商与型号，这是脚本不改即可运行（D5）的前提，发布版也如此。只以名称指明所模拟的型号：不使用厂商标志与商业外观，不复制手册原文，文档声明 SimuBench 与各厂商无关联、商标归各自所有者（real-models.md 第 7 节）。

## D43 访问令牌改为可选，默认关闭

- **结论**：`simubench serve` 与 `simubench mcp` 默认不要求访问令牌；`--require-token`（随机生成）或 `--token 值` 开启。只监听本机、Host/Origin 校验、工作区边界等其他防护不变。
- **理由**：令牌是同机威胁模型下的一次性访问凭证，不是登录或识别用户的手段；在工程师自己的电脑上，浏览器页面已由 Host/Origin 校验挡住，令牌带来的主要是“新标签页或重开浏览器后令牌无效”的使用摩擦。
- **代价**：默认时不再防护本机其他用户（他们可以绕过浏览器直接访问 127.0.0.1）。多人共用的电脑上应开启令牌；见 [security.md](security.md)。

## D44 画布在运行时反映信号与活动

- **结论**：运行中的画布展示测试台此刻的状态，而不是静态的拓扑图：
  - 连线按网络电平着色：有信号时以通道色从源向负载流动，0 V 时为灰色；悬停显示网络的直流、有效值与峰值；
  - 示波器节点的通道行带波形缩略图（两个周期）；
  - 仪表收到 SCPI 写入时节点短暂闪烁；
  - 顶栏把“运行中”细分为“等待命令”“执行命令”（命令驱动时钟、步进时钟）与“时钟走动”（墙钟），悬停说明原因与操作。
- **数据**：一个只读接口 `GET /api/sessions/{sid}/levels` 一次返回所有网络的电平与缩略图（与虚拟探针 D37 同一求解），界面在状态变化时重新读取；编辑模式下不显示（预览的测试台可能与运行中的不同）。
- **理由**：命令驱动时钟下，没有命令时虚拟时间不动，原来的画布在“运行中”时没有任何变化，用户分不清是在运行、在等待还是坏了，也看不出信号有没有到达。
- **约束**：动效遵循 `prefers-reduced-motion`；状态同时用文字与颜色表达（ui-design.md 4.2）。

## D45 真实型号：示波器与信号源改用 Siglent

- **结论**：示波器与信号源的首个真实型号改为 Siglent SDS2104X Plus 与 Siglent SDG2042X，替代 D42 中计划的 Keysight InfiniiVision 3000T 与 33500B（产品负责人同意）。Keysight 34465A、Fluke 5522A、Keithley 2450 不变。
- **理由**：D42 要求逐条以编程手册为准，并在 `reference` 中写明版本。Siglent 的 *SDS Series Programming Guide*（EN11F）、*SDG Series Programming Guide*（PG02_E05C）与两份数据手册可从官方站点直接下载；Keysight 两份手册无法从公开渠道直接获取。D4 场景中的 T3DSO2000 同属 Siglent 平台。
- **框架补充**：`builtins` 限定一个型号回答哪些内置命令（SDS 手册只写了 `*IDN`、`*OPC`、`*RST`，没有错误队列，其余一律“未建模”）；返回格式 `enum: as_defined` 按定义原样返回枚举（Siglent 回复 `RISing`、`FMDepth`）；`display.actions.single` 指定面板“单次”在仪表内部执行的命令（SDS 没有 `:SINGle`，用 `:TRIGger:MODE SINGle`；不经过 SCPI，见 D32）；手册用例的 `binary` 步骤按块读取二进制回复。
- **手册没有给出的值**：`*RST` 后的多数设置、存储深度的默认值等，手册没有写；这些值作为 SimuBench 的默认值写入覆盖表的说明，而不是当作手册内容。
- **示波器的开发验证基准改为 Keysight DSO-X 2024A**（#151）：SDS 的手册不给 `*RST` 值、回复格式与多数取值范围，示波器模块的每项能力都要另找依据。InfiniiVision 2000 X-Series *Programmer's Guide*（02.66.0000）给出每条命令的回复格式、`*RST` 示例回复与范围，数据手册 5990-6618EN 给出增益、偏置、时基与输入的指标；两份文件可从公开镜像稳定取得。示波器模块的新能力以 DSO-X 2024A 为验收型号；SDS2104X Plus 保留为第一个产品型号与 Siglent 平台的样本，不再作为新能力的依据。信号源仍是 SDG2042X。

## D46 示波器的噪声与量化（真实型号）

- **结论**：真实型号示波器（首个为 SDS2104X Plus）的每条记录包含输入噪声、触发抖动和 ADC 量化：
  - **输入噪声**：白噪声，均方根值由数据手册的噪声底推得。SDS2000X Plus 只给出“500 MHz 带宽时 80 µV rms”，按白噪声随 √带宽变化，100 MHz 型号取 80 µV × √(100/500) ≈ 35.8 µV（输入端），显示电压中乘以探头衰减比。这是推导值，写在定义的 `specs` 中。
  - **触发抖动**：数据手册的 10 ps rms，作为每次采集的记录时间偏移。
  - **量化**：记录按当前分辨率（8 位每格 30 个码，10 位每格 120 个码）取整后再保存，测量和波形读取看到的都是码。
  - **平均**：`:ACQuire:TYPE AVERage,N` 的噪声为 1/√N，并消耗 N 次采集的时间。
- **确定性**：噪声是种子、仪表、通道与绝对采样序号的纯函数（`engine/noise.py`）：每次采集不同，相同的会话重放逐位一致（architecture.md 2.5）。
- **随档位变化的噪声、ERES、PEAK**（修改，instrument-authoring.md 第 8 节 G4）：原定数据手册没给数值就不建模，结果是大档位上噪声远小于 1 LSB、平均与高分辨率提高不了分辨率，脚本在虚拟环境中得出错误的数值。改为：噪声按档位表给出（V rms 或格 rms），平均、峰值检测与高分辨率在码值上处理；数据手册没给的档位值可以由写型号的人估计，必须在 `specs` 与覆盖表中标为“估计”并写明依据。另一条路是继续不建模，因为错误结论比估计值的误差更有害而不采用。
- **不建模的部分**：信号源（SDG2042X）的数据手册只给出失真与杂散的上限、150 ps 的周期抖动，没有输出噪声底，输出按无噪声处理。`sb-*` 仪表不加噪声（D42 不为虚构型号编造指标）。
- **一并修正**：周期测量在量化记录上把 -0.0 当作负值导致 NaN；PyVISA 后端逐字节读取，大波形块的读取时间与长度的平方成正比；运行记录把无穷大（高阻负载设定）写成 null，重放时测试台无法加载。均已修正并加测试。


## D47 命令时钟的空闲时间：`run.idle` 三档，pytest 默认 `sleep`

- **结论**：Bench 的 `run` 新增 `idle`，表示命令之间空闲的真实时间怎么计入虚拟时间（只对命令驱动时钟有意义；墙钟、步进时钟不读它）：
  - `wall`（默认，即原有行为）：空闲的真实时间计入虚拟时间。交互使用、界面与 `simubench serve` 保持如此，脚本里的等待能“等”出建立时间；
  - `sleep`：空闲不计入；进程内把 `time.sleep(t)` 拦截为虚拟时间恰好推进 `t`、不真的等待。pytest 插件默认此档（环境变量 `SIMUBENCH_IDLE` 与标记参数 `idle=` 可覆盖，与 `SIMUBENCH_CLOCK` 一致）；
  - `off`：空闲完全不推进虚拟时间，只有命令与显式 `advance` 推进。
- **理由**：`wall` 空闲推进让慢机器把命令间的调度延迟算进虚拟时间，同一个测试在不同机器上读到不同的数（issue 4 的 Windows 1508 Ω）。测试要的是可复现：`sleep` 档下结果只由命令、`time.sleep` 和显式推进决定，脚本里的 `sleep(5)` 也不再真的等 5 秒，CI 更快。
- **`sleep` 只在本进程有效**：拦截 `time.sleep` 是进程级补丁，在测试台打开期间生效、最后一个关闭后恢复原函数；进程内同时打开多个 `sleep` 档测试台时，一次被拦截的 `sleep` 推进其中每一个。只拦截 `time.sleep`：`asyncio.sleep`、线程等待与外部进程（SOCKET、HiSLIP 客户端）的等待都不拦截，因此 `simubench serve` 把配置为 `sleep` 的测试台按 `off` 处理。
- **记录与回放**：记录头部写入 `idle`；回放按记录中的设置执行，但 `sleep` 按 `off` 处理（回放的时间由记录驱动，重放环境中不应有补丁改变行为）。
- **用例运行器**：`simubench cases`、MCP `run_cases` 与测试中的用例都在 `idle: off` 的测试台上运行（不论测试台文件的设置）：用例的结果只由它的命令决定。测试台文件不写 `idle` 时为 `wall`，慢的 CI 机器上空闲时间推进虚拟时间，带噪声的读数随之变化（main 上 Windows 的 SDS 校准契约用例读到 -10.4 V）。
- **代价**：同一个测试台在 `sleep` 档下，靠“命令间空等”建立的时序不再出现——测试需要建立时间时应写 `time.sleep(t)`（会精确推进）或显式 `advance`。依赖旧行为的测试显式标注 `idle="wall"`。

## D48 幅度的多单位：范围按 Vpp 检查，切单位换算数值

- **结论**：信号源的幅度状态仍以当前单位存值；范围由 `amplitude_level` 的 `vpp_min` / `vpp_max`（负载设定下的 Vpp）检查，任一单位写入先换算到 Vpp 再比较，越界报 -222；改波形或负载设定导致越界报 -221 并拒绝。切换单位时把数值换算到新单位，物理输出不变（Rigol / Keysight 的 `VOLT:UNIT` 行为）。
- **理由**：真机只有一个物理上限（输出级在负载设定下的 Vpp），Vrms 与 dBm 的范围由它随波形和负载推出，不是独立约束；按单位各写一对静态范围，换波形或负载后就错了。SDG 的 `AMP` / `AMPVRMS` / `AMPDBM` 独立关键字与单位开关都能落在这一语义上。
- **影响**：模板 `signal_source` 的 `amplitude.min/max` 改为 Vpp 口径；含 dBm 时最小幅度必须大于 0；多单位的幅度状态不再有静态范围。

## D49 通用组件按真实仪表的功能块建模：粒度与命名

- **结论**：内置型号的内部组件及其连线对应该仪表真实框图的主要功能块；组件命名与参数用仪表工程师认知中的真实功能块（NPLC、CV/CC 交叉、中频带宽、扫描表），不按软件抽象。本条分两部分，适用范围不同：
  1. **粒度**——覆盖全部内置型号（含已有）。依据为厂商的工作原理章节、维修手册或数据手册框图；没有公开框图的，用该类别公认的架构并注明来源（[component-map.md](component-map.md) 逐类别登记）。反向约束：不允许装饰性的块——每个组件必须带参与仿真的参数或行为。
  2. **命名与存在性**——只约束新组件；已有组件在 component-map.md 的债务列审计（如 `specan` 的 `mixer_limit`、`maxhold_limit` 已偏软件命名，拆分时更名）。
- **可检查**：[docs/blocks/](blocks/)`<class>.yaml` 每类别列出功能块与可覆盖它的组件类型（一块可接受多类型；尚不存在的组件类型允许入清单，测试只对内置定义生效）；`tests/test_block_coverage.py` 检查内置定义的组件（含通道组件）覆盖每一块。已有型号的缺口进该测试的 `EXEMPT` 例外清单，与 `test_model_components.py` 的 `ALLOWED` 同规则——只能缩短。不用组件数量作标准，否则会鼓励凑装饰块。
- **理由**：D3 第 2 层要求用数据手册的语言填写参数，D3 第 3 层的组件图要求能看出真实结构；定义写在整块上，以后拆分要连同定义一起重写。备选是按软件抽象建模、允许大整块组件，不采用。
- **执行**：类别铺开（#181）的每个拆分 issue 按 component-map.md 的框图与求解层级落地——**拆分前先定每块的求解层级**（进电路求解还是设置/数据层），先录金标准（#94 方法），行为不变。

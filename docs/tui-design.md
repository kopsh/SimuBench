# 终端控制台（TUI）设计

状态：草案，待产品负责人确认。确认后在 decisions.md 中补一条决定（见第 10 节），并按第 9 节拆成 `核心` issue。

参考：EdgeSim 的终端仪表控制台（Galois Labs，*Terminal instrument console*，`edgesim tui`，Textual 实现）。本文只借鉴它“在终端里看着测试台、动手操作、与脚本共用同一个世界”的形态，概念与术语一律按 SimuBench（[glossary.md](glossary.md)）。

## 1. 定位

D18 定下“第一个界面是 Web Bench，TUI 以后作为补充”；architecture.md 8.1 比较过两者。TUI 不是第二个 Web Bench，而是**在终端里观察和操作运行中的测试台**：

| 场景 | 为什么用 TUI |
| --- | --- |
| 远程服务器、实验室工控机、CI 机器上调试 | 只有 SSH，没有浏览器，也不想做端口转发 |
| 一边在终端跑脚本 / pytest，一边看仪表状态 | 与脚本在同一个终端窗口里分屏（tmux），不切到浏览器 |
| 快速确认“测试台在不在跑、信号到没到、哪台仪表报错” | 启动快、全键盘、信息密度高 |
| 文档与 CI 中可复现的截图 | 同一测试台 + 同一操作脚本 → 逐字节相同的 SVG |

**做**：测试台总览、仪表面板与屏幕、网络电平与探针、通信记录、故障注入、时钟控制、运行记录列表。

**不做**（交给 Web Bench，TUI 中给出“在浏览器中打开”的链接）：画布编辑与连线、版本历史与差异审阅、仪表定义编辑、仪表内部组件图、波形的精细测量（光标、缩放）。TUI 能看波形的大概，不替代示波器屏幕。

## 2. 架构：TUI 是服务的一个客户端

```
              ┌──────────────── simubench serve（或 mcp）────────────────┐
 PyVISA 脚本 ─┤ SCPI 网络仪表 / HiSLIP                                    │
 pytest      ─┤                                                          │
 Agent (MCP) ─┤ MCP          引擎：会话、动作队列、运行记录（D9 并发串行） │
 浏览器      ─┤ HTTP + WebSocket ──┐                                      │
 TUI         ─┤ HTTP + WebSocket ──┘  同一套 /api 接口（D7、D21）          │
              └──────────────────────────────────────────────────────────┘
```

- **只走 HTTP/WebSocket 接口**，与 Web Bench 用同一批端点（`/api/sessions/...`、`/levels`、`/screen`、`/panel`、`/faults`、`/clock`、WebSocket `events`），不直接调用引擎。理由：
  1. 远程状态（D32、#121）、令牌（D43）、Host/Origin 校验、危险确认的语义与 Web 完全一致，不需要第二份实现；
  2. 同一个会话可被脚本、Web、Agent、TUI 同时观察（D9），TUI 只是又一个观察者；
  3. 接口模型是 Python 中的 Pydantic（D21 单一来源），TUI 直接复用 `simubench.models.api`，不需要生成客户端，接口改动由类型检查与测试发现。
- **两种启动方式**，内部是同一条路径：
  - `simubench tui <bench.yaml>`：在本进程后台线程中启动服务（只监听 127.0.0.1、端口自动分配，与 `simubench serve` 相同的参数：`--hislip-port`、`--idle` 等），打开会话并连上它；退出 TUI 即关闭服务。SCPI 端口照常监听，另一个终端的脚本可以直接连。
  - `simubench tui --attach [http://127.0.0.1:8000] [--session <sid>]`：连接已运行的 `serve` / `mcp` 服务；有多个会话时先让用户选。
- **来源标记**：TUI 发出的操作在运行记录与事件中标为来源“终端”（与“界面”“Agent”并列），回放与审阅时能分辨是谁动的手。现在服务端把 HTTP 接口的操作一律记为 `client="ui"`（`server/manager.py`），需要让请求带上客户端类型（例如请求头 `X-SimuBench-Client: tui`，缺省仍为 `ui`），这是接口改动，走 schema 生成。
- **接口补充**：示波器屏幕（`/screen`）现在固定返回 400 点，TUI 需要按终端点阵宽度请求（增加可选的 `points` 参数，Web 也可用它按画布宽度取点）；`/levels`、`/nets/{net}/waveform` 已有点数参数。除这两处外不需要新端点。
- **技术栈**：[Textual](https://textual.textualize.io/)（Python，Windows Terminal 与 Linux 终端都可用，支持鼠标、CJK 双宽字符、SVG 截图、无头测试 `Pilot`）。作为可选依赖 `simubench[tui]`（与 `simubench[mcp]` 一致），不进入核心依赖；未安装时 `simubench tui` 提示安装命令。HTTP 用 `httpx`，WebSocket 用 `websockets`（`uvicorn[standard]` 已带）。

## 3. 界面结构

所有屏幕共用顶栏与底栏：

```
┌ SimuBench · siglent_scope_rc ─────────── ● 等待命令  命令时钟  t = 00:00:04.200 ─┐   顶栏
│                                                                               │
│                         当前屏幕（总览 / 仪表 / 网络 / 通信 …）                  │
│                                                                               │
└ n 网络  l 通信  f 故障  a 推进  ? 帮助  q 退出 ─────────── 远程：scope ← 1 个客户端 ┘  底栏
```

- **顶栏**：测试台名称、运行状态（D44 的“等待命令 / 执行命令 / 时钟走动”，文字 + 颜色）、时钟模式、虚拟时间；断开时显示“已断开，只读，正在重连”。
- **底栏**：当前屏幕可用的按键（随焦点变化，Textual `Footer`）；右侧显示远程状态（哪台仪表被哪个客户端占用，D32）。

### 3.1 总览（启动后的首屏）

```
┌ scope · SDS2104X Plus ───────┐┌ awg · SDG2042X ──────────────┐┌ rc · RC 低通 · DUT ──────┐
│ CH1 ● 200 mV/div  ⣀⡠⠔⠊⠉⠑⠢⢄  ││ CH1 ● 开  正弦 1 kHz 1 Vpp   ││ in ← awg.CH1  1.00 Vpp   │
│ CH2 ○                        ││ CH2 ○ 关                     ││ out → scope.CH1 0.71 Vpp │
│ 触发 自动 · 运行              ││ 负载 50 Ω                    ││ R 1 kΩ · C 100 nF        │
│ 错误 0                        ││ 错误 0                        ││                          │
└──────────────────────────────┘└──────────────────────────────┘└──────────────────────────┘
┌ 通信 ─────────────────────────────────────────────────────────────────────────────────┐
│ 00:00:04.200  scope  →  :WAVeform:DATA?                                               │
│ 00:00:04.201  scope  ←  #9000002000…  2011 B                                          │
└───────────────────────────────────────────────────────────────────────────────────────┘
```

- 每台仪表与元件一张卡片，按测试台文件的顺序、自适应列数排列。卡片内容由**与 Web 相同的数据**生成：仪表的通道摘要、输出开关、错误队列计数（`GET /instruments/{name}`）；示波器通道行带盲文字符缩略图（`/levels` 的 `wave`，D44）；元件显示端口所连网络与电平。DUT 带标记。
- 卡片边框颜色只表达状态：正常为中性色，有错误、跳闸、过载时为红色并在卡片内写出原因（ui-design.md 4.2：始终同时有文字）。
- 下方是最近的通信记录（可用 `l` 展开为全屏）。

### 3.2 仪表屏幕（Enter 打开）

按仪表的面板生成，与 Web 共用 `library/panels.py` 的 `effective_panel`（类别模板 + 通用布局，D1）：

- **读数**（D32 只读读数接口，不产生通信记录、不推进时间）：大号等宽数字 + 单位，按仪表分辨率取有效位；
- **控件**：开关、枚举、数值；Enter / `e` 编辑，`+` `-` 按步进调整，Space 切换开关；经 `POST /configure`，被远程占用时提示并提供“本地（LOCAL）”（D32）；
- **面板操作**：运行 / 停止 / 单次等软键（`display.actions`，`POST /panel`）；
- **SCPI 控制台**：`:` 打开单行输入，查询结果就地显示（`POST /scpi`，与 Web 控制台相同，不取走脚本的回复）；
- **危险操作**：打开输出等需二次确认的命令弹出确认框，写明命令、仪表与影响（ui-design.md 第 5 节）。

#### 示波器、频谱仪等屏幕

用盲文字符（每个字符 2×4 点）画迹线：80 列终端约 160×(行数×4) 点。与 Web 一样只取屏幕需要的点数（architecture.md 8.3），TUI 请求时传入**点阵宽度**（第 2 节的 `points` 参数），不接收全部采样。通道颜色与 Web 相同（CH1 黄、CH2 青、CH3 品红、CH4 蓝）；终端不支持真彩色时退回 16 色并在图例中写通道名。屏幕下方列出档位、触发与自动测量。`r` 运行 / 停止，`s` 单次，与面板操作相同。

### 3.3 网络（`n`）

左侧是网络列表（名称、驱动端、直流 / 有效值 / 峰值、是否有信号，来自 `/levels`）；右侧是所选网络的波形（`/nets/{net}/waveform`）与探针结果。`w` 切换波形，`?` 请求“为什么是这个值”（D37 因果解释；0 V 时沿电路向上游追溯原因，`engine/silence.py`）。Enter 跳到驱动这条网络的仪表屏幕。

### 3.4 通信（`l`）

全屏通信记录：时间（虚拟 / 真实可切换）、仪表、方向、命令或回复、字节数、来源。`/` 过滤（按仪表、文字、只看错误），二进制块显示摘要，Enter 展开十六进制。WebSocket 事件流增量追加；超过一定条数只保留可见窗口附近的行（与 Web 的虚拟列表一致）。

### 3.5 故障（`f`）

在当前仪表或网络上注入故障：先选类型（超时、断连、乱码、延迟、忙、错误码、保护跳闸、参数漂移，D27），再填参数与持续时间；列出生效中的故障，可撤销。经 `/faults` 接口，写入运行记录。

### 3.6 运行记录（`R`）

列出 `/api/runs`，显示时间、测试台、命令数、结果；Enter 查看摘要，`p` 回放并报告第一处不同（`/runs/{id}/replay`）。时间线与逐条对比留在 Web。

## 4. 按键

| 范围 | 按键 |
| --- | --- |
| 任意屏幕 | `n` 网络 · `l` 通信 · `f` 故障 · `R` 运行记录 · `a` 推进虚拟时钟（步进时钟下按设定步长；命令时钟下弹出时长输入） · `Ctrl+P` 命令面板 · `?` 帮助 · `Esc` 返回 · `q` 退出 |
| 总览 | 方向键 / Tab 在卡片间移动 · `1`–`9` 跳到第 n 张卡片 · Enter 打开 · Space 切换所选仪表的主输出（需确认） |
| 仪表屏幕 | Tab / 方向键在控件间移动 · Enter / `e` 编辑 · `+` `-` 步进 · Space 切换 · `:` SCPI 控制台 · `L` 本地（从脚本接管） |
| 示波器 / 频谱仪 | `r` 运行 / 停止 · `s` 单次 · `c` 切换显示的通道 |
| 网络 | ↑↓ 选择 · Enter 打开驱动端 · `w` 波形 · `?` 为什么是这个值 |

- 键位以 EdgeSim 控制台为参照，使从那边过来的用户不用重新学；与 Web Bench 的快捷键冲突时以 Web 为准（例如命令面板）。
- 所有操作都能通过命令面板搜索执行；鼠标可用但不是必需。

## 5. 视觉与文案

- **配色**：以终端默认前景 / 背景为底的单色界面；颜色只用于通道（与 Web 相同）与状态（绿 / 琥珀 / 红 / 灰）；仿真专属信息（真实值、保真度标注 ≈）用紫色。浅色与深色终端都可读；`NO_COLOR` 环境变量下完全不用颜色，状态全靠文字。
- **数值**：工程单位与 SI 前缀，数字右对齐、等宽（终端天然等宽），与 Web 相同的格式化函数（服务端 `_eng` 一类的实现抽到共用模块）。
- **语言**：中文为主、英文为辅（D23），`--lang zh|en`，默认跟随 `LANG`。术语按 glossary.md。文本外置在 Python 侧的 `tui/i18n` 中；与 Web 重复的词条（状态、按钮、错误提示）以 `web/src/i18n` 为准，由检查脚本比对，避免两边措辞漂移。
- **宽度**：最小 80×24；更窄时提示放大窗口，不做挤压布局。CJK 字符按双宽计算（Textual 内置）。

## 6. 可复现截图

`simubench tui <bench.yaml> --screenshot <steps.yaml> --out <dir>`：无头运行，按步骤文件执行按键与等待（“按 `n`”“等待虚拟时间 10 ms”“截图 overview”），每个截图输出一张 SVG。

- 使用 `idle: off` 与固定种子（D47），虚拟时间只由步骤推进，同一测试台 + 同一步骤 → 逐字节相同的 SVG；
- 文档中的 TUI 截图由它生成，CI 重新生成并比较（与 Web 的视觉回归同理）；
- 截图只是某一时刻的画面，不是测试结果——判定以运行记录为准（D36）。

## 7. 状态与错误

与 Web 的“完整的状态”要求一致（roadmap.md 界面质量标准）：

| 状态 | 表现 |
| --- | --- |
| 连接中 / 加载 | 顶栏“正在连接 …”，屏幕显示占位而不是空白 |
| 服务断开 | 顶栏红色“已断开”，界面只读，后台按退避重连，恢复后重新拉取状态并补齐事件（WebSocket 的 backlog） |
| 令牌无效 | 提示 `--token` 或 `SIMUBENCH_TOKEN`，不反复重试 |
| 会话不存在 / 被关闭 | 回到会话选择，说明原因 |
| 仪表被远程占用 | 控件只读，底栏写明占用的客户端，`L` 接管（D32） |
| 测试台文件被修改（D25） | 顶栏提示“文件已改，可重建”，重建需确认（有脚本连着时会断开它们） |
| 测试台无法构建 | 列出校验诊断（错误码、位置、建议），提示在 Web 或编辑器中修改 |

## 8. 测试

- **单元与交互**：Textual `Pilot` 驱动，服务端用测试中的 FastAPI 应用（与现有 `tests` 的方式相同）；覆盖每个屏幕的按键路径、远程状态、断线重连、危险确认。
- **快照**：`pytest-textual-snapshot` 对每个屏幕在中英文、80 列与 120 列下各一张 SVG 快照，进入 PR 的快速检查（纯 Python，Ubuntu 上运行）。
- **跨平台**：Windows 上的 TUI 测试随 `main` 上的 Windows 任务运行（D20）。
- **端到端**：一个 PyVISA 脚本驱动信号源，TUI 中的读数随之变化（博客中“脚本与控制台并排”的场景），验证 TUI 与脚本共用同一会话。
- `scripts/check.sh` 增加 i18n 词条比对。

## 10. 待确认（确认后写入 decisions.md）

1. **TUI 只通过 HTTP/WebSocket 接口访问引擎**（第 2 节）。另一条路是进程内直接调用引擎（少一层、启动更快），但远程状态、确认与来源标记要再实现一遍，且无法与 Web / 脚本共用会话。建议前者。
2. **Textual 作为可选依赖 `simubench[tui]`**。替代方案：urwid、prompt_toolkit（更底层，截图与无头测试要自己做），或 Rust 的 ratatui（与 D19 的 Python 起步不符）。建议 Textual。
3. **TUI 的范围**：只观察与操作运行中的测试台，不做编辑（第 1 节）。是否需要在 TUI 中做最基本的编辑（例如改一个元件参数）？建议不做，保持“文件是唯一来源”（D25）只有画布、MCP 与编辑器三个入口。
4. **事件来源增加“终端”**（请求头 `X-SimuBench-Client`）：会改变接口与运行记录的 schema（D21 生成物）。是否接受，还是 TUI 沿用“界面”？建议增加，审阅运行记录时能分辨操作来自哪里。
5. **D18 / architecture.md 8.1 的更新**：确认后把“TUI 以后作为补充”改为指向本文。

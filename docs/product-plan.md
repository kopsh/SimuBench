# 产品规划：从“看得见”到“能验证”

状态：草案（2026-11-12），供产品负责人确认后拆成 issue。它不替代 [positioning-review.md](positioning-review.md)（定位与缺口）与
[signal-chain.md](signal-chain.md)（信号链的技术方案与 S1–S15），只回答一个问题：**接下来按什么顺序做，每一步交给谁，做到什么算完。**

## 0. 目标与现状

目标（定位复盘第 1 节的第二个场景）：

> 硬件样机还没出来，上位机、驱动和校准程序就能对着一台“行为对”的虚拟仪表开发，连内部信号链的算法和架构也能先验证。

| 半句 | 现状 | 差什么 |
| --- | --- | --- |
| 对着虚拟仪表开发下游软件 | 平台能力齐（按手册生成定义、验收页、用例、校准测试台，样板 `examples/lowfreq-cal/`） | 没有一台自研仪表；用例不能对真机运行；非 Python 上位机未实测；服务只监听本机；试点未开始 |
| 验证内部信号链的算法和架构 | 信号链第一版 15 项完成 8 项（S1–S8）：示波器经采样流采集，内部探针与界面可看每一级的信号 | 第一版余下 7 项（S9–S15）；算法托管、金标准比对、定点、链路预算未开始，且按定位复盘 8.5 等 A0 访谈后才做 |

两半都卡在同一件事上：**一台试点的在研仪表和使用它的工程师**。这件事 agent 做不了。本规划因此分两类工作：

- **只有产品负责人能做的**（第 1 节）：三项确认、试点、可用性验证、A0 访谈。
- **agent 现在就能做的**（第 2–5 节）：把试点到来之前能准备的全部准备好，使试点开始后的每一处卡顿都是真实的领域问题，而不是平台缺一个入口。

## 2. P1 闭环：下游软件对着虚拟仪表开发（现在可做）

定位复盘 4.3 的缺口 2–4 与问题一（正确性没有外部锚点）。不依赖试点。

| 编号 | 内容 | 标签 | 依赖 | 完成条件 |
| --- | --- | --- | --- | --- |
| P1-1 | **用例对真实资源地址运行**：`simubench cases <文件> --resource <VISA 地址>`，不上电测试台，把同一份用例的 `send`/`query` 发给该地址，用同一套 `expect` 规则判定，输出与现有相同的结果与 JUnit XML；差异报告逐条列出命令、期望、实得 | 核心 | — | 测试里起两个本机服务：一个按原定义，一个按故意改错三处回复的定义；对后者运行，恰好报出这三处；对前者全部通过。用例文件格式不变。`docs/instrument-authoring.md` 的用例一节补用法 |
| P1-2 | **真机录制与对照**：`simubench record --resource <地址> <用例文件>` 把真机的回复存成文件；`simubench cases --against <录制文件>` 离线对照。录制文件纳入仓库后，CI 里对照不需要真机 | 核心 | P1-1 | 对 P1-1 的“改错的服务”录制，再离线对照，差异与在线相同；数值回复按用例已有的容差规则比较；格式记入 architecture.md，属于文件格式，写一条决策 |
| P1-3 | **非 Python 上位机实测**：仓库加入 C#（.NET）与 C++ 两个最小客户端（raw socket 各一，HiSLIP 至少一个），在 CI 里对示例测试台发一组命令并核对回复；另写一页“在 Windows 上用 NI-VISA / Keysight IO Libraries 连接”的操作清单，留给 H2 的工程师照做并回填结果 | 核心（客户端与 CI）；可认领（操作清单） | — | CI 新增一个作业，两个客户端通过；清单在 `docs/` 下，步骤可逐条照做，末尾有“实测记录”表（空着等回填，不由 agent 填） |
| P1-4 | **组内共用**：`serve --host <地址>` 显式开启监听非本机；不带令牌拒绝启动；`docs/security.md` 更新威胁与自检 | 核心 | — | 默认仍只监听本机；`--host 0.0.0.0` 无 `--token` 时报错退出；安全模型变化，改 decisions.md 的对应条目（不新增条目） |
| P1-5 | **非 SCPI 入口**（串口、Modbus、私有协议） | 核心 | **H2 确认需要** | 未确认前不做。确认后先写设计（哪一种、帧格式在定义里怎么声明），再拆 issue |
| P1-6 | **一页使用说明**：面向工程师，从“我有一份命令手册草稿”到“我的上位机连上了”，每步一条命令或一张截图 | 可认领 | P1-1 | 一页以内；每条命令由 `tests/test_docs_examples.py` 运行 |

顺序：P1-1 最先（工作量小、价值最高，定位复盘 4.3）；P1-3、P1-4 与它并行；P1-2 在 P1-1 之后。

## 7. 交给 agent 时的规则

- 一行一个 issue；标题写用户可见的变化；正文抄“内容”与“完成条件”两栏，并写明依赖的 issue 编号。标签按上表（`核心` 只由主 agent 做，`可认领` 任何 agent 可认领，见 AGENTS.md）。
- 第 2–4 节的每个 issue 都必须能在没有 H1–H6 的情况下完成并验收；做不到的，说明卡在哪个 H 上，不要用假设的数据补。
- “实测记录”“卡点记录”“验证清单”这三类内容只记录真实发生的事：agent 不替工程师填实测结果，不替算法工程师写验证需求。
- 每完成一项，在 progress-log.md 末尾追加自检表；本文只在一个阶段整体完成或顺序变化时修改。

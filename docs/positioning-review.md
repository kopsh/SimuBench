# 定位复盘与后续规划

状态：草案，供后续规划参考（2026-11-11）。本文是一次对现状的评估与由此得出的规划建议，不是决策记录；
其中与 [decisions.md](decisions.md) 不一致的地方列在第 6 节，待产品负责人确认后再改对应条目。

## 1. 定位

SimuBench 是**内部仪表仿真工具**，不是商业化产品。它解决两件事：

1. **仪表短缺**：内部工程师在研发过程中拿不到或排不上真实仪表时，用虚拟仪表开发和调试测试程序。
2. **自研仪表的仿真**：公司研发自己的测试测量仪表时，在硬件样机就绪之前，为上位机、驱动、校准程序和测试脚本提供一台“行为对”的虚拟仪表。

由此不再属于目标的内容：授权与计费、对外发布、对外的商标与法务处理、安装包与对外分发、公有云形态。

## 2. 现状评估

评估依据：`docs/` 下的设计文档、代码、各型号的覆盖表，以及在 Keysight 34465A 定义上实际执行的一组常用命令。

### 2.1 已经具备的

| 能力 | 说明 |
| --- | --- |
| 拒绝而不猜 | 未建模的命令报 `-113`，不返回看似合理的假数据 |
| 确定与回放 | 同种子、同命令序列结果一致；运行记录可回放并定位第一处不同 |
| 读数来自电路求解 | 例：分压器被万用表 10 MΩ 输入阻抗加载，读数 0.0991 V 而非理想的 0.1 V |
| 接入方式 | PyVISA 后端、raw socket、HiSLIP、VXI-11；进程内约 1500 次 `READ?`/秒 |
| 定标闭环 | 34465A 的解锁、调整、存储、计数已实现；真值已知，可判定脚本的结论（`examples/demo/`） |
| 自定义仪表 | 声明式定义、Agent 经 MCP 生成、Web 验收页、用例运行（`examples/lowfreq-cal/` 是完整样板） |

### 2.2 主要问题

**问题一：正确性没有外部锚点。**

- 型号定义按厂商手册编写，用例出自同一份手册、由同一批 agent 编写。测试通过说明“实现与对手册的理解一致”，不说明“与真机一致”。
- 仓库中没有真机录制数据的对比，也没有用 NI-VISA、Keysight IO Libraries 或 LabVIEW 实测的记录。
- D4 的衡量标准（虚拟环境通过的脚本上产线后出问题的比例）从未测量。
- D11 由产品负责人验收定标场景，D24 取消了中间评审，PR 过 CI 即合并；产品负责人不是仪表领域的人，领域把关实际缺位。
- M1、M2 的可用性验证（5 位内部工程师）至今为“待安排”。

**问题二：型号铺得宽，每台做得浅。**

27 个真实型号的覆盖表共约 9000 条手册命令，标为“实现”的约 1400 条（约 16%）。

| 型号 | 手册命令数 | 已实现 |
| --- | --- | --- |
| Siglent SDG2042X | 193 | 7（4%） |
| Keysight N9042B | 1309 | 64（5%） |
| Keysight DAQ970A | 437 | 47（10%） |
| Keysight 34465A | 239 | 69（28%） |
| B&K 8614（最高） | 116 | 49（42%） |

34465A 上的实测：直流/交流电压、电流、电阻、触发、读数缓冲正常；频率、温度、电容、通断/二极管、
统计（`CALC:AVER`）、限值、NULL、`STAT:OPER`、`FORM:DATA REAL` 报错。真实的测试程序很可能在前几十行撞上 `-113`。

**问题三：验证场景与真实需求脱节。**

- D4 点名的场景是定标脚本驱动 UTG9604T 与 T3DSO2000，这两个型号不在库中。
- D10 用 EdgeSim 的公开指南作为验证场景，数值对齐它的输出；型号选择没有来自内部的紧缺清单。
- 同时维护 Web、TUI、MCP、AI 助手与四种协议，投入分散。

**问题四：模型边界。**

- 求解器是频域稳态线性网络加工作点迭代，没有瞬态；这是合理取舍，但需要让使用者知道。
- 测试台元件只有电阻、RC 低通、探头、线缆、缓冲器；真实 DUT（电路板、电源模块）需要写 Python 插件。
- 非 SCPI 设备（串口、Modbus、私有协议）没有入口；GPIB/USB 地址只在 PyVISA 后端中有效。
- 仿真的是仪表**对外的行为**，不是仪表内部的 FPGA/DSP 算法。

## 3. 场景一：仪表短缺

做法：按内部真实的紧缺情况选型号，做深而不是做多。

- 向内部工程师收集紧缺清单（哪些仪表排队最久）与他们现成的脚本。
- 只对清单上的 2–3 个型号继续投入，目标是真实脚本原样跑通；其余型号停止扩展。
- 每个做深的型号借一台真机对照一次（见 5.2）。

## 4. 场景二：自研仪表

### 4.1 谁用、解决什么

共同痛点：硬件样机来得晚、数量少、不稳定，下游工作都在等它。虚拟仪表是**命令手册的可执行版本**。

| 角色 | 在等什么 | 仿真提供什么 |
| --- | --- | --- |
| 固件/协议工程师 | 命令集定稿 | 命令手册草稿变成能连上的虚拟仪表，评审时直接试 |
| 上位机/驱动工程师 | 能通信的样机 | 硬件就绪前开发 PC 软件、驱动、示例程序 |
| 校准/产线软件工程师 | 样机与标准器（贵、要排队） | 虚拟被校仪表 + 虚拟标准器，反复跑完整校准流程，含超差、调整失败等异常路径 |
| 测试工程师 | 样机 | 自动化测试脚本先写好，样机到了直接跑 |

### 4.2 使用流程

1. 协议工程师给出命令手册草稿：命令、参数范围、回复格式、错误码。
2. Agent 经 MCP 按手册生成仪表定义（D3），定义的 `reference` 填自己的手册。
3. 在 Web 验收页确认：命令清单、内部结构、试发命令。
4. 把手册中的示例写成用例文件（`cases.yaml`），`simubench cases` 运行。
5. 下游接入：上位机与校准程序只换资源地址；校准场景配上虚拟的校准源或标准表（5522A、5730A、8588A）搭成测试台。
6. 样机到货后，同一份用例对真机运行。不一致处要么是固件缺陷，要么是定义写错。
7. 固件改版时定义随之修改，用例在 CI 中回归。

样板：`examples/lowfreq-cal/`（第 2–5 步，两台按接口契约写的自定义仪表，主机程序不改源码）；
`examples/demo/calibrate_34465a.py`（校准流程与真值判定）。

### 4.3 缺口

按对本场景的影响排序：

1. **库中没有任何一台自研仪表。** 平台能力是用别家型号验证的；自家命令集中可能有平台表达不了的内容，只有做一台才知道。
2. **用例不能对真机运行。** 第 6 步需要“对真实资源地址执行同一份用例”的入口。工作量小，价值最高。
3. **非 Python 上位机未实测。** C#、C++、LabVIEW 经 NI-VISA 走 socket 或 HiSLIP 理论可行，没有实测记录；串口、Modbus、私有协议没有入口。
4. **服务只监听本机。** 每人本机运行没有问题；一个组共用一台虚拟测试台做不到。是否需要取决于内部的工作方式。
5. **仪表内部算法的仿真不在范围内。** 若需求包含 FPGA/DSP 算法仿真，那是另一类工具，需先确认。

## 5. 推进顺序

### 5.1 先确认三件事

- 在研的是哪台仪表，命令手册在谁手里；
- 上位机与校准程序用什么语言、什么 VISA、什么总线；
- 哪些仪表最紧缺、排队最久。

### 5.2 步骤

| 顺序 | 内容 | 完成的标志 |
| --- | --- | --- |
| 1 | 完成 5.1 的三项确认 | 有一份紧缺清单、一台试点仪表及其手册、下游工具链的清单 |
| 2 | 试点：一台在研仪表（命令集有草稿、硬件未到），按 4.2 生成定义，由它的上位机或校准工程师实际使用两周 | 记录了平台卡住的地方；下游程序不改代码能连上 |
| 3 | 短缺替代收窄到紧缺清单上的 2–3 个型号并做深 | 内部工程师的现成脚本原样跑通 |
| 4 | 实现“用例对真机运行” | 试点仪表的样机与一台短缺型号的真机各对照一次，差异有记录 |
| 5 | 写一页面向工程师的使用说明，推广到第二台仪表 | 第二台仪表由其团队自行完成 4.2 |

试点仪表的工程师同时承担领域验收：他们是 D11 所需的“熟悉业务的人”。

### 5.3 暂停的投入

在第 2、3 步有结果之前，不再增加新的仪表型号与新的界面功能。

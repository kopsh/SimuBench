# 定位复盘与后续规划

状态：定位已由产品负责人确认（2026-11-11），已同步到 [decisions.md](decisions.md)（第 6 节）；第 3–5 节的规划是建议，供后续规划参考。

## 1. 定位

SimuBench 是**内部仪表仿真工具**，不是商业化产品。它解决两件事：

1. **仪表短缺**：内部工程师在研发过程中拿不到或排不上真实仪表时，用虚拟仪表开发和调试测试程序。
2. **自研仪表的仿真**：公司研发自己的测试测量仪表时，在硬件样机就绪之前，为上位机、驱动、校准程序和测试脚本提供一台“行为对”的虚拟仪表；并用于**验证仪表内部的算法与架构**（信号链级，产品负责人 2026-11-11 确认，规划见第 8 节）。

由此不再属于目标的内容：授权与计费、对外发布、对外的商标与法务处理、安装包与对外分发、公有云形态。

## 2. 现状评估

评估依据：`docs/` 下的设计文档、代码、各型号的覆盖表，以及在 Keysight 34465A 定义上实际执行的一组常用命令。

### 2.1 已经具备的

| 能力 | 说明 |
| --- | --- |
| 拒绝而不猜 | 未建模的命令报 `-113`，不返回看似合理的假数据 |
| 确定与回放 | 同种子、同命令序列结果一致；运行记录可回放并定位第一处不同 |
| 读数来自电路求解 | 例：分压器被万用表 10 MΩ 输入阻抗加载，读数 0.0991 V 而非理想的 0.1 V |
| 接入方式 | PyVISA 后端、raw socket、HiSLIP、VXI-11；进程内约 1500 次 `READ?`/秒 |
| 定标闭环 | 34465A 的解锁、调整、存储、计数已实现；真值已知，可判定脚本的结论（`examples/demo/`） |
| 自定义仪表 | 声明式定义、Agent 经 MCP 生成、Web 验收页、用例运行（`examples/lowfreq-cal/` 是完整样板） |

### 2.2 主要问题

**问题一：正确性没有外部锚点。**

- 型号定义按厂商手册编写，用例出自同一份手册、由同一批 agent 编写。测试通过说明“实现与对手册的理解一致”，不说明“与真机一致”。
- 仓库中没有真机录制数据的对比，也没有用 NI-VISA、Keysight IO Libraries 或 LabVIEW 实测的记录。
- D4 的衡量标准（虚拟环境通过的脚本上产线后出问题的比例）从未测量。
- D11 由产品负责人验收定标场景，D24 取消了中间评审，PR 过 CI 即合并；产品负责人不是仪表领域的人，领域把关实际缺位。
- M1、M2 的可用性验证（5 位内部工程师）至今为“待安排”。

**问题二：型号铺得宽，每台做得浅。**

27 个真实型号的覆盖表共约 9000 条手册命令，标为“实现”的约 1400 条（约 16%）。

| 型号 | 手册命令数 | 已实现 |
| --- | --- | --- |
| Siglent SDG2042X | 193 | 7（4%） |
| Keysight N9042B | 1309 | 64（5%） |
| Keysight DAQ970A | 437 | 47（10%） |
| Keysight 34465A | 239 | 69（28%） |
| B&K 8614（最高） | 116 | 49（42%） |

34465A 上的实测：直流/交流电压、电流、电阻、触发、读数缓冲正常；频率、温度、电容、通断/二极管、
统计（`CALC:AVER`）、限值、NULL、`STAT:OPER`、`FORM:DATA REAL` 报错。真实的测试程序很可能在前几十行撞上 `-113`。

**问题三：验证场景与真实需求脱节。**

- D4 点名的场景是定标脚本驱动 UTG9604T 与 T3DSO2000，这两个型号不在库中。
- D10 用 EdgeSim 的公开指南作为验证场景，数值对齐它的输出；型号选择没有来自内部的紧缺清单。
- 同时维护 Web、TUI、MCP、AI 助手与四种协议，投入分散。

**问题四：模型边界。**

- 求解器是频域稳态线性网络加工作点迭代，没有瞬态；这是合理取舍，但需要让使用者知道。
- 测试台元件只有电阻、RC 低通、探头、线缆、缓冲器；真实 DUT（电路板、电源模块）需要写 Python 插件。
- 非 SCPI 设备（串口、Modbus、私有协议）没有入口；GPIB/USB 地址只在 PyVISA 后端中有效。
- 仿真的是仪表**对外的行为**，不是仪表内部的 FPGA/DSP 算法。

## 3. 场景一：仪表短缺

做法：按内部真实的紧缺情况选型号，做深而不是做多。

- 向内部工程师收集紧缺清单（哪些仪表排队最久）与他们现成的脚本。
- 只对清单上的 2–3 个型号继续投入，目标是真实脚本原样跑通；其余型号停止扩展。
- 每个做深的型号借一台真机对照一次（见 5.2）。

## 4. 场景二：自研仪表

### 4.1 谁用、解决什么

共同痛点：硬件样机来得晚、数量少、不稳定，下游工作都在等它。虚拟仪表是**命令手册的可执行版本**。

| 角色 | 在等什么 | 仿真提供什么 |
| --- | --- | --- |
| 固件/协议工程师 | 命令集定稿 | 命令手册草稿变成能连上的虚拟仪表，评审时直接试 |
| 上位机/驱动工程师 | 能通信的样机 | 硬件就绪前开发 PC 软件、驱动、示例程序 |
| 校准/产线软件工程师 | 样机与标准器（贵、要排队） | 虚拟被校仪表 + 虚拟标准器，反复跑完整校准流程，含超差、调整失败等异常路径 |
| 测试工程师 | 样机 | 自动化测试脚本先写好，样机到了直接跑 |

### 4.2 使用流程

1. 协议工程师给出命令手册草稿：命令、参数范围、回复格式、错误码。
2. Agent 经 MCP 按手册生成仪表定义（D3），定义的 `reference` 填自己的手册。
3. 在 Web 验收页确认：命令清单、内部结构、试发命令。
4. 把手册中的示例写成用例文件（`cases.yaml`），`simubench cases` 运行。
5. 下游接入：上位机与校准程序只换资源地址；校准场景配上虚拟的校准源或标准表（5522A、5730A、8588A）搭成测试台。
6. 样机到货后，同一份用例对真机运行。不一致处要么是固件缺陷，要么是定义写错。
7. 固件改版时定义随之修改，用例在 CI 中回归。

样板：`examples/lowfreq-cal/`（第 2–5 步，两台按接口契约写的自定义仪表，主机程序不改源码）；
`examples/demo/calibrate_34465a.py`（校准流程与真值判定）。

### 4.3 缺口

按对本场景的影响排序：

1. **库中没有任何一台自研仪表。** 平台能力是用别家型号验证的；自家命令集中可能有平台表达不了的内容，只有做一台才知道。
2. **用例不能对真机运行。** 第 6 步需要“对真实资源地址执行同一份用例”的入口。工作量小，价值最高。
3. **非 Python 上位机未实测。** C#、C++、LabVIEW 经 NI-VISA 走 socket 或 HiSLIP 理论可行，没有实测记录；串口、Modbus、私有协议没有入口。
4. **服务只监听本机。** 每人本机运行没有问题；一个组共用一台虚拟测试台做不到。是否需要取决于内部的工作方式。
5. **仪表内部算法与架构的验证目前做不了。** 已确认属于需求（第 1 节）；现状与规划见第 7、8 节。

## 7. “软件定义仪表 + 合成仪表”：示波器与频谱仪和真实仪表的差距

产品的思路（D1、D50）是：仪表由真实的功能块组合而成（软件定义），不同仪表由同一个通用功能块库、
经软件“合成”出测量功能（合成仪表：信号调理、频率变换、数据转换、数字处理四类模块）。
这里的“共用”指**共用块的类型**，不是物理上共用一份硬件：每台仪表有自己的实例和参数
（示波器的 ADC 是 8 位、每秒数吉采样，频谱仪的是 16 位、每秒数百兆采样，但它们是同一种块）。
本节对照代码（`library/components/scope.py`、`specan.py`、`docs/blocks/`）看这个思路落实到哪一步。

### 7.1 架构层面：三处与思路不符

1. **网络上传递的是稳态谱线，不是采样流。** 信号是“直流 + 若干条谱线”的解析描述（`engine/signal.py`），
   电路按频率求解。好处是精确、快、可复现；代价是没有瞬态：电路对变化的响应是立即切换到新稳态，
   没有过渡过程，也没有单次事件（毛刺、上电过冲、偶发异常）。示波器最核心的用途是抓单次事件，目前没有对象可抓。
2. **频谱仪的功能块有名字，没有信号流。** `specan.py` 的说明写明除输入端口外各块都是“数据级”：
   衰减器、混频器、中频、检波、视频滤波是参数的持有者，由迹线引擎依次读取；谱线直接经高斯 RBW 滤波画到迹线上，
   没有真的混频。因此没有本振、镜像、中频这些中间信号，功能块之间的输出也无法替换（D1 的设想）。
   示波器的拆分更接近真实结构，但采集组件同样是按名字引用各模块，而不是信号在模块之间流动。
3. **示波器与频谱仪没有用同一批块类型搭出“数字化 + 数字处理”。** 按合成仪表的思路，频谱仪 = 下变频 + 数字化器 + FFT，
   其中数字化器与数字处理和示波器用的是同一种块（各自的实例、各自的参数）。现在两者是各自独立的实现（约 2100 行与 1000 行），示波器没有 FFT/数学通道，频谱仪没有 FFT 扫描；
   把现有功能块重新接线，拼不出一台新类别的仪表（如矢量信号分析仪）。instrument-authoring.md 8.1 已指出同一问题。

### 7.2 示波器

| 真实仪表的功能块 | 已建模 | 未建模 |
| --- | --- | --- |
| 输入与探头 | 输入阻抗与电容对电路的加载、探头比、通道时延 | — |
| 垂直通道 | 耦合、带宽及滤波形状（一阶、砖墙、高斯、Bessel、Butterworth）、档位与偏置范围、增益与偏置的个体偏差与校准常数 | 档位切换的继电器/衰减器耗时与过载恢复 |
| ADC | 位数、量化、削波、采样率上限与通道配对 | 有效位数随频率下降、非线性（INL/DNL）、交织失配杂散 |
| 时基 | 记录长度规则、采样率阶梯、时钟误差、触发抖动 | 滚动模式、等效时间采样的细节 |
| 触发 | 边沿触发：独立耦合通路、迟滞、释抑、亚采样插值；采集作为待完成操作 | 脉宽、欠幅、码型、视频、串行总线触发 |
| 采集 | 普通、平均、峰值检测、高分辨率；AUTO/NORMAL/SINGLE/STOP | 分段存储、余辉与波形刷新率 |
| 数字处理 | 自动测量（幅度、频率、周期等，含直方图法顶底值、迟滞、无效判定） | 数学通道、FFT、光标、串行解码、模板测试 |
| 远程 | 波形传输（前导、二进制块） | 各型号约 80% 的命令（DSO-X 2024A 实现 109/487） |

结论：示波器的信号链结构已接近真实仪表，短板在**触发类型、数字处理功能与瞬态信号**。

### 7.3 频谱分析仪

| 真实仪表的功能块 | 已建模 | 未建模 |
| --- | --- | --- |
| 输入衰减器 | 自动/手动衰减、混频器过载判定 | 衰减器切换不确定度、前置放大器、预选器 |
| 混频与本振 | 参考时钟误差对频率轴的影响、外参考锁定 | **相位噪声**、镜像与杂散响应、残余响应、本振馈通 |
| 非线性 | 仅过载标志 | **二次谐波与三阶交调失真、增益压缩** |
| 中频与 RBW | 高斯滤波、步进规则、RBW 自动耦合 | 滤波器形状因子、RBW 切换不确定度、FFT 扫描 |
| 幅度精度 | 噪声底 kT·F·NBW（随 RBW 与衰减变化） | **频响平坦度**、噪声底随频率变化、绝对幅度不确定度、校准常数与个体偏差 |
| 检波与视频 | 六种检波器、VBW、平均类型 | 扫描过快导致的幅度与频率误差 |
| 迹线与标记 | 写入/平均/最大/最小保持、峰值搜索、频率计数 | 噪声标记、带功率、通道功率、邻道功率比、占用带宽 |
| 其他 | 按虚拟时间扫描 | 零扫宽、IQ 采集与解调、跟踪源 |
| 远程 | — | N9042B 实现 64/1309，N9320B 实现 54/260 |

结论：频谱仪目前是一台**理想接收机加热噪声**。凡是以分析仪自身性能为限的测量——相位噪声、交调、杂散搜索、
邻道功率——都会得到理想结果，而这些正是射频测试脚本的主要内容；它也没有可校准的误差，无法充当被校仪表。

### 7.4 三个层次

| 层次 | 用途 | 现状 |
| --- | --- | --- |
| 行为级：命令、状态、数值合理 | 上位机、驱动、测试脚本 | 已有基础，缺命令覆盖 |
| 指标级：误差、噪声、失真按数据手册指标出现 | 校准程序、测试方案评估 | 示波器部分具备，频谱仪基本没有 |
| 信号链级：采样流在功能块之间流动 | 验证仪表内部算法与架构 | 不具备 |

三层都在需求内（第 1 节）。第三层的做法与顺序见第 8 节。

## 8. 信号链级仿真：验证仪表内部的算法与架构

### 8.1 要回答的问题

算法与架构工程师想在硬件之前知道的事，举例：

- **架构**：ADC 用 12 位还是 14 位、采样率多少，噪声底与动态范围够不够；增益怎样分配；中频选在哪里，镜像与杂散落在何处。
- **算法**：数字下变频与抽取滤波的通带纹波和阻带泄漏；RBW 数字滤波器的形状因子；检波与平均的统计是否正确；
  数字触发的抖动；高分辨率抽取实际提高了几位；sin(x)/x 插值的误差；平坦度补偿、通道失配校正是否收敛。
- **定点实现**：位宽截断后与浮点模型差多少，是否溢出。

共同点：需要**采样点在功能块之间流动**，每一级的输出可以观察、可以替换成自己的实现、可以与金标准比对。

### 8.2 做法：模拟域保持解析，数字域用采样流，ADC 是边界

不替换现有的信号表示，而是在它上面加一层：

```
测试台与模拟前端（现有）            │  数字域（新增）
谱线 + 传递函数，解析、精确         │  采样流：定长帧，带采样率、数据格式（实数/IQ、浮点/定点）
源 → 线缆 → DUT → 衰减 → 放大 → 滤波 → [ADC] → 下变频 → 抽取 → 滤波/FFT → 检波 → 迹线/测量
                                    ↑ 按采样时刻对解析信号求值，加噪声、量化、非理想
```

- **依据**：真实的软件定义仪表本来就是这个结构，ADC 之后全是数字处理，待验证的算法几乎都在 ADC 之后。
  architecture.md 2.2 已有“逐点采样”的求值方式，示波器的采集就是按采样时刻对解析信号求值再量化，边界已经存在，只是没有成为公共的块。
- **保留的性质**：模拟域仍然精确且快；噪声用计数器式随机数（按种子与样本序号），同种子逐位复现不变（architecture.md 2.5）。
- **模拟域的非线性**（混频器、放大器压缩）先在谱线级解析计算（交调产物是新增的谱线）；需要逐点非线性时，在过采样的采样流上做。
- **瞬态与单次事件**：由时域信号源提供（任意波段、录制波形，D14），经线性网络时用有限长记录的频域方法；这是 8.4 的最后一步，不是前提。

### 8.3 需要新增的能力

| 能力 | 内容 |
| --- | --- |
| 采样流端口 | 功能块之间的一种新连接：帧数据 + 采样率 + 格式；按需拉取（下游要 N 点，上游产生），速率变换与延迟由块声明 |
| 通用 ADC 块 | 从示波器的采集中提出：采样时钟（含抖动与 ppm）、量化、削波、有效位数、交织失配；一种块类型，示波器与频谱仪各建自己的实例、各填自己的参数 |
| 数字处理块库 | NCO/数字下变频、CIC/FIR 抽取、窗与 FFT、数字滤波器、检波器、平均、数字触发、插值 |
| 定点数据类型 | 位宽、舍入与饱和方式；同一块可在浮点与定点下运行并比对 |
| 内部探针 | 任一块的输出可在界面与 SDK 中看时域与频谱（现有虚拟探针只到测试台的网络） |
| 算法托管 | 算法工程师把自己的实现放进某一块：Python 插件（现有插件出口，instrument-authoring.md 4）；C/C++ 动态库；与金标准向量逐点比对并报告第一处不同 |
| 链路预算 | 由各块的声明参数直接算出级联噪声系数、增益、截点、动态范围，与采样流仿真的结果互相核对 |

不做的：通用的系统仿真平台（MATLAB/Simulink、SystemVue、GNU Radio 已经成熟）与 HDL 仿真器。SimuBench 的独特之处是
**算法跑在一台可以被上位机和脚本驱动、接在测试台上的虚拟仪表里**：同一条信号链既是算法的验证环境，也是下游软件的开发环境。
算法团队已有的 MATLAB 或 C 模型通过“算法托管”接入，而不是在这里重写。

### 8.4 顺序

| 步骤 | 内容 | 完成的标志 |
| --- | --- | --- |
| A0 | 向算法/架构工程师确认：试点仪表、现在用什么工具建模（MATLAB、C、HDL）、最想提前验证的三件事 | 有一份具体的验证清单，8.1 的例子换成他们自己的 |
| A1 | 采样流端口与通用 ADC 块；示波器的采集改为经它们实现 | 示波器全部现有用例的回复不变；ADC 输出可用内部探针观察 |
| A2 | 用 A1 的块搭一台 FFT 式频谱仪：模拟前端（解析）→ ADC → 数字下变频 → RBW 滤波/FFT → 检波 → 迹线 | 对同一输入，与现有解析式频谱仪的迹线在声明的容差内一致；两种实现互为对照 |
| A3 | 算法托管与金标准比对；定点类型 | 算法工程师把一个自己的滤波器或检波算法放进 A2 的链路，比对通过 |
| A4 | 频谱仪模拟前端的指标级非理想（7.3 的未建模项）；链路预算 | 改 ADC 位数或中频增益，噪声底与无杂散动态范围的变化与预算一致 |
| A5 | 时域信号源与瞬态；示波器的数字触发类型、分段存储在采样流上实现 | 单次毛刺能被脉宽触发抓到 |

A2 是“合成仪表”思路的第一个实例：示波器与频谱仪由同一批数字化与数字处理块类型搭成（不是共用一份实例）。它同时提供了目前缺少的一种正确性对照——
两套独立实现算同一个量。

### 8.5 风险

- **性能**：采样流在 Python/NumPy 上按帧向量化计算，单次采集百万点量级可行；长时间连续流不行。D19 已为计算密集部分留了改用 Rust 的边界，按性能分析决定。
- **范围**：第三层的工作量与前两层之和相当。A0 暂时做不了（8.7），因此第一版只做**同时改善外部行为**的那部分内部结构；没有外部收益的能力（算法托管、定点、金标准比对、链路预算工具）等 A0 之后再做，否则会做成一个没有人用的通用框架。
- **人**：这一层的验收者必须是算法或架构工程师（D11）。

### 8.6 对第 5 节顺序的调整

- 5.1 的三项确认增加 A0。
- 5.2 的第 2 步（试点一台在研仪表）不变，并且是 A0 的前提：试点仪表同时是第三层的对象。
- 5.2 的第 3 步（短缺型号做深）降为按需进行，只做紧缺清单上最靠前的一台。
- 5.3 暂停的投入不变：不增加新型号与新的界面功能。

### 8.7 第一版的策略：对外是行为仿真，内部按信号链实现

A0（直接找算法与架构工程师谈验证需求）现在做不了：最终目标在没有实物时讲不清楚。因此第一版这样做（产品负责人 2026-11-11 确认）：

- **对用户**：第一版就是仪表外部行为的仿真——脚本与上位机连上能用，行为与真机一致。用户验证的是这一点。
- **对内**：示波器与频谱仪按第 8.2 节的信号链结构实现，使内部结构本身真实、专业。
- **之后**：用户认可行为仿真、看到内部结构之后，再谈“用它验证仪表内部的算法与架构”，届时补做 A0 与 A3。

**做什么、不做什么**

| | 内容 | 用户看得到 |
| --- | --- | --- |
| 做 | A1：采样流端口、通用 ADC 块，示波器经它们实现 | 行为不变 |
| 做 | A2 + A4：频谱仪改为真实信号链，带前端的非理想（相位噪声、交调、杂散、平坦度） | 行为更接近真机（7.3 的未建模项出现在迹线上） |
| 做 | 内部结构图上的信号：每个功能块的输出都有真实的中间信号，可点开看时域与频谱；参数用数据手册的语言 | 看得到，这是“内部结构真实”的证据 |
| 做 | A5 中有外部收益的部分：示波器的脉宽等触发类型、分段存储 | 行为更完整 |
| 不做（等 A0） | 算法托管、定点类型、金标准比对、链路预算工具 | — |

**三条约束**

1. **内部结构必须是真的，不能只是画出来的。** 懂仪表的人会点开每一块看。一个标着“混频器”的块如果没有输出信号，
   比没有这个块更糟。所以内部探针属于第一版要做、要让用户看到的部分；被推后的只是“把自己的算法放进去”的那一组能力。
2. **结构的依据要写明。** 每台仪表的功能块划分依据公开资料（厂商手册的工作原理章节、应用指南；D50、component-map.md），
   在界面与文档中说明它是**功能框图级的模型**，不是该型号的实际电路设计。自研仪表的结构则由自己的设计文档给出。
3. **为第三层留好接口，但不提前实现。** 每个数字处理块是“输入帧、参数、状态 → 输出帧”的函数，端口带采样率与数据格式，
   块可经现有插件出口替换。满足这三点，A3 以后是纯增量。

**第一版的范围**：一台示波器、一台频谱仪。型号仍需向内部工程师问清（他们手头用的是哪台、有没有现成脚本）；这只是问型号，不涉及最终目标。

**从第一版过渡到最终目标的演示**：打开频谱仪的内部结构图，把 ADC 的位数从 16 改成 12，迹线的噪声底随之抬高；
把 RBW 数字滤波器换成另一种形状，邻近信号的分辨能力随之变化。这时再问“你们的算法想不想放进来试”，对方有东西可看。

**风险**：第一版的验收仍然需要懂仪表的人说“行为对”“结构像”；团队里没有这样的人时，至少借一台真机做对照（D11），
并请一位内部工程师看一遍内部结构图。

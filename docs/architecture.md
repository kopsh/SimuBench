状态：草案。

## 0. 总览

```
┌──────────────────────────── 客户端 ────────────────────────────┐
│  界面（Web Bench / TUI）  定标与测试脚本  AI Agent  pytest / CI │
└──────┬──────────────────────┬──────────────┬──────────┬────────┘
       │                      │              │          │
┌──────┴──────────────────── 接入层 ─────────────────────┴───────┐
│  界面服务   PyVISA 后端   SCPI 网络仪表   MCP 服务   Python SDK │
│                     （都调用同一套引擎接口）                    │
└──────────────────────────────┬─────────────────────────────────┘
┌──────────────────────────── 引擎 ──────────────────────────────┐
│  会话（运行中的 Bench）：动作队列 · 虚拟时钟 · 网络求解 ·        │
│  信号求值 · 组件状态 · 随机数 · 事件 · 故障                      │
└──────────────┬─────────────────────────────────┬───────────────┘
┌──────────── 模型层 ───────────┐   ┌──────── 可观测性 ──────────┐
│ 组件库 · 仪表定义 · 模板 ·     │   │ 运行记录 · 虚拟探针 · 因果  │
│ Bench 定义 · 波形文件          │   │ 解释 · 日志 · 指标 · 诊断   │
└────────────────────────────────┘   └────────────────────────────┘
```

设计原则：

1. **组件组合**（D1）：从 Bench 到仪表内部使用同一套“组件 + 端口 + 连线”；行为由组件决定，命令层只是映射。
2. **Bench 是核心对象**（D8）：所有操作围绕 Bench 的定义、运行与记录。
3. **以仪表展示**（D1）：组件是实现方式，界面展示的是仪表。
4. **单一入口**：任何改变运行中 Bench 的操作都是一个“动作”，按顺序执行并进入运行记录。
5. **确定**（D6、D12）：同一版本、同一 Bench、同一种子、同一动作序列，结果完全一致。
6. **可观测**（D16）：每个结果都能被观察、解释和回放。
7. **拒绝优于猜测**：超出模型能力时明确报错并标注，而不是返回看似合理的结果。

## 1. 组件模型

### 1.1 组件

组件是 SimuBench 的基本构件。一个组件类型由五部分组成：

| 组成 | 说明 | 例子（一阶低通） |
| --- | --- | --- |
| 端口 | 名称、方向（输入 / 输出 / 双向）、介质（电压信号、参考时钟、触发）、阻抗 | `IN`（输入）、`OUT`（输出） |
| 参数 | 类型、单位、范围、梯级规则；可由命令或 Bench 设置 | 截止频率、阶数 |
| 隐藏状态 | Bench 可设置、命令读不到、只能通过测量发现 | 元件容差造成的截止频率偏差 |
| 动态状态 | 随时间演化的内部状态 | 滤波器的状态变量 |
| 行为 | 见下表 | 对信号施加 H(f)；向输入网络呈现输入阻抗 |

行为分为五类，一个组件可以具备其中几类：

| 行为 | 含义 | 例子 |
| --- | --- | --- |
| 信号变换 | 由输入信号与参数得到输出信号 | 滤波、衰减、乘法器、耦合 |
| 电气负载 | 端口对所在网络呈现的阻抗或戴维南等效 | 50 Ω 输出级、1 MΩ 输入、探头 10 MΩ |
| 求值 | 把信号转换成测量结果 | ADC 采样、锁相解调、频谱计算、计数器 |
| 时间消耗 | 某操作需要的虚拟时间（D12） | 一次采集、一次扫描、一次积分 |
| 事件 | 条件满足时产生事件 | 过载、失锁、超出模型能力 |

### 1.2 组合组件与封装

组合组件包含子组件与内部连线，对外暴露一部分端口与参数。三种常见的组合组件：

| 组合组件 | 对外暴露 | 额外具备 |
| --- | --- | --- |
| 仪表 | 端口、可设置参数 | 命令层、状态系统、身份信息（第 3 节） |
| DUT | 端口、参数 | — |
| Bench | — | 运行条件、故障、布局（第 4 节） |

因此“仪表是封装好的小 Bench”：两者使用同一套组合机制，区别只在于仪表多了命令层。

**组件替换**：组合组件内部任一子组件的输出都可以被另一个组件替换（例如用波形文件源替换 ADC 的输出，D14）。替换写在 Bench 中，不修改仪表定义。

### 1.3 多通道

- 仪表定义中声明**通道定义**（一组组件与内部连线的模板）与**通道实例**（每个通道的参数，可不同），引擎按此展开（D15）。
- **共享组件**（时基、触发、存储）在仪表层声明一次，各通道连接到它。
- **跨通道组件**（数学通道、通道组合、相位同步）以多个通道的端口为输入。

### 1.4 连线、网络与求解

- **连线**连接两个端口；相互连通的端口构成一个**网络**。
- **配件属于连线**：探头、线缆、衰减器是串在连线上的组件，Bench 中写在连线上，展示为连线的属性。
- **一个网络只能有一个驱动源**；多个驱动源在校验时报错。
- **求解分两部分**：
  1. **线性网络**：端口的阻抗与二端口组件（RC、探头、线缆、缓冲器）构成线性网络，按频率做节点分析，得到每个网络相对于每个驱动源的传递函数。这样负载效应、源阻抗分压和多级串联都由求解得到，不需要逐级特殊处理。
  2. **非线性元件**：带限值的源（SMU、电源的恒压/恒流）、电子负载等用分段线性模型，通过直流工作点迭代求解；仪表内部扫描按负载线计算，负载在扫描范围内不是一条直线时拒绝（validation-smu.md）。
- **何时求解**：拓扑、参数或开关状态改变时重新求解；只改变信号源内容（如频率）时只更新信号描述。
- **不在第一个闭环**：瞬态电路耦合（探头电容、线缆长度造成的上升沿与振铃）。

> 求解按物理正确进行，与参考场景数值的差异按 D13 逐项记录在场景文档中。

### 1.5 组件库

第一批组件从验证场景归纳，同一组件在多处复用：

| 类别 | 组件 |
| --- | --- |
| 信号源 | 直流、正弦、方波、锯齿、脉冲、噪声、任意波、PRBS、波形文件源、调制器（AM / FM / PM） |
| 线性处理 | 增益/衰减、n 阶低通、n 阶高通、耦合（DC/AC）、带宽限制、延迟、求和 |
| 非线性处理 | 乘法器（混频）、削波、限幅、检波（峰值、平均、有效值、采样） |
| 电气 | 输出级（戴维南源）、输入端口（阻抗）、电阻、电容、二端口 RC、缓冲器、带限值的源、电子负载 |
| 采集与测量 | ADC（采样、量化、限幅）、触发（施密特、边沿、自动）、存储、锁相解调、频谱计算（谱线 + FFT 路径）、计数器、正弦拟合 |
| 时钟 | 时基（含隐藏偏差）、参考输入/输出与锁定、内部振荡器、锁相环 |
| 控制 | 梯级取档、自动增益、自动相位、扫描序列器（列表、步进）、过载检测 |
| 误差（定标场景） | 增益/偏置/非线性误差、漂移、定标系数修正 |

## 2. 信号

### 2.1 信号描述

网络上传递的是**信号描述**：一棵表达式树，而不是采样点。

```
网络 net-out 的描述（示波器场景）：
  ÷10（探头） ← H_RC(f) ← 戴维南分压 ← sine(1 kHz, 1 V 峰值)
```

- **叶子**：信号源（直流、正弦、方波、锯齿、噪声、任意波表、PRBS、波形文件）。
- **线性节点**：缩放、求和、传递函数 H(f)（以零极点或有理式表示）、延迟。
- **非线性节点**：乘法、削波、取绝对值；调制展开为谱线集合。
- 信号描述按时间分段：参数在某一时刻改变时，从该时刻起使用新的描述；带动态状态的组件（如锁相放大器的低通）记录状态并按精确解推进（2.4）。

### 2.2 三种求值方式

读取信号的组件按需要选择求值方式：

| 求值方式 | 适用 | 精确性 |
| --- | --- | --- |
| **谱线** | 周期信号经过线性处理；锁相解调、频谱计算、有效值 | 正弦、方波、锯齿用解析式，精确 |
| **逐点采样** | ADC、触发、示波器波形 | 按采样时刻求值；线性滤波用精确离散化 |
| **直流** | 万用表直流档、工作点、SMU | 精确 |

**数值路径**：任意波、PRBS、削波、录制波形没有解析谱线，按需生成采样后计算（FFT、整周期数值解调），受能力上限约束。

### 2.3 能力上限与截断

所有截断与上限都由明确规则定义并公开误差界：

| 规则 | 例子 |
| --- | --- |
| 调制谱线截断 | FM/PM 按卡森规则保留 floor(β)+1 阶；遗漏功率上界 4.1% |
| 谱线数上限 | 一个信号最多 999 条谱线；一条迹线最多 65 536 条 |
| FFT 记录长度上限 | 2²⁰ 点 |
| 数值解调窗口 | 至少 256 个整参考周期 |

超出上限时：产生“超出模型能力”事件（第 6 节），仪表按其定义返回对应错误码（如 329、−221），结果标注保真度。

### 2.4 时间与动态状态

- 带动态状态的线性组件（低通、高通、积分器）以状态空间形式保存状态与“上次更新时间”；求值时从上次更新时间精确推进到当前虚拟时间，不按固定步长迭代。
- 结果只取决于虚拟时间与动作序列，与求值的频率或真实耗时无关。

### 2.5 噪声与随机性

- 噪声由**计数器式随机数**生成：数值由（Bench 种子、组件编号、通道、时间或样本序号）决定。
- 因此同一虚拟时刻两次读取结果相同，不同通道相互独立，结果可复现，并且不依赖求值顺序。

## 3. 仪表定义

### 3.1 定义文件的结构

仪表定义是一个声明式文件（YAML），包含：

| 部分 | 内容 |
| --- | --- |
| 元信息 | 厂商、型号、类别、版本、能力标签 |
| 身份 | `*IDN?` 模板；序列号、固件版本可由每个实例在 Bench 中覆盖（calibration-notes.md） |
| 通道 | 通道定义与通道实例（1.3） |
| 组件与连线 | 内部组件、内部连线、共享组件（1.2） |
| 端口 | 对外端口及其映射到的内部端口 |
| 可设置状态 | 对外参数：类型、单位、范围、梯级、默认值、`*RST` 值；绑定到内部组件参数 |
| 命令 | SCPI 命令树（3.2）；每条命令绑定到可设置状态、查询或动作 |
| 动作 | 多步行为（自动增益、自动相位、扫描），由控制组件执行 |
| 状态系统 | IEEE 488.2 状态字节、标准事件寄存器、`*OPC`、设备相关寄存器、错误队列 |
| 时间 | 每条命令消耗的虚拟时间，可依赖参数（如扫描时间）（D12） |
| 显示提示 | 类别模板绑定、摘要字段、控件样式（D1） |
| 危险标记 | 需要确认的命令（MCP 与界面使用） |

### 3.2 命令层

命令层是通用的 SCPI 引擎，每台仪表只提供命令树，不写解析代码：

- 遵循 SCPI 规则：长短格式、大小写不敏感、可选节点 `[...]`、数字后缀（映射到通道号，省略时按默认值）、`;` 复合命令与路径规则、`*` 公共命令。
- 参数：数值（含单位后缀与 MIN/MAX/DEF）、布尔、枚举、字符串、列表（加引号与不加引号都接受，D13）、定长二进制块。
- 响应：数值格式、字符串、IEEE 488.2 定长二进制块（字节序、字长可配置）。
- 标准错误：命令错误（−1xx）、执行错误（−2xx）、设备错误（−3xx）、查询错误（−4xx）；设备相关错误码由仪表定义。
- 命令行为对齐真实仪表（D13）：与参考实现不同之处在验证场景文档中逐项列出。

### 3.3 模板

模板服务于 D3 第 2 层：

- 每个仪表类别有一个模板，参数用数据手册的语言表达（量程、准确度表、带宽、采样率、噪声）。
- 模板包含从这些参数到内部组件参数的**映射函数**（例如把“1 年准确度 ±(35 ppm 读数 + 5 ppm 量程)”映射成 ADC 增益与偏置误差的分布）。
- 填好的模板生成一份完整的仪表定义，与手写定义没有区别。

### 3.4 自定义组件

D3 第 3 层需要表达声明式定义无法描述的行为时，可用代码实现自定义组件，通过插件注册，接口与内置组件相同。加载规则与声明式能力的设计见 [instrument-authoring.md](instrument-authoring.md)。

### 3.5 校验

仪表定义与 Bench 共用一套校验机制：每条诊断包含错误码、文件内位置（JSON 指针）、说明与修改建议，供界面显示与 Agent 自我纠错（D9）。`simubench validate` 两种文件都接受；定义的检查项与错误码见 [instrument-authoring.md](instrument-authoring.md) 5.1。

## 4. Bench

### 4.1 Bench 定义文件

| 部分 | 内容 |
| --- | --- |
| 元信息 | 名称、版本、格式版本 |
| 仪表实例 | 实例名、引用的仪表定义及版本、身份覆盖（序列号、固件）、资源地址（可写真实测试台的地址，D5）、初始状态、隐藏状态 |
| DUT | 引用的组件或组合组件、参数、隐藏状态 |
| 连线 | 两端端口；连线上的配件（探头、线缆、衰减器） |
| 组件替换 | 例如用波形文件源替换某仪表某通道的 ADC 输出（D14） |
| 运行条件 | 随机种子、时钟模式（D12）、真实值可见性（D9） |
| 故障与场景 | 预设故障及触发时机 |
| 外部文件 | 波形文件等，按相对路径引用并记录哈希 |
| 布局 | 界面上的位置与大小；与仿真无关，单独成段，修改布局不改变仿真结果 |

### 4.2 三种形态

| 形态 | 在架构中的对应 |
| --- | --- |
| Bench 定义 | 上述文件，始终是干净的初始状态 |
| 运行中的 Bench | 引擎中的一个会话（第 5 节）；同一定义可启动多个会话 |
| 运行记录 | 会话产生的记录（5.6） |

运行状态不回写到定义（D8）。

### 4.3 编辑

Bench 的编辑操作（添加/删除仪表与 DUT、连线、修改配置、校验）实现在引擎中，界面画布与 MCP 共用（D9）。编辑作用于 Bench 定义；对运行中的会话，拓扑编辑需要重新启动会话，参数修改作为动作执行。

### 4.4 校验规则（示例）

| 级别 | 规则 |
| --- | --- |
| 错误 | 网络有多个驱动源；端口介质不兼容；引用的定义不存在；参数越界；端口不存在 |
| 警告 | 阻抗不匹配（如按 50 Ω 负载设定电平的源接到高阻输入）；未连接的输出；参考输入未连接却选择外部参考 |

## 5. 引擎

### 5.1 会话

会话是运行中的 Bench，拥有：组件实例、网络与求解结果、虚拟时钟、随机数、事件、故障、运行记录，以及一个动作队列。

### 5.2 动作：唯一的改变入口

| 动作 | 来源 | 说明 |
| --- | --- | --- |
| SCPI 命令 | 脚本、Agent | 发送给某台仪表的字节 |
| 配置 | 界面、Agent、SDK | 带外直接修改状态，与 SCPI 命令区分记录 |
| 推进时间 | 步进时钟下的 SDK、界面 | 虚拟时钟前进指定时长 |
| 注入故障 | 界面、Agent、SDK、预设场景 | 见 5.5 |
| 探针读取 | 界面、Agent、SDK | 只读，不改变状态（第 6 节） |

- 所有动作进入同一个队列，**按到达顺序串行执行**；多个客户端可同时连接同一个会话（D9）。
- 每个动作产生一条**转换记录**：状态变化、观测结果、事件、保真度、执行前后的虚拟时间。

### 5.3 虚拟时钟（D12）

- 虚拟时间用整数纳秒表示。
- **命令驱动**（默认）：动作按仪表定义声明的时长推进时钟；队列空闲时，虚拟时间跟随真实时间推进，并把这段推进作为“空闲推进”动作写入运行记录，使回放仍然确定。
- **墙钟**：虚拟时间等于真实时间。
- **步进**：只有“推进时间”动作才前进。

### 5.4 确定性

- 确定性的来源：整数虚拟时间、计数器式随机数（2.5）、串行动作队列、空闲推进写入记录。
- 保证范围：同一引擎版本、同一平台上逐字节一致。跨平台（Windows 与 Linux）的浮点结果在验收容差内一致，不保证逐字节一致（D20）。

### 5.5 故障

| 层次 | 故障 |
| --- | --- |
| 通信层 | 超时、断连、乱码、延迟、忙 |
| 仪表层 | 指定错误码、保护跳闸、参数漂移 |
| 组件层 | 改变隐藏状态（如元件值偏移） |

故障可立即注入，也可在 Bench 中预设触发时机。仿真专用的控制能力（注入故障、推进时间、读取真实值）在 MCP 中默认关闭，需显式开启。

### 5.6 运行记录

- **格式**：只追加的分段文件；头部记录引擎、组件库、仪表定义、Bench 的版本与哈希、种子、时钟模式；正文是动作、转换与事件记录。
- **内容要求**（参考 calibration-notes.md 第 5 节）：保存原始响应字节与全部精度；中止的运行同样保留；记录发起运行的客户端。
- **大数据**：波形默认保存为可重新生成的“配方”（版本、时刻、窗口、采样率、种子），需要时可选择保存原始数据。
- **回放**：在同一版本下按记录重新执行动作，得到相同结果；**对比**：逐动作比较两次运行的观测与事件。

## 6. 可观测性（D16）

### 6.1 用户可观测

| 能力 | 架构上的实现 |
| --- | --- |
| 虚拟探针 | 对任意网络或内部端口的信号描述求值；理想探针不参与网络求解，因此不影响电路。需要模拟真实探针的负载时，在连线上加入探头组件 |
| 状态与真实值 | 读取组件参数、动态状态与隐藏状态；真实值受会话的可见性开关控制 |
| 通信 | 转换记录中的 SCPI 动作，带虚拟时间与真实时间 |
| 事件 | 组件产生的事件进入事件流，带时间与来源组件 |
| 因果解释 | 每个观测结果附带**来源**：参与求值的表达式树、组件与参数值；“为什么读到这个值”即展开这棵树 |
| 保真度标注 | 每个观测结果带标签：精确、近似（附原因：截断、离散化）、超出上限、未建模 |
| 时间线 | 动作、转换、事件按虚拟时间排列 |
| 回放与对比 | 基于运行记录（5.6） |
| 出口 | 界面、MCP、CI 产物（运行记录、JUnit 报告）、导出 |

### 6.2 运维可运维

| 能力 | 架构上的实现 |
| --- | --- |
| 结构化日志 | JSON 日志，带会话编号、运行编号、组件编号 |
| 指标 | 求解耗时、动作延迟、内存、会话数、错误率；采用标准可观测性协议导出 |
| 产品改进信号 | 统计不支持的命令（只记命令头，不记参数）、触发的能力上限、常见错误 |
| 版本清单 | 引擎、组件库、仪表定义、Bench 格式的版本与兼容性 |
| 健康检查 | `doctor` 命令：检查环境、端口、版本、定义库、接入服务 |
| 诊断包 | 一键导出脱敏后的日志、版本、环境与运行记录摘要 |
| 问题重现 | 用户同意时，凭 Bench 定义 + 运行记录在产品团队本地回放 |

### 6.3 数据边界

每类数据在代码中标明归属，分别写入不同出口：

- **用户资产**（脚本、Bench 内容、波形、测量结果、完整运行记录）：只写入用户本地，不进入遥测；
- **运维数据**（日志、指标、产品改进信号、版本）：内部阶段默认发送到内部收集服务（D17），对外发布时默认关闭。

## 7. 接入层

### 7.1 引擎接口

所有接入方式调用同一套引擎接口：打开 Bench、启动/停止会话、提交动作、订阅事件、读取状态与探针、读取运行记录、编辑与校验 Bench。

### 7.2 进程结构

- **进程内**：脚本或 pytest 直接在自己的进程中打开 Bench（PyVISA 后端、SDK），适合 CI。
- **服务进程**：`simubench serve` 启动一个服务进程承载会话，界面、SCPI 网络仪表、MCP、外部脚本连接到它，适合交互调试与多客户端同时观察。
- 两种方式使用同一个引擎；服务默认只监听本机地址；客户端与服务之间使用本机 TCP，Windows 与 Linux 一致（D20）。

### 7.3 PyVISA 后端（D5）

- `pyvisa.ResourceManager("<bench 文件>@simubench")` 在进程内打开 Bench；也可连接到正在运行的服务。
- 资源名支持：Bench 中的实例名，以及 Bench 中为实例配置的真实测试台地址。后者让脚本连地址都不用改，只换资源管理器。
- 后端看得到每次读写，因此命令驱动的虚拟时间在这条路径上自然成立。
- 通信层故障（超时、断连等）在这一层生效，返回与真实 VISA 一致的错误。

### 7.4 SCPI 网络仪表（D9、D41）

- 每台仪表在本机监听一个 TCP 端口（raw socket）；端口可指定或自动分配，地址表在启动时输出。
- HiSLIP（IVI-6.1，D41）：所有仪表共用一个端口（默认 4880，`--hislip-port 0` 自动分配），按子地址 `hislip0`、`hislip1`…（或 `hislip_<实例名>`）区分；只实现 synchronized 模式，支持消息边界（`DataEnd`）、设备清除、读 STB、锁与 SRQ，与 PyVISA 后端的 `clear`/`read_stb` 语义一致；不实现 overlapped、TLS 与认证。客户端连接形如 `TCPIP0::127.0.0.1::hislip0,<端口>::INSTR`。
- 以后再支持 VXI-11、USBTMC 等协议。

### 7.5 MCP 服务（D9）

| 工具组 | 内容 |
| --- | --- |
| 构建 | 查询仪表定义库（`get_definition` 含组件、内部连线与端口）与组件库；组件目录 `list_components`（含内部组件，端口、参数、op 与电路角色，由组件类生成）；创建与编辑 Bench；校验并返回诊断 |
| 由脚本生成 | 分析脚本中的资源地址与命令，生成 Bench 草稿，列出模型不支持的命令 |
| 部署 | 启动会话，返回资源地址与脚本切换配置 |
| 仪表 | 发送 SCPI、读取状态与测量 |
| 观察 | 通信记录、事件、探针、因果解释 |
| 运行脚本 | 针对会话运行测试程序，返回判定与运行记录 |
| 仿真控制（默认关闭） | 注入故障、推进时间、读取真实值 |

- 危险命令带标记，需确认；对命令多的仪表分页提供，而不是为每条命令生成一个工具；MCP 层做限流。

### 7.6 Python SDK

进程内完整访问引擎接口：步进时钟、注入故障、读取网络信号与探针、读取运行记录；提供 pytest 插件（每个测试一个带种子的会话）。

## 8. 界面

### 8.1 第一个界面（已决定：Web Bench，D18）

| | Web Bench（本地服务 + 浏览器） | TUI（终端） |
| --- | --- | --- |
| 画布编辑与审阅 Agent 搭建的 Bench | 适合 | 很难做好 |
| 波形、频谱、IV 曲线 | 清晰，可缩放 | 字符分辨率，只能看大概 |
| 仪表内部组件图 | 适合 | 不适合 |
| 远程服务器、SSH | 需要端口转发 | 适合 |
| 开发成本 | 较高 | 较低 |
| 参考 | Galois 把可视化拓扑编辑器作为付费功能 | EdgeSim 的终端控制台 |

**决定：第一个界面做 Web Bench**，由本地的 `simubench serve` 提供，用浏览器打开，不需要安装桌面程序。TUI 以后作为补充（例如在远程服务器上查看会话状态）。引擎与界面分离（D7），选择不影响引擎。

### 8.2 Web Bench 的页面

| 页面/区域 | 内容 |
| --- | --- |
| Bench 画布 | 仪表卡片、DUT、连线与配件；拖拽与连线；校验诊断标在出错的位置；Agent 修改后显示差异，由工程师确认 |
| 仪表卡片 | 由仪表定义自动生成（类别模板 + 通用布局，D1）；按通道显示设置、读数、端口与所连网络、错误队列 |
| 仪表屏幕 | 打开一台仪表：示波器波形、频谱迹线、锁相读数与建立曲线、SMU 的 IV 曲线、信号源各通道 |
| 通信与事件 | SCPI 通信记录（虚拟时间与真实时间）、界面与 Agent 的操作、事件，同一条时间线 |
| 虚拟探针 | 点选任意网络或仪表内部端口，查看信号；对读数请求因果解释 |
| 控制 | 修改参数、注入故障、暂停/单步/加速虚拟时钟、真实值开关 |
| 运行记录 | 回放、对比两次运行 |
| 仪表内部 | 主动打开时显示组件图（D3 第 3 层）；第一个闭环中只读 |

### 8.3 技术要点

- 界面通过 WebSocket 订阅会话的事件与状态，提交动作；与其他客户端一样走引擎接口。
- 波形与迹线由服务端按屏幕分辨率抽取后推送（每个像素列的最小/最大值），浏览器不接收全部采样。
- 布局保存在 Bench 文件的布局段（4.1），不影响仿真。
- 危险命令需要确认（3.1）。

## 9. 技术选型

### 9.1 约束

| 约束 | 来源 |
| --- | --- |
| PyVISA 后端必须是 Python 包 | D5 |
| 首批用户写 Python 脚本，pytest 插件与 SDK 面向 Python | D5、D6 |
| 数值计算：FFT（最多 2²⁰ 点）、按频率的网络求解、采样求值 | 第 2 节 |
| 确定性 | 5.4 |
| 内网部署：内部软件包源、内部 CI、离线可用 | D17 |
| Windows 与 Linux 都要支持 | D20 |

### 9.2 引擎实现语言（已决定：方案 A，D19）

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **A. Python + NumPy/SciPy** | 开发最快；与 PyVISA、pytest、MCP 生态天然一致；FFT 与线性代数由 NumPy 完成；打包简单 | 逐点逻辑多时性能受限；需要注意多线程数学库带来的不确定性 |
| **B. Rust 核心 + Python 绑定** | 性能好、内存安全、确定性易控制；EdgeSim 的构建依赖 Rust 工具链，可能采用此方案 | 开发较慢，团队需要 Rust 能力；每个平台需要编译发布 |
| **C. C++ 核心 + Python 绑定** | 性能好、生态成熟 | 内存安全与构建复杂度高 |

**决定：方案 A 起步，并为方案 B 留好边界。**

- 第一阶段在内部使用（D17），首要目标是尽快验证产品，6 个验证场景的计算规模不大，NumPy 足以胜任。
- 把计算密集的部分（信号求值、网络求解、频谱计算）放在清晰的接口后面；性能分析表明需要时，再把这些部分改用 Rust 实现，接口与上层不变。

### 9.3 其他选型（建议）

| 部分 | 建议 |
| --- | --- |
| 服务进程 | FastAPI：HTTP 与 WebSocket 服务；每台仪表一个异步 TCP 监听（D21） |
| MCP | 官方 Python SDK；本机 stdio 与 HTTP 两种方式 |
| PyVISA 后端 | 按 PyVISA 的后端扩展机制实现，注册名 `simubench` |
| Web 前端 | TypeScript + React + shadcn/ui；Bench 画布用 React Flow；波形与迹线用 Canvas 绘制（D21） |
| 接口生成 | Pydantic 模型为唯一来源：FastAPI 生成 OpenAPI → 生成前端 TypeScript 类型与客户端；WebSocket 消息、Bench 与定义文件、MCP 工具的 schema 由同一批模型导出；CI 检查生成结果是否最新（D21） |
| 定义与 Bench 文件 | YAML，配由 Pydantic 模型导出的 JSON Schema 校验 |
| 运行记录 | 分段 JSON Lines；以后可选列式格式用于大数据 |
| 日志与指标 | 结构化 JSON 日志；指标与追踪采用 OpenTelemetry 导出 |
| 确定性 | 固定依赖版本；数学库单线程运行；随机数用计数器式算法（如 Philox） |
| 发布 | 内部软件包源上的 Python 包；CI 用容器镜像 |

## 10. 验收

### 10.1 把场景文档变成自动化测试

- 每个验证场景对应一组 pytest 测试；场景中的 Bench 文件、脚本与期望值作为测试数据放入仓库。
- 测试脚本按场景文档中的操作编写，使用 SimuBench 的接入方式；与参考实现不同之处按场景文档的“差异”表处理（D13）。
- 期望值以数据文件保存，每个值附来源：参考场景的公开输出，或电路理论计算。

### 10.2 期望值必须独立于引擎

按物理正确重新计算的期望值（D13），由一个**独立的参考计算模块**给出：直接写出电路公式与解析解，不调用引擎的任何代码。否则引擎算错时，期望值会跟着错，测试无法发现。

### 10.3 允许偏差（建议）

| 类别 | 允许偏差 |
| --- | --- |
| 解析路径（谱线、直流、建立公式） | 相对 1e-6，或场景给出的显示位数 |
| 数值路径（FFT、数值解调、正弦拟合） | 按场景文档，如 0.05 dB、0.1% |
| 统计量（噪声标准差、平均） | 按样本数给出的统计区间，如 400 个样本时 ±10% |
| 多通道增益与相位 | 0.1%、0.1° |
| 错误码、状态位、点数、字节数 | 完全一致 |
| 确定性 | 同版本同平台逐字节一致 |

### 10.4 持续运行

- 每次提交在 CI 中运行全部场景测试；结果按场景汇总，失败时附运行记录，可在本地回放。
- 定标场景由产品负责人验收（D11）；引擎为它预留的能力（隐藏误差、定标系数、实例身份、真值判定）在场景测试中以单元测试覆盖。
